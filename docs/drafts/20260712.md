探讨一下，一个新项目如何进行系统设计、模块设计，再到具体实施。
背景：当前 AI 生成模块级代码已经能保证质量了，但是从系统总体的角度来看，局部最优不代表整体最优。现在需要考虑整个项目的 roadmap 和任务拆分了。
初步思路：
第一步先做架构设计，生成架构设计文档SAD：就是将整个系统划分为多个子系统，每个子系统有明确目标、范围、边界，各子系统之间确定 contract，并确定各子系统的要特别注意的事项；
第二步，对每个子系统进一步细化，生成各子系统的设计文档：将子系统拆分为多个子模块，每个子模块有明确目标、范围、边界，各子模块如何实现子系统对外 contract，各子模块之间确定 contract，并确定各子模块的要特别注意的事项；
第三步，对每个子模块进行细化设计，拆分成一个个 task 或 change。

以上是我的一些思考，希望能深入探讨一下，你结合业界的权威的最佳实践，从方法论到实践可行性来探讨一下。


拆分 roadmap 以及 change task的标准：
1. 目标是：一次就做出一个阶段结果，完整的结果。 不要一个事情分几次，跟别的功能混在一起做。 
2. 如果在执行过程中发现新的 bug，是跟本次功能相关的，就马上修改；发现新的 todo，与本次功能相关的，也马上做掉。
3. 有些功能需要别的模块配合，但现在没有，可以留占位，并记入 todo。
4. 核心原则一句话：change 边界往上合、内部粒度往下拆
5. 每一步迭代不追求完成一个完整可用的软件，而是达到当前 task设计的目标。


设计/实现过程中，方案决策的标准：
1. 首先应该判断是否能根本解决问题；
2. 要以最终目标为准，不能被现有的代码和设计所束缚，不能以目前的现状来反驳目标不该做，来限制目标的实现。
3. 最后才考虑改动成本

根据前面的讨论，对于子系统划分：
1. 子系统如何分解，分解的判据是什么？
- 变化率 / 变化原因：一起变的放一起，独立变的分开（信息隐藏的现代表述）
- 领域语言边界（DDD bounded context）：同一个词两边含义不同处即边界
- 数据所有权：谁 owns 写权，单写者原则
- 认知负载（Team Topologies）→ AI 语境翻译为 context 预算：一个子系统的完整设计 + 邻居 contract 必须装进一个 agent 的有效上下文
2. 子系统之间的 contract 如何确定？如何表达？
- 语法：API / schema / 类型（机器可查）
- 语义：不变量、前置/后置条件、错误语义（哪类错误谁负责、error taxonomy）、幂等性、顺序与并发假设
- 质量：延迟/吞吐预算、一致性等级
- 所有权：数据谁写、谁只能读
- 演进：向后兼容策略、版本规则
3. 是不是单独做一套基础横切面？
- 错误分类学、认证授权、可观测性约定、时间/时区、ID 生成、重试与幂等、配置策略、数据一致性策略——横切关注面不属于任何子系统
- 只能「约定集中化 + 每个模块任务把这份约定作为 context 强制携带」。
4. 如何做到骨架先行？
- Walking skeleton / tracer bullet（Cockburn、《程序员修炼之道》）：SAD 后第一个 change 不是任何子系统的第一个模块，而是穿过全部子系统边界的最细垂直切片，打通部署/集成/每条 contract。sdflow-implement 已在 ticket 层用 tracer-bullet，此处是同一思想上移到系统层。
- Contract 成熟度分级：draft →（骨架验证后）validated → frozen；frozen 后改动走显式变更流程（≈ ship_gate 设计门失鲜 REFUSE_START 的同一机制）。
- 回流（backflow）是三层文档活下来的唯一条件：没有回流的三层文档 = 三层谎言。AI 时代更致命——人类读过期文档会起疑，AI 把它当 ground truth 喂进 context，等于主动投毒。（仓内先例：「先改 assets、再推下游」单一真相源纪律。）
- 流水线不设全局 barrier：不要求「所有子系统 L2 完成才开始任何 L3」。唯一合法 barrier = 需要跨子系统信息汇总的决策点（如 contract 定稿评审——改一条边要两边同时看）。
5. 文档的维护生命周期：
- 文档允许迭代更新；
- 每次更新要确保后续 AI 读取不会误解；
- 每次更新也要保证人能分辨出哪些被删改了，哪些是增加的（改动部分用删除线划掉，并加时间和简短说明，但不删；新增部分也加时间和简短说明， 这样可行不？）
