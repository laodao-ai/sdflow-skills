## 0. 定位：原始三要素 vs 权威模板

**原始提案的第一步**：系统划分为多个子系统，每个子系统有明确目标/范围/边界，子系统间确定 contract，标注各子系统特别注意事项。

**对照结论**：此表述 ≈ arc42 十二节里的第 5 节（Building Block View）+ 半个第 11 节（风险）——约 **1.5/12**。它回答了「系统由什么构成」，权威共识还要求回答：

- **为什么是这个形状**（质量属性 + 决策 + 约束）
- **它如何运行**（运行时场景）
- **它站在什么之上**（外边界 + 部署）
- **什么贯穿所有部分**（横切概念 + 词汇表）

## 1. 缺口清单（按「缺了它会发生什么」排序）

### 缺口① 质量属性目标与场景（最重要）

SEI 核心论点：**塑造架构的不是功能，是质量属性**。功能几乎可在任何架构上实现；让方案分出高下的是质量要求（性能/可用性/安全/可修改性/可观测性…）。

缺失后果：

- 子系统划分**没有评判标准**——「这样切好不好」无对标物，评审镜只能凭感觉审；
- contract 的质量层（延迟预算、一致性等级）**没有来源**——必须从系统级质量目标分解，不能由各子系统自己发明。

权威做法：

- arc42 §1.2：**Top 3–5 质量目标，强制排序**（不许「都重要」）；
- SEI/ATAM **六元质量场景**落成可测度句子：刺激源→刺激→制品→环境→响应→**响应度量**。
  反例：「系统要高可用」；正例：「broker 断连时，运行中的 console 在 5 秒内进入可见的重连状态，不丢已接收消息」。
- **可测度的质量场景 = 未来 fitness function 的前身**（散文→可执行的机械化梯子，承 00 文档 §2.2）。

### 缺口② 运行时视图（动态行为）

原始三要素全是**静态**的（结构+契约）。Kruchten 4+1 的「+1」（场景视图）存在的唯一目的 = **用端到端场景验证其他视图**（arc42 §6 同理）。

做法：挑 3–5 个关键场景——主用例流、启动/停机、故障与恢复、数据一致性路径——在纸上**穿过所有子系统走一遍**，标出每步落在哪个子系统、跨了哪条 contract。

与核心关切的关系：跨子系统的时延累积、故障级联、一致性破洞**只在交互中显形，静态分解看不见**——这正是「局部最优 ≠ 整体最优」的主要藏身处。场景走查 = 「纸面上的 walking skeleton」（骨架 change 用运行证据验证 contract，场景走查用推演证据先筛一遍，同一思想的设计期/实施期两形态）。

### 缺口③ 系统自身的外边界（Context）

原始第一步直接从内部切分开始，跳过了更靠前的一问：**系统整体的内外边界在哪**——外部系统/角色/协议（C4 Level 1 Context、arc42 §3）。

优先级高的原因：**外部 contract 不可控**（第三方 API、硬件协议、遗留系统），不可控 = 风险最高 = 最该先钉死、最该在骨架 change 里先验证。内部 contract 错了自己改两边即可，外部 contract 理解错了返工代价不同量级。

### 缺口④ 架构决策记录（ADR）

arc42 §4（解决方案策略）+ §9（决策）/ Nygard ADR 实践。「注意事项」≠ 决策记录——ADR 必填三件：**决策 + 被否掉的备选 + 后果**。没有被否方案的记录，未来（人或 AI）会把否掉的路线再走一遍。**分解判据本身就该是第一条 ADR**（承 00 文档 Q1 结论）。

### 缺口⑤ 约束

arc42 §2：技术栈钦定、合规、预算、必须兼容的存量。**约束是解空间的输入**，与决策（解空间里的选择）必须分开记——否则评审时分不清「不能改的」和「可以挑战的」。

### 缺口⑥ 横切概念

arc42 §8：错误分类学、认证授权、可观测性、时间/时区、ID 生成、重试与幂等、配置策略……是 SAD 的**一等章节**，不是散落在各子系统注意事项里的碎片（论证见 00 文档 §2.3：横切约定不集中，N 个模块的 N 次生成各自发明 N 套——「局部最优≠全局最优」最高频的表现形式）。

### 缺口⑦ 部署视图

arc42 §7：进程形态、二进制形态、数据目录、分发方式。物理视图经常**反向修正**逻辑视图（哪些东西不能共进程/共文件，逻辑上就必须切开）。

### 缺口⑧ 风险与技术债登记

arc42 §11 / Fairbanks。「特别注意事项」最接近这条，但权威做法是**集中登记 + 用它分配设计深度**：风险清单直接决定哪个子系统做深设计、哪个一页纸带过（风险驱动）。

### 缺口⑨ 词汇表 / 统一语言

arc42 §12 / DDD ubiquitous language。对 AI 尤其关键：**术语漂移是多次生成之间一致性流失的最隐蔽通道**。

## 2. 防官僚化：不是填满十二节

- arc42 自身反复强调**裁剪**（tailoring）；ISO 42010：视图跟着利益相关者的关切走，不是越多越好；Fairbanks 整本书 = 「刚好够的架构」。
- 实操共识：**每节深度 ∝ 风险**，低风险节一句话带过甚至 N/A。
- 但「**考虑过并判定不需要**」和「**没想到**」必须可区分——跳过类判定显式留痕（与 sdflow workflow「跳过类判定必须显著呈现」同一纪律）。

## 3. 完整性检验：不问「节全了吗」，问「场景走得通吗」

ATAM 评估逻辑：拿 Top 3–5 质量场景 + 2–3 个端到端运行场景，逐个在 SAD 上走查——每一步能定位到子系统、每次跨界能指到 contract、每个质量场景能说出靠什么机制满足。**走不通的地方就是文档的洞**。比检查模板完整性有效得多，且评审镜可机械执行。

## 4. 最小可行 SAD 骨架（汇总）

| # | 内容 | 权威源 | 深度原则 |
|---|---|---|---|
| 1 | 目标 + **Top 3–5 质量属性**（强制排序 + 可测度场景） | arc42 §1 / SEI | 必填，半页起 |
| 2 | 约束（技术/组织/合规） | arc42 §2 | 列表即可 |
| 3 | **系统外边界**：外部系统/角色/外部接口 | arc42 §3 / C4-L1 | 一图一表 |
| 4 | 解决方案策略 + **ADR**（含分解判据、被否方案） | arc42 §4/§9 / Nygard | 每决策一条 |
| 5 | **子系统分解 + contract + 注意事项** ← 原始三要素 | arc42 §5 / C4-L2 | 核心；分解按 Q1 判据流水线 |
| 6 | **关键运行场景 3–5 个**（跨子系统走查） | arc42 §6 / 4+1 | 每场景一段一图 |
| 7 | 部署与进程形态 | arc42 §7 | 简 |
| 8 | **横切概念**（错误/认证/观测/时间/ID/重试…） | arc42 §8 | 一等章节 |
| 9 | 风险登记 → **驱动各子系统设计深度分配** | arc42 §11 / Fairbanks | 活清单 |
| 10 | 词汇表 / 统一语言 | arc42 §12 / DDD | 活文档 |
