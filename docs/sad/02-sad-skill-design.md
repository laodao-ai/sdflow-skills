## 0. 目标与范围校准（2026-07-12 重梳理）

**skill 目标（不放大）**：做架构设计，生成 SAD——系统划分为多个子系统（每个有明确目标/范围/边界）+ 子系统间 contract + 各子系统特别注意事项。

### 0.1 DoD 重定义（骨架先行的结构性后果）

skill 的完成态**不是「approved SAD」而是「skeleton-ready SAD」**——够切出骨架 change 即合格。纸上 contract 全是假设，在骨架 change 用真实调用验证之前不存在「定稿」。文档状态机：

```
draft → skeleton-ready →（骨架 change 验证 contract）→ validated →（逐条）frozen
```

这个重定义**系统性降低**两类要求（回答「是否要求过高」）：

- **对人的信息要求**：价值类（质量排序/数值/风险承受度）允许「AI 推荐值 + 待校准」占位放行，不阻塞——骨架前都是假设，逼人在 day 0 给准数是伪严谨；
- **对文档完成度要求**：contract 五层允许留洞（draft 态 + 显式标记），骨架前只强制主干三层：**语法 + 所有权 + 错误语义归属**。

### 0.2 「人无法提供」审计结论

不存在人绝对无法提供的信息，但三类价值判断**以抽象形式问就答不出**（排序、数值、承受度）。解法 = AI 承担「抽象→场景化」翻译：

- 不问「请排序质量属性」→ 问「broker 断连时，宁可丢消息还是宁可卡界面？」（排序从场景化二选一反推）
- 不问「延迟预算多少」→ 给域惯例推荐值让人**否决**（否决比填空容易一个量级）

**fail-closed 锁 draft 的关键项收窄为事实类三项**：一句话定位、外部系统清单、硬约束。价值类一律推荐+标记放行（D1 由此收结）。

### 0.3 范围分层（十节按目标重新定位，防 skill 自身违反「刚好够」）

| 层 | 节 | v1 深度 |
|---|---|---|
| **core**（目标本体 + 其前提与验证器） | §5 分解+contract+注意事项 · §3 外边界（切分的**前提**） · §6 场景走查（切分的**验证器**） · §8 横切（「注意事项」的集中化归宿） · 分解判据 ADR | 完整做 |
| **支持**（为 core 供料） | §1 质量属性（Top 3 场景化问答即可，不做完整六元场景） · §2 约束 · §9 风险（轻量登记） · §10 词汇表（判据流水线第一步顺产，零额外成本） | 轻量 |
| **条件** | §7 部署 | 仅当物理形态影响切分时展开 |
| **目标态（v1 不做全）** | S1–S11 完整 lint 投影 · 数值溯源三态 · 走查多镜大阵仗 | v1 机械层做最小集（节存在性 / 假设计数 / 排序存在）；走查 = 骨架前的 **cheap filter**，真验证在骨架 change |

## 1. 生成什么样的文档（形态）

**一份 SAD 主文档 + 两处分家 + 一份附录**，遵守单一真相源纪律：

| 产物 | 位置 | 说明 |
|---|---|---|
| **SAD 主文档** | `openspec/architecture/sad.md`——**项目级单例**（per-system 非 per-effort，生命周期 = 系统生命周期；D5 拍定，见 §8） | 十节骨架（见 §2），是「为什么是这个形状 + 由什么构成 + 如何运行」的单一入口 |
| **ADR 独立文件** | `openspec/adr/NNNN-*.md`（生态已有 home） | 决策记录**分家**——决策随时间累积、被后续 change 持续引用，生命周期比 SAD 单版本长；SAD §4 只放索引 |
| **词汇表** | `openspec/CONTEXT.md`（生态已有 home） | 统一语言**分家**——它被所有层（SAD/L2/change）引用，必须只有一份；SAD §10 只引用 |
| **假设清单（附录）** | SAD 附录或独立 `assumptions.md` | 全部 AI 推测/占位的聚合视图（见 §3 机制 A），机械可数 |

> 分家理由：ADR 与词汇表的**生命周期和引用面**都大于 SAD 本体——复述进 SAD 会造成双写发散。SAD 引用不复述（与「contract 单一真相源」同一纪律）。

## 2. 文档包含哪些内容：十节骨架

（来源标注：由业界权威模板交叉推导——arc42 / ISO 42010 / SEI / Kruchten 4+1；推导过程记录在同目录 01 文档，此处为完整规格）

| # | 内容 | 权威源 | 深度原则 |
|---|---|---|---|
| 1 | 目标 + **Top 3–5 质量属性**（强制排序、不许并列 + 可测度场景：刺激→响应→**响应度量**有数） | arc42 §1 / SEI | 必填，半页起 |
| 2 | 约束（技术/组织/合规）——**解空间的输入**，与决策分开记 | arc42 §2 | 列表即可 |
| 3 | **系统外边界**：外部系统/角色/外部接口（外部 contract 不可控 = 风险最高，最先钉死） | arc42 §3 / C4-L1 | 一图一表 |
| 4 | 解决方案策略 + **ADR 索引**（每条含决策+被否备选+后果；分解判据本身是第一条 ADR） | arc42 §4/§9 / Nygard | 每决策一条 |
| 5 | **子系统分解 + contract + 注意事项**（分解按 §5.1 判据流水线；contract 按下方五层规格） | arc42 §5 / C4-L2 | 核心 |
| 6 | **关键运行场景 3–5 个**（主流程/故障恢复/启停/数据一致性≥各一，跨子系统走查：每步落到子系统、每次跨界指到 contract） | arc42 §6 / 4+1 | 每场景一段一图 |
| 7 | 部署与进程形态（物理视图可反向修正逻辑视图） | arc42 §7 | 简 |
| 8 | **横切概念**：错误分类学/认证授权/可观测性/时间时区/ID 生成/重试幂等/配置策略…（集中一份 + 强制进每个模块任务的 context 包） | arc42 §8 | 一等章节 |
| 9 | 风险登记（含承受度）→ **驱动各子系统设计深度分配** | arc42 §11 / Fairbanks | 活清单 |
| 10 | 词汇表 / 统一语言（分家到 CONTEXT.md，此节只引用） | arc42 §12 / DDD | 活文档 |

**Contract 五层规格**（第 5 节的字段标准）：

1. **语法**：API / schema / 类型（机器可查）
2. **语义**：不变量、前置/后置条件、错误语义（哪类错误谁负责）、幂等性、顺序与并发假设
3. **质量**：延迟/吞吐预算、一致性等级（从系统级质量目标分解，不许各子系统自己发明）
4. **所有权**：数据谁写、谁只能读
5. **演进**：向后兼容策略、版本规则

每层允许**显式 N/A，不允许静默缺失**；每条 contract 另带**成熟度标签**：`draft →（骨架验证后）validated → frozen`（§7 lint 规则的挂钩点）。

**裁剪原则**：每节深度 ∝ 风险，低风险节一句话或 N/A——但「考虑过判不需要」与「没想到」必须可区分（跳过留痕）。

**skill 特有的增量要求**：每节内容必须带**来源标记**（见 §3 机制 A/B）——同样一句话，「人拍的」和「AI 猜的」在后续流程里的效力完全不同。

## 3. 文档质量如何判定：语义判据全集 → 机械化拆解

> **推导顺序（本节方法，2026-07-12 拍定）**：先枚举「好 SAD」的**语义判据全集**（质量的定义），再逐条问「有无确定性信号」——能结构化的下沉为脚本断言，残余留给评审镜与人门。**不从机械清单起手**——那会犯路灯谬误（能检查什么就把质量定义成什么）。

### 3.1 语义判据全集（S1–S11）

| # | 判据 | 一句话定义 |
|---|---|---|
| S1 可裁决性 | 质量目标有排序有度量，两方案冲突时文档能给出裁决 |
| S2 可走查性 | 关键场景在文档上走得通：每步定位子系统、跨界指到 contract、质量场景有满足机制 |
| S3 分解正当性 | 划分有判据、无反模式（entity-service / 流程式）、边界与变化对齐 |
| S4 contract 完备性 | 每条边界五层覆盖，缝隙不留给实现者自由发挥 |
| S5 可追溯性 | 决策有 why（备选+后果）、数值有来源、假设有标记——读者能区分事实/拍板/推测 |
| S6 一致性 | 术语统一、数值无互斥、各节不自相矛盾、不违约束 |
| S7 考虑面完整性 | 该考虑的都考虑过：十节全覆盖或显式 N/A；「考虑过判不需要」≠「没想到」 |
| S8 目标态锚定 | 设计锚目标态而非现状快照；不拿现状反驳目标 |
| S9 风险对位 | 设计深度与风险分布对齐：高风险深、低风险浅 |
| S10 context 可路由性 | 文档可切片喂给下游 agent：子系统任务包可独立抽取，无需读全文 |
| S11 演进可维护性 | 单一真相源、引用不复述；改一处不需同步 N 处 |

### 3.2 逐条拆解：可结构化部分 vs 语义残余

| 判据 | 可结构化（确定性信号 → 脚本断言） | 语义残余 | 残余归属 |
|---|---|---|---|
| S1 | 排序存在且全序（无并列）；每条带数值度量；数值有溯源标记 | 排序反映真实优先级吗；数值合理吗 | **人门**（价值） |
| S2 | 走查矩阵存在；场景覆盖四类（主流程/故障/启停/一致性）≥各一；矩阵无空格 | 「满足机制」真能满足吗；场景选对了吗 | 评审镜 + 人补场景 |
| S3 | 分解判据 ADR 存在（按什么切+否了什么）；每子系统有变化驱动标注 | 边界与变化真对齐吗；反模式识别（启发式弱信号，判定归语义） | 评审镜；**后验共变回检**（跨期机械，见下注） |
| S4 | 每条 contract 五层字段「有内容 或 显式 N/A」 | 不变量是真不变量吗；错误语义闭合吗；还剩哪些缝 | 评审镜（对抗镜找缝） |
| S5 | ADR 三件套结构；`[假设]` 计数；数值溯源三态覆盖率 100% | 推测依据成立吗 | **人门**（逐条确认假设） |
| S6 | 术语扫描（正文 vs 词汇表）；引用完整性；同量纲数值互斥比对 | 跨节隐含假设冲突 | 评审镜 |
| S7 | 十节「存在 或 N/A+理由」；横切清单逐项「已定 或 N/A」 | N/A 理由成立吗；清单外领域特有项遗漏 | 评审镜 |
| S8 | **几乎无确定性信号**（至多弱启发：否决理由含「现状/目前很少/存量没有」词面 → 只报不判） | 全部 | 评审镜专项 lens（目标态镜） |
| S9 | 风险登记存在、每条有等级+承受度字段；深度分配与风险等级联动（高风险子系统必须标 L2 深设计） | 风险评估准吗；等级定对了吗 | **人门**（承受度）+ 评审镜 |
| S10 | 每子系统切片 token 测量 ≤ 预算；切片引用闭包可机械解析 | 切片语义自足吗（agent 拿着够用吗） | 骨架期试跑验证 / 评审镜 |
| S11 | 重复段检测（双写告警）；分家落位检查（ADR 在 adr/、术语在 CONTEXT.md、SAD 只索引） | 真相源划分合理吗 | 评审镜 |

> **S3 特例注**：分解正当性在设计期近乎纯语义，但**运行期有后验机械仪器**——git 共变分析：按**逻辑变更**（非 commit——实测 commit 级口径会低估耦合约 3 倍）聚合统计模块共同被改的频率，高共变对即边界裂缝候选。属「跨期机械化」：设计期评审标注「待后验」，阶段边界回跑仪器，共变漂移 → 回流修正 SAD。
> **S8 特例注**：全集里唯一近乎纯语义的判据——这是诚实边界，不是弱点；它成为评审镜单里的专职一镜。

### 3.3 拆解的产出 = skill 的三份组件清单

分类结果直接落成 skill 的三个组件（无一浪费）：

1. **「可结构化」列聚合 → 机械层脚本断言清单**（`sad_lint` 类工具的需求规格）
2. **「语义残余」列聚合 → 评审镜单**（spec-review domains 的 SAD 版——每条残余就是一面镜的审查焦点）
3. **价值类残余（S1 排序 / S5 假设确认 / S9 承受度 + 拍板项）→ 人门清单**（HARD-GATE 议程）

### 机制 A：假设显影（防「幻觉架构文档」，服务 S5）

一次生成的 SAD 最危险的属性是**看起来权威**。AI 从薄需求也能产出一份完整、自洽、专业的 SAD——里面塞满了它自己编的组织事实和价值取舍。对策：

- AI 每处推测/编造 **MUST** 标 `[假设]`（含推测依据），聚合进假设清单
- 一份「看起来完整」但带 30 个未确认假设的 SAD = 30 个洞的 draft
- **文档状态机**（§0.1）：`draft → skeleton-ready → validated →（逐条）frozen`。skeleton-ready 门槛 = 事实类三项齐（定位/外部系统/硬约束）+ 假设逐条「显式接受 或 标待校准」；事实类关键项缺失 → **fail-closed 锁 draft**

### 机制 B：数值溯源（服务 S1/S5）

每个数（延迟预算、容量、超时……）标来源。目标态三态：**人拍** / **域惯例推荐**（AI 给出处）/ **纯占位**；**v1 简化为两态**（人拍 / 推荐待校准——纯占位并入后者的告警清单，见 §0.3）。fitness function 只允许长在「人拍」与「推荐已校准」上。

## 4. 人机分工（核心问题）

**总原则：人 owns 事实与价值，AI owns 枚举、推演与纪律。**

- 人必须给的两类：①**组织/环境事实**（问不出来、猜必错）：约束、外部系统、运行环境、存量、预算；②**价值判断**（只有 owner 有权）：质量排序、风险偏好、方案拍板。
- AI 的三类强项：①**枚举完备性**（候选方案、被否备选、横切清单——不遗漏）；②**推演**（判据流水线跑分解、场景走查、后果分析）；③**纪律**（格式、一致性、留痕——全机械化）。

### 分工矩阵（按十节）

| SAD 节 | 人必须提供 | AI 推荐 → 人拍板 | AI 全自动（机械） |
|---|---|---|---|
| 1 目标+质量属性 | 产品定位、**排序**、风险偏好、数值校准 | 领域典型质量属性候选、冲突对提示、可测度场景措辞、推荐数值（带溯源） | 每条有度量/有排序检查 |
| 2 约束 | **全部事实**（栈/预算/合规/存量） | 从需求文本识别隐含约束并**追问** | 约束 vs 决策分区检查 |
| 3 外边界 | 外部系统清单、协议文档指针 | 领域典型外部依赖问卷、外部 contract 风险排序 | context 图/接口表生成 |
| 4 策略+ADR | **拍板**、组织性理由 | 备选枚举、后果推演、推荐+理由 | ADR 三件套完整性、编号索引 |
| 5 分解+contract | 领域知识补充、**方案选择** | **判据流水线产 2–3 候选分解**+tradeoff、contract 五层草案 | 判据留痕、contract 字段、context 预算粗测 |
| 6 运行场景 | 场景重要性确认、遗漏补充 | 场景提名（主流程/故障/启停/一致性）、**执行走查**、报洞 | 场景×子系统×contract 矩阵生成+空格检测 |
| 7 部署 | 运行环境事实（平台/分发） | 部署形态推荐 | 与约束的一致性检查 |
| 8 横切概念 | 领域特殊项、取舍确认 | **领域清单模板推荐**+逐项草案 | 每项「已定 或 N/A 留痕」检查 |
| 9 风险登记 | 风险承受度、业务后果 | 技术风险枚举、风险→设计深度分配建议 | 格式+深度分配联动检查 |
| 10 词汇表 | 领域术语确认 | 从需求+讨论提取术语草案 | 术语一致性扫描 |

> **价值类信息的采集形式（2026-07-12 校准，服务 §0.2）**：矩阵中「人必须提供」的排序/数值/承受度**不以抽象表格形式问人**——AI 翻译成场景化二选一（排序反推）与可否决推荐值（数值）。人 day 0 答不出抽象问题 ≠ 人无法提供，是问法错了。

### 关键洞察：中间态「人给原料 → AI 推演」

分工不是二分而是三段：很多节 AI 无法从零推荐，但**人给出原始事实后 AI 的推演是高价值的**。例：人说「broker 是第三方托管、固件是存量不可改」→ AI 推导出外部 contract 风险排序、把固件协议列为最高优先钉死项。skill 设计上这就是「采集 → 推荐」两阶段的存在理由。

  │    判据流水线跑出候选分解（规则见 §5.1；数量由分歧驱动，见 §5.2）

### 5.1 内嵌规格：子系统拆分规则集（R1–R11 + 反模式黑名单）

> 本 skill 最核心的规格。来源标注：Parnas 1972 信息隐藏 / Evans DDD / Newman / Skelton-Pais / Löwy / Nygard；四判据推导记录在同目录 00 文档 Q1 结论，此处为完整可执行规则。

#### Phase A：生成候选（从需求到候选清单）

- **R1 原料提取**：从需求 + 问卷答案提取四类原料：**用例清单**（系统要响应的事件/要做的事，动词短语）、**领域名词**、**外部接口**（十节骨架第 3 节）、**数据类别**（持久数据 + 运行态）。这是轻量版 event-storming——不开工作坊，AI 枚举 + 人补漏。
- **R2 语义聚类成候选**：按领域语言聚类——同一词汇圈的用例+数据 = 一个候选子系统；每个候选先给**一句话职责**。候选数量此阶段不设限，进 Phase B 前粗合并到 ≤9。
- **R3 物理边界先行**：部署/进程/二进制边界（来自骨架第 7 节与约束）是**硬切分**——跨进程/跨网络处必有子系统边界（反之不然：同进程内仍可多子系统）。**技术分层不是子系统**（见 AP3）；域概念被物理边界劈开时（如同一概念在前端+后端各有一半），两侧以 contract 缝合、**命名强制对齐**（防语言漂移）。

#### Phase B：四判据精修（对候选清单迭代执行）

- **R4 变化率检验**：列**预期变化清单**（类别 checklist：需求功能方向 / 外部协议与依赖版本 / 技术选型替换 / 规模与性能 / UI 形态 / 合规——载体：`references/checklists/`）。逐条标注击中几个候选：**击中 ≥2 → 边界疑点**，按序三选一（**根治优先，顺序即优先级**）：①移动职责（根治）→ ②判定该变化属横切、归骨架第 8 节（重新定性）→ ③显式接受并记 ADR（显式债务）——不许跳到③图省事。
- **R5 单写者检验**：每类数据（含运行态）标唯一 writer；出现双写 → 边界错，重新分派所有权。
- **R6 context 预算检验（硬约束）**：估算每个候选「完整设计 + 自身 contract + 邻居 contract 摘要」的体量；**超预算 → 必须再切或收窄职责**；远低于预算且与某邻居高内聚 → 考虑合并（防碎片化）。
- **R7 依赖形状检验**：画候选间依赖图。**环 → 违规必须解**（提取公共下层 / 翻转依赖）；**hub**（一个候选与全部相连）→ 疑点：要么它是真核心域（记 ADR 显式接受），要么职责过宽（按语义簇拆）。

#### Phase C：仲裁与终止

- **R8 冲突仲裁序**（判据打架时）：
  1. **context 预算 + 依赖无环是硬约束**——必须满足，无豁免；
  2. **语言边界默认保持**——两个语义域高共变时，优先解释为「contract 缺了抽象」（修 contract），**而非合并两个语义域**（合并污染语言，代价更高、不可逆）。**后验兜底**：修完 contract 后若后验仪器回检**仍**高共变 → 承认语言边界误判（本是一个域被误拆为二），此时合并是对的——语言优先是**第一响应，非永久豁免**（2026-07-12 确认）；
  3. 同一语义域内出现**独立变化簇** → 记为该子系统的 L2 内部模块候选，**不升子系统**（那是步骤二 scope）；
  4. **改动成本不进 SAD 期仲裁**——SAD 期是边界决策的**免费窗口**（纸上重切零成本，代码里重切昂贵），此时按 1–3 把边界做对；成本仲裁仅在存量迁移场景进场且**排最后**（先判根治、再锚目标态、最后才计成本）。存量项目的现状代码结构只是证据、**不是判据输入**。
- **R9 粒度带与终止**：目标 **3–7 个**子系统（超出 → 合并低风险相邻域；不足 3 且单体超 context 预算 → 再切）。一个子系统 = 一个 agent 一个 context 吃得下的设计单元。到粒度带且 R4–R7 通过 → **停止**，不做子系统内部细分。
  **统一原理：边界贵、内部便宜**——每条子系统边界 = contract + 集成 + 评审 + 文档的固定协调成本，内部结构改动自由。口号：**子系统边界往上合、内部模块往下拆**（与 change 拆分标准「change 边界往上合、内部粒度往下拆」同源，两轴共用同一条经济学；「别为小职责开新子系统」与「相关项 fold 进当前 change」也是同一防碎片化逻辑）。
- **R10 拆分做全景、实施做增量**：SAD 一次把**空间切全**——含后期阶段才实现的子系统（边界 + contract 占位，成熟度标 `planned`），**不许**因「阶段 N 才做」而不划边界；实现缺位的依赖 = contract-only 占位 + todo 登记（与骨架先行同构：contract 先行，实现后补）。空间一次切全，时间分期填充。
- **R11 留痕与输出 schema**：拆分判据、被否切法、显式接受的疑点（hub/横跨变化）→ **第一条 ADR**。每个子系统按固定 schema 落盘（= 原始三要素的字段化）：

  | 字段 | 内容 |
  |---|---|
  | 目标 | 一句话职责（R2 产出，精修后） |
  | 范围 | owns 的用例清单 + owns 的数据（R5 写权矩阵行） |
  | 边界 | 明确**不做**什么（与邻居的分界句） |
  | 对外 contract | 清单，骨架前只填主干三层（语法/所有权/错误语义归属），带成熟度标签 |
  | 注意事项 | 指向横切概念（第 8 节条目引用）+ 风险登记（第 9 节条目引用），**不自由发挥散文** |

> **两轴正交提醒**：本规则集切**空间**（子系统边界）；change/task 切**时间**（交付单元）。feature/change 垂直穿多个子系统是**正常且推荐**的（tracer bullet 即此形态）——「一个 change 一个完整结果」**不等于**「一个 feature 独占一个子系统」。子系统的内聚单位是**职责与变化原因**，不是交付单元。

#### 反模式黑名单（AI 推荐步必须先自检再交人——AI 自由分解的默认输出 = AP1/2/3 高发）

| # | 反模式 | 识别特征 | 修正动作 |
|---|---|---|---|
| AP1 | entity-service（按名词切） | 子系统名 = 数据实体名（User/Order/Device）；任一用例都要穿 ≥3 个子系统 | 按用例/能力重新聚类 |
| AP2 | 流程式分解（按步骤切） | 子系统名 = 处理阶段（接收/解析/处理/输出）；数据一路穿过全链；任何需求变化击中全链 | 按变化原因重新聚类 |
| AP3 | 技术分层当子系统 | 切出来是「UI 层/业务层/存储层」 | 层是子系统**内部**结构或横切约定；子系统按领域垂直切（物理边界除外，见 R3） |
| AP4 | God-hub | 一个子系统与所有人高耦合；职责描述要用「和」连 ≥3 个名词 | 按语义簇拆；或确属核心域 → ADR 显式接受留痕 |

### 5.2 候选分解的数量规则（D2 结论，2026-07-12 拍定）

候选数**不定配额，由仲裁分歧数驱动**：

- R8 仲裁出现**真实分歧**（如语言边界 vs 变化率打架、hub 拆不拆）→ 每个分歧点生成一对真实候选（整体通常收敛为 2–3 个方案）——分歧点即分叉点，天然不是稻草人；
- 四判据**无分歧** → 允许单方案直出，**MUST 显式声明一行**「判据无分歧，单方案直出」（跳过类判定显著呈现）；黑名单自检中被 AP 规则毙掉的形态充当 ADR「被否切法」栏，三件套仍填得满；
- **禁止凑数**：候选必须源于真实判据分歧，不许构造明显劣化的对照方案——稻草人让拍板变表演（假绿近亲），比单方案更糟。

### 5.3 问卷规格（D3 结论，2026-07-12 拍定）

- **问卷 = 事实类三问**（必答，任一缺 → 锁 draft）：①一句话定位（是什么/给谁用/解决什么）②外部系统清单 + 文档指针 ③硬约束（栈/平台/**部署形态**/必须兼容的存量/合规红线）。部署形态并入第③问为 R3 物理边界供料，**不开第七类**。任何项目 owner 五分钟可答完。
- **价值类不是问卷**：质量取舍/风险承受度/Non-goals **后置到③拍板**，挂具体产物以选择题形态问（「A/B 切法选哪个」优于「描述你的质量取舍」一个量级）——**事实前置、价值后置**：day 0 不仅不逼人答抽象问题，连问都不问，等有具体产物再问。
- 载体 `references/intake-questionnaire.md` 只含三问 + 各问的追问提示。

### 5.4 走查与评审分档（D4 结论，2026-07-12 拍定）

**独立性三层级**（各治不同的病）：①fresh context（治生成 session 自证偏差——默认必有）②跨模型 outside voice（治**同族先验相关性**：同族模型用同一 prior 填缝，「合理但错」的假设同族审稿人同样觉得合理——升档时尽量有）③人门（治价值判断——必有）。

- **默认档（每次必跑）**：lint + **冷走查**（1 个 fresh Claude 子代理执行场景×子系统×contract 矩阵——**禁止生成 session 自查**）+ 人门。走查是半机械活（prior 依赖低），fresh context 已够，默认不引外部依赖。
- **升档多镜**，命中信号表任一（判定显式陈述一行 + 留痕）：
  1. **骨架验证慢/贵**：无法一个 change 打通（硬件依赖/外部审批链/分布式部署）——核心判据：**多镜价值 ∝ 骨架真验证的延迟与成本**，骨架快时纸面重审是浪费，骨架慢时纸面审是唯一防线；
  2. **不可逆决策面大**：落盘 schema/对外发布 API/多进程拓扑（骨架也难救的错）；
  3. **不可控外部 contract 多**；
  4. **操作者显式要求**。
- **outside voice（codex）政策**：升档多镜且 codex 可用 → **至少一面镜用跨模型**，放在 prior 依赖最强的镜位（S4 对抗找缝镜 / S8 目标态镜）；宿主探测 + 降级路径：未装/调用失败 → 退回 Claude 镜 + **显式提示不静默**。操作者显式要求时任何档可指定。
- **排除项**：假设计数高 **≠** 升档信号——假设多 = 缺事实，回①补采集；多镜审不出事实缺失，只会花预算确认「这确实是假设」。

### 6.2 组件 ③ 的角色澄清：规格，不直接执行（防双写发散）

质量判据是**规格真相源**，它的执行分身到三处投影：

```

   ├─ 投影 2: review-lenses.md   ← 「语义残余」列   (镜单条目引用 S 编号)
   └─ 投影 3: 人门清单(SKILL.md) ← 价值类残余      (HARD-GATE 议程引用 S 编号)
```

投影带 S 编号引用 → 「投影与真相源一致」本身可机械核对（防三处各自漂移）。

### 6.3 两处「脚本 + 大模型」切分（按确定性信号判据）

| 活 | 归属 | 理由 |

| 缺口识别（需求里缺什么）、候选分解推演、场景走查、措辞起草 | **模型** | 无确定性信号，纯判断 |
| 问卷事实、排序、拍板 | **人** | 事实与价值 |

**组件④review 期**（次序固定：先脚本后模型——机械不绿不值得花模型预算审语义）：

| 层 | 工具 | 输入 |
|---|---|---|
| 1 机械层 | `sad_lint.py`（fail-closed 退出码 + reason code） | 拆解表「可结构化」列 |
| 2 语义层 | 多镜评审（每镜一条语义残余为焦点：走查镜/对抗镜找缝/目标态镜/一致性镜…） | `review-lenses.md` |
| 3 人门 | HARD-GATE 议程 | 人门清单 |

review 工具**不是生成的附属品**：生成流程 ④ 走查步内嵌调用它，人工后续修订 SAD 后也用它复检——生成期与维护期共用同一套判定。

## 7. 产出文档的维护生命周期（2026-07-12 拍定）

### 7.1 三层分离（不按读者切，按层切）

人与 AI 同读 live 层，差异只在下钻深度：

| 层 | 内容 | 特性 | 读者 |
|---|---|---|---|
| **live 层** | SAD 本体（十节）+ contract | **永远只有当前态**，零历史残留；引用决策不复述 | 人与 AI 同读一份 |
| **decision 层** | 每决策一文件（ADR，含详述+图） | **不可变、只追加**：从不改旧文件；新决策 supersede 旧决策，旧文件头标 `Status: superseded-by NNNN`（Nygard 惯例；生态 home = `openspec/adr/`） | 按需下钻 |
| **history 层** | git + changelog（可脚本从 git 派生） | 完整修订史 | 人复盘 |

> 被否候选（体内删除线保留历史、AI/人双轨真相）见附录 A1/A2。

### 7.2 「AI 不误读」机械化为阅读安全规则 → lint 规则（并入 sad_lint）

| 阅读安全规则 | 机械化形态 |
|---|---|
| 不消费非当前态内容 | frontmatter `status:` 机器可读；live 层引用 superseded 决策 → lint 报错 |
| 分辨草案/定稿 | contract 成熟度（draft/validated/frozen）入 frontmatter，非散文 |
| frozen 不许静默改 | frozen 内容有 diff 但无新 ADR 关联 → lint 报错（≈ ship_gate 设计门失鲜同款机制） |
| 人看「改了什么」 | git diff/blame + changelog 派生脚本，不进文档体 |

## 8. 生态位与端到端序列（D5 结论，2026-07-12 拍定）

- **skill 命名**：`sdflow-architecture`（生态全词命名惯例，无缩写先例；文档内部术语仍用 SAD）。
- **落位**：`openspec/architecture/`，**项目级单例**——SAD 是 per-system 的，roadmap 包是 per-effort 的（一个项目可有多个 roadmap effort，但只有一份系统 live 层）；与 `openspec/adr/`（decision 层）、`openspec/CONTEXT.md`（词汇表）成兄弟，§7 三层分离在目录结构上直接成立。未来 L2 子系统文档落 `architecture/subsystems/`。
- **与 roadmap 三件套职责切分**：roadmap 的 design.md = **WHY-product**（需求与产品决策）；SAD = **HOW-structure**（子系统/contract/横切）；roadmap.md = **WHEN**（时间编排）——互相引用不复述（sdflow-roadmap 的 design 模板后续瘦身让位，属小 change）。
- **先例佐证**：mqtt-console 的 roadmap 包自发长出 `technical-architecture.md`（B1–B7 接缝）——design.md 装不下架构细节会自然分裂，需求真实；本方案将其规范化并纠正落位（effort 包 → 系统级单例）。

**端到端默认序**（不强制，操作者拍定；回流全程双向）：

```
需求讨论
  ▼
① SAD（sdflow-architecture）→ skeleton-ready + 交棒骨架 proposal
  ▼
② 骨架 change —— 不等 roadmap 直接实施（骨架先行）；roadmap 排期时收编为阶段 0
     L1 contract 逐条 draft → validated
  ▼
③ roadmap（sdflow-roadmap）—— 排期只需 SAD 全景 + 风险分布；近细远雾
  ▼
④ L2 子系统设计 —— just-in-time：子系统进入实施窗口才细化；深度 ∝ 风险
     （= 近细远雾在空间轴的对应物；不设「全部 L2 完成」的全局 barrier）
  ▼
⑤ changes per 阶段（既有 sdflow 门禁链）
  ▲
  └── 回流：下层发现上层错 → 改上层 + 记 ADR，禁止只在下层绕过
```

**序列三条纪律**（防重回瀑布）：

1. **骨架插在 SAD 与一切之间**——L2 要在**被验证的** contract 上做才有意义，纸上 contract 上做 L2 是沙上盖楼；
2. **L2 不全量先行**——just-in-time + 风险驱动，「所有子系统 L2 做完再往下」= 瀑布回潮；
3. **roadmap 不等 L2**——只有近期阶段的子任务细化需要对应子系统的 L2（「近细远雾」的成因即此）。

**每层出口门**：① lint + 走查 + 人门（skeleton-ready）｜② contract validated 回写｜③ roadmap 既有 review 分档｜④ 按风险分档（低风险免门）｜⑤ 既有门禁链。
