## 1. 轴定位（过程轴管什么、不管什么）

过程轴 = **「怎么开发、测试、运维、上手」的操作/程序性知识**。它与其余五轴正交，明确**不含**：

```
结构（SAD/L2）· 排期（roadmap）· 决策 why（ADR）· 术语（CONTEXT）· 契约（specs）
                                    └─ 这五样在 04 已分清，本文不重述 ─┘
过程轴 = 操作(搭建/运行/部署) + 方法(测试) + 协作(贡献) + 上手(入口索引)
```

判据仍是 SAD 边界总则第②问的镜像：**「操作步骤」不进 SAD/L2，归过程轴文档**（`04` / `quality-criteria.md` 边界总则）。本文管的是：这些「操作步骤」自己该怎么组织成文档。

## 2. 文档集

### 2.1 第一刀：两类文档

过程轴内部先分两类——这是组织文档集的**第一刀**，也决定后面交付机制（§5）：

- **真相源类**：每份 own 一个操作子域，是该子域内容的**唯一出处**；
- **入口·索引类**：自己 **own 任何内容**，只做「概要 + 指向真相源」；跨轴聚合指针。

## 3. 文档间边界（引用不复述）

每格内容只有一个家，跨格一律引用、禁复述（承 `04` §5 真相源分工 + S11 单一真相源）：

```
SAD §7 部署(决策) ──被引──▶ environments §3(操作)      ← 决策 vs 操作
testing-strategy(方法) ─被引─▶ environments §2(测试环境) ← 方法 vs 环境
environments(真相源) ──被引──▶ README / CLAUDE.md(入口)  ← 真相 vs 入口
CONTRIBUTING(人流程) ──引──▶ openspec workflow(规则真相源) ← 项目流程 vs 工作流规则
```

**入口类的边界纪律更严**：README/CLAUDE **MUST NOT** 复述任何真相源细节，只放「最小起步命令 + 指针」——否则入口一膨胀就成了第二个真相源，指针与本体双写漂移（范式见 `environments-template-draft.md` 附 A/B）。

### 3.0 例外：同一事实的两面投影，不算双写

「每格内容只有一个家」有**唯一一条合法例外**——同一事实被**两个轴各投影一个面**时，两边各 own 一个面，都不算复述：

```
结构轴（L2 / runtime-model）：「行为是什么」   ← 系统侧
过程轴（testing-strategy）  ：「为什么这条断言长这样」 ← 测试侧
```

**判据**：两个面回答的是**不同的问题**，删掉任一边另一边都不完整 ⇒ 合法两面。若一边只是把另一边**换个说法重说一遍**（同一问题、同一答案）⇒ 双写，删。

**MUST 显式互指**——否则一侧改了另一侧无从察觉（这是两面投影唯一的风险，也是它与双写的操作区别：双写靠删治，两面靠互指治）。

> 接地实证（06 §5）：mqtt-console `testing-strategy.md §8.5`「断言背后的行为契约」14 条（Stop ≠ Shutdown 的丢失契约、generation guard 的双向性、rowSeq 1-based…）读起来像系统语义（该归 L2），但它们**只在测试注释里成文**，且每条都是「为什么这条断言长这样」的答案。判进 testing-strategy 正确，并埋了互指「系统侧的语义展开见 runtime-model.md」——**这是全流程最容易误判的一处边界。**

### 3.1 testing-strategy ↔ environments §2 的精确切线（2026-07-12 拍板：拆）

上图第 2 条链（方法 vs 环境）是过程轴内最易糊的一处（fixture/测试数据两边都想放）。**拍板：拆**——testing-strategy 独立第 3 份真相源，**不并入 env §2**。切线 = **方法/决策 vs 环境/操作**，与第 1 条链（SAD §7 决策 ↔ env §3 操作）**同一把刀**（体系一致，非给 testing 开特例）：

| 内容 | testing-strategy（方法/决策） | environments §2（环境/操作） |
|---|:---:|:---:|
| 分层：unit/int/e2e 各测什么、为什么这么分 | ✓ | |
| contract = 集成测试点（哪些边界必被穿过） | ✓ | |
| 覆盖目标 / 门禁护栏（policy 阈值） | ✓ | |
| mock 边界选在哪（策略） | ✓ | |
| fixture **策略**（golden-file / factory · 数据代表什么） | ✓ | |
| **分层的实例化：逐文件门禁清单**（哪个测试文件跑哪条泳道） | ✓ | |
| **已知盲区 / 测试债**（哪条不变量架构上守不住） | ✓ | |
| **测试编写 idiom**（barrier / retry-until-settled：怎么写出确定性断言） | ✓ | |
| **flake 的定性与放行决策**（是什么 · 为何不修 · 靠什么护栏放行） | ✓ | |
| 各层**执行命令**（`make test` / `go test ./...`） | | ✓ |
| **flake 护栏的实现**（Makefile 的 `\|\| retry once`） | | ✓ |
| **测试选择路由**（改了什么 → 该跑哪条） | | ✓ |
| 测试**依赖**（起 broker / playwright 浏览器） | | ✓ |
| CI runner 平台 / headless 处理 / 缓存 | | ✓ |
| fixture **文件在哪 / 怎么生成**（`make test-data`） | | ✓ |
| 覆盖率**当前数字** | | ✓（或不放，工具产出） |

> **后 7 行 = 接地新增**（06 §3）。其中「flake 定性/决策」与「flake 护栏实现」这一对是**同一件事的决策面与操作面**，切线表的刀在此切得最漂亮：B13「不修、靠回归网放行」+ 四条护栏归 testing-strategy §7.3，而「重跑消歧」落地成 Makefile 的 `|| retry once` 归 environments §2.2。
>
> **「逐文件门禁清单」的判据**（原表十行没有这一行，是接地时真撞上的硬骨头）：它既不是「为什么这么分层」也不是「怎么跑」，而是**分层的执行态**——问「随工具链变还是随测试哲学变？」答后者 ⇒ 方法侧；问「reviewer 读还是 contributor 读？」答前者 ⇒ 方法侧。

> **拍板依据（决策三镜 + 主次）**：**主 = 系统镜**——方法（稳定哲学）与环境（易变工具链）是**两条独立变化轴**，混一则易变部分每次改动搅动稳定部分（违 S11 演进可维护），且「决策 vs 操作」本就是过程轴统一组织原则。**佐证**：用户镜（reviewer 问「测得够不够好」vs contributor 问「怎么跑」，两类读者→两个文档）+ 开发循环镜（合并 diff 噪音）是同根（两轴混一）的两个侧面，非独立理由。**次要保留**：小项目 testing-strategy 薄 → 用 §2.3「填或显式 N/A」化解，**不构成合并理由**（目标态导向：别拿现状"薄"缩水目标）。切线**无确定性硬信号**（「命令/路径→env」是弱启发），属语义边界，靠起草纪律守 + git 审计兜。
> **现实一致**：`environments-template-draft.md` §2 边界注（「测什么/怎么分层归 testing-strategy——本节只放环境依赖+执行命令」）已隐含此切线，本节把它**显式化 + 补精确归属表**，无需回改模板。

## 4. 槽的三个来源（2026-07-13 接地订正：二分 → 三分）

> **原文写的是二分**（SAD 投影 / 项目自填）并断言「约一半槽能从 SAD 投影」。mqtt-console 实测**两条都错**：比例远低于一半，且**二分问错了源**。以下为订正版，证据见 `06-process-axis-grounding-receipt.md` §1。

### 4.1 实测投影率：12%（严）/ 41%（宽），**不到一半**

口径：environments 14 槽去 2 个纯指针槽 = 12 实质槽；testing-strategy 5 槽（原表）。合计 **17 槽**。

| 类别 | 数量 | 槽 |
|---|---|---|
| **真投影**（SAD 直接给得出内容） | **2** | `contract = 集成测试点`（← SAD §5 逐条映射，投影度最高的一节）· `目标平台`（← SAD §7） |
| **半投影**（SAD 给骨架，给不出肉） | **5** | 工具链←§2 · 本地依赖←§3 · 配置项←§8 · 发布流程←§7 · 分层←§1 可测试性 |
| **纯人写**（无任何机械源） | **10** | 构建运行 · **常见坑** · 测试依赖 · 各层执行命令 · CI · fixture · 回滚 · **护栏** · **mock 边界** · 测试数据 |

**半投影的肉在哪**：SAD 只供「用哪些工具 / 什么策略」这一层。`Go ≥ 1.26.4`、四根目录的三平台默认路径、`location.yaml` 键名、构建产物名——**SAD 一个字都给不出**，全部来自 `go.mod` / `internal/store/location.go` / `wails.json`。

**且能投影的那部分恰恰最不值钱**（一句话 + 指针）；两份文档真正的价值——**常见坑 · 四条护栏 · 逐文件门禁表 · 已知盲区**——**SAD 投影率为零**。

### 4.2 ⚠ 二分问错了源：真正的机械投影源是**构建配置**，不是 SAD

接地时模型能把命令写准（Makefile 四个 target 行号全中、`wails.json` 行号全中、**零虚构 target**），靠的不是 SAD，是：

```
Makefile · package.json · wails.json · go.mod · 测试文件注释
        └─ 全部机械可读，有确定性信号 ─┘
```

原 §4 只问了「SAD 能投影多少」，**没问「别的机械源能投影多少」**。按机械/语义切分线判据（有无确定性信号，见 `CLAUDE.md` §设计基准 1）重划为**三分**：

| 槽来源 | 源 | 例 | 机械化档位 |
|---|---|---|---|
| **SAD 投影** | `sad.md` | contract=集成测试点 · 目标平台 · 配置**策略** | 半机械（给骨架） |
| **构建配置投影** | Makefile / package.json / wails.json / go.mod | **各层执行命令**（含出处列）· 工具链**版本** · 配置项**默认值** · CI 存在性 | **强机械**（可核验，甚至可生成） |
| **纯人写** | 踩坑史 / 决策史 / 测试哲学 | 常见坑 · 护栏 · mock 边界 · 盲区 ·**归属判定** | 无信号，人判 |

**关键观察（订正版）**：
1. **从 SAD 生成 env 的天花板只有 ~12%**，且产出的是最不值钱的部分 ⇒ **「从 SAD 生成」这条腿几乎不存在**（比原判更弱）。
2. **但「从构建配置生成/核验命令表」是强机械的** ⇒ 值得机制化的不是「从 SAD 生成」，而是**「对构建配置核验」**（这直接定义了 §5 里 B 的 scope）。

## 5. 交付形态决策

### 5.1 三个候选

| | C 模板 + prompt | D 独立 skill（工作名 `sdflow-ops`） | B 并入 `sdflow-init` |
|---|---|---|---|
| 形态 | 结构化模板 + 一段起草 prompt，项目自跑 | 新 skill：init 从 SAD 投影生成 + 维护 + 边界守卫 | init 铺项目骨架时一并铺过程轴模板 |
| 成本 | 零（已有 `environments-template-draft`） | 一个新 skill 的建设 + 维护 | init 增量（已有铺设机制） |
| 生成价值 | —（人跑 prompt） | **仅一半**（§4：SAD 只投影一半槽） | 同 D，一次性 |
| 维护价值 | 无机制（靠人自觉） | **有**（入口指针漂移检测 + 边界守卫） | **有**（随 init update 扫描/刷新） |

### 5.2 拍板：B + C，D 不立（2026-07-13 接地确认）

把 §2.1 + §4 合起来看：

1. **「从 SAD 生成」这条腿几乎不存在**——§4.1 实测天花板 ~12%，且产出的是最不值钱的部分（一句话 + 指针）。**⇒ D 的生成腿被证伪，比原判（"只值一半"）更弱。**
2. **维护价值真实**——§2.1：入口类（README/CLAUDE）的指针最易腐烂；真相源类的**边界越界**（架构决策漏进 env、测试方法漏进 env §2）是起草高发错。
3. **且维护有强机械信号**——§4.2：命令表可对**构建配置**核验。这是原文没看到的一条：值得机制化的不是「从 SAD 生成」，而是「对 Makefile/package.json 核验」。
4. **维护是「扫描已存在的文档」，天然属 init update 域**——`sdflow-init update` 已有「扫消费仓 + 刷新/告警」机制（tools/ 刷新、陈旧遮蔽告警）。指针漂移检测 + 过程轴边界守卫**同构于它现有职责**。

**拍板**：**B（并入 sdflow-init 的维护扫描）+ C（模板 + 归位型 prompt 起草）**。**独立 ops skill（D）不立**——生成腿已证伪、维护腿该归 init，**撑不起一个独立 skill**（承拆分标准：别为凑齐四轴硬造 skill）。

### 5.2.1 B 的精确 scope（接地实测出的五条机械项）

`sdflow-init update` 的过程轴扫描**只守这五条**（全部有确定性信号，见 06 §4.1）：

| # | 检查 | 信号强度 |
|---|---|---|
| ① | **命令出处一致性**——env 里每条命令能在 Makefile / package.json / wails.json 找到 | 强（可核验，甚至可生成命令表） |
| ② | **指针不悬空**——markdown 链接 + 章节锚可达 | 强 |
| ③ | **删源残留引用**——grep 已删文件的旧路径（含**代码注释里**的引用） | 强 |
| ④ | **N/A 显式性**——槽在但内容空 → 报错（区别于显式 `N/A — 理由`） | 强 |
| ⑤ | **入口复述检测**——README/CLAUDE 出现真相源才该有的细节（完整命令表 / 配置项表） | 弱（启发式告警） |

**守不了的（无信号，人判）**：归属判定（这段是方法还是操作，§3.1 自认语义边界）· 坑/护栏/盲区的内容本身 · 什么该 N/A（「无 CI」是事实，但「这是现状还是该有而没建」是判断）。

> ⚠ **机械层的诚实边界**（接地自证，06 §4.3）：mqtt-console 那次归位自称「markdown 链接零悬空」**并且确实通过**，却漏掉了 `docs/README.md` 里一句「两份真相源在**仓库根**」的事实错误（文件实际在 `openspec/architecture/`）。**链接可达性校验抓不到散文里的事实错误**——这不是 ①②③④ 的弱点，是它们合法的残余，交 ⑤ 的启发式 + 人读兜。
