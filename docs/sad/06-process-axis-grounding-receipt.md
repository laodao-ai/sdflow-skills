## 1. §4「SAD 只投影一半槽」——高估了，实测 12%～41%

口径：environments 模板 14 槽（4+5+5）去掉 2 个纯指针槽 = 12 个实质内容槽；testing-strategy 按 05 §2.2 给的 5 槽。合计 **17 槽**。

| 类别 | 数量 | 槽 |
|---|---|---|
| **真投影**（SAD 直接给得出内容） | **2** | `contract = 集成测试点`（← SAD §5.1–5.7 逐条映射，全篇投影度最高）· `目标平台`（← SAD §7：桌面单 binary、无服务端） |
| **半投影**（SAD 给骨架，给不出肉） | **5** | 工具链（← §2 约束）· 本地依赖（← §3 外边界）· 配置项（← §8 横切）· 发布流程（← §7）· 分层（← §1 可测试性） |
| **纯自填**（SAD 无源） | **10** | 构建运行 · **常见坑** · 测试依赖 · **各层执行命令** · CI · fixture · 回滚 · **B13 四护栏** · **mock 边界** · 测试数据 |

- 严口径：**2/17 ≈ 12%**
- 宽口径（半投影全算有源）：**7/17 ≈ 41%** —— **仍不到一半**

**半投影的肉在哪**：SAD 只供「用哪些工具 / 什么策略」这一层。`Go ≥ 1.26.4`、四根目录的三平台默认路径、`location.yaml` 键名、`wails build` 的输出名——SAD **一个字都给不出**，全部来自 `go.mod` / `internal/store/location.go` / `wails.json`。

### 1.1 对 05 §5 的影响：结论不变，理由变硬

原文：「SAD 只投影一半 ⇒ 生成天花板只有一半 ⇒ 削弱 D」。
实测：天花板 ≈ 1/8～2/5，**且能投影的那部分恰恰最不值钱**（一句话 + 指针）；两份文档真正的价值——6 条坑、B13 四护栏、逐文件门禁表、T22 盲区——**SAD 投影率为零**。

⇒ **D（独立 ops skill）的「生成」腿比原判更弱。B+C 成立。**

### 1.2 ⚠ 但 §4 问错了源（本次接地最重要的发现）

模型这次能把命令写准（`Makefile:11-14` / `:19-22` / `:33-37` / `:46-47`、`wails.json:4/6-8/10` 行号全中，零虚构 target），靠的**不是 SAD**，是：

```
Makefile · wails.json · frontend/package.json · go.mod · 测试文件注释
   └─ 全部机械可读，有确定性信号 ─┘
```

产物 §2.2 那张命令表**每行都带「出处」列**——这张表本身就是「可从构建配置机械抽取」的自证。

**05 §4 只问了「SAD 能投影多少」，没问「别的机械源能投影多少」。** 按机械/语义切分线判据（有无确定性信号）重划：

| | 有确定性信号 → 可机械 | 无信号 → 只能人判 |
|---|---|---|
| **源** | Makefile / package.json / wails.json / go.mod | 踩坑史 / 决策史 / 测试哲学 |
| **槽** | 各层执行命令 · 工具链版本 · 配置项默认值 · CI 存在性 | 常见坑 · 护栏 · mock 边界 · 盲区 · **归属判定** |

⇒ **回写 05 §4：把「SAD 投影 vs 项目自填」二分改为三分——SAD 投影 / 构建配置投影 / 纯人写。**

## 4. 机械 vs 人判——B（sdflow-init 维护扫描）的精确 scope

### 4.1 机械可做（有确定性信号）→ 这就是 B 该守的

| # | 检查 | 信号 |
|---|---|---|
| ① | **命令出处一致性**——env 里每条命令能否在 Makefile / package.json / wails.json 找到 | 强（可核验，甚至可**生成**命令表） |
| ② | **指针不悬空**——markdown 链接 + 章节锚可达 | 强 |
| ③ | **删源残留引用**——grep 已删文件的旧路径（本次归位重指了 20 处，含 Makefile 与 7 个测试文件的注释） | 强 |
| ④ | **N/A 显式性**——槽标题在但内容空 → 报错（区别于显式 `N/A — 理由`） | 强 |
| ⑤ | **入口复述检测**——README/CLAUDE 里出现真相源才该有的细节（完整命令表 / 配置项表） | 弱（启发式告警） |

### 4.2 人判不可（无信号）

- **归属判定**（这段是方法还是操作）——05 §3.1 已自认属语义边界，本次接地确认：**这是全流程唯一无确定性信号的部分**，故 prompt 把人门放在 STEP 1（搬运表先给人确认）而非末尾审文档，是对的。
- **坑 / 护栏 / 盲区的内容本身**。
- **什么该 N/A**——「无 CI」是事实，但「这是现状还是该有而没建」是判断。产物诚实地写了「无 CI」并连带记了后果，这个诚实是人给的。

### 4.3 ⚠ 机械校验的边界（本次实证）

产物 commit 自称「markdown 链接零悬空 · go vet OK」并**确实通过**，但 `docs/README.md:87` 仍写着「两份真相源在**仓库根**」——而文件实际在 `openspec/architecture/`（同段标题自己写对了）。

**链接可达性校验抓不到散文里的事实错误。** 这是机械层的诚实边界，不是弱点——它精确落在 05 §3.1 承认的语义残余里。（已修，2026-07-13）

## 5. 最易判错的边界：同一事实的两面投影

testing-strategy §8.5「断言背后的行为契约」14 条（Stop ≠ Shutdown 的丢失契约、generation guard 的双向性、rowSeq 1-based 连续…）：

- 读起来像**系统语义** → 该归 L2 `docs/architecture/runtime-model.md`；
- 但它们**只在测试注释里成文**，且每条都是「为什么这条断言长这样」的答案 → 属**测试的判定依据**。

产物判进 testing-strategy 并埋了互指（「系统侧的语义展开见 runtime-model.md」）——**判对了**，但这是全篇最容易误判的一处。

⇒ **回写 05 §3 的新规则**：
> **同一事实的两面投影**（结构轴「行为是什么」 vs 过程轴「为什么这么断言」）**不算双写**——视角不同，各自 own 一个面。但**必须显式互指**，否则一侧改了另一侧无从察觉。

## 6. 落位改动：过程轴文档归 `openspec/architecture/`，不归项目根

prompt 要求落项目根（与 README 平级），执行时改落 `openspec/architecture/`，与 `sad.md` 同居。**这个改动比原方案对**：

- 过程轴与空间轴（SAD）同属**设计真相源层**；
- `docs/` 是 **as-built 解释层**（系统「是什么」），过程轴（「怎么搭/怎么跑」）不属于它；
- 落项目根则两头不靠，无家。

⇒ **回写 `environments-template-draft.md`**：附 A/B 的路径范式（根级 `./environments.md`）改为 `openspec/architecture/environments.md`；**回写 05 §2.2** 的文档集布局。
