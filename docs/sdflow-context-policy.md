# sdflow 工作流的上下文管理：clear 与 compact 的选择

> **本文不是 as-built 文档**（as-built 见 `docs/sad/`），记录的是 sdflow 工作流工具链的
> 一项**待实施改进**——结论与依据，不是现状描述。
>
> **调研日期**：2026-07-25 · **状态**：结论已定，规则改动未实施
>
> **关联**：缓存计费机制的通用部分见 [`subagent-definitions-plan.md`](./subagent-definitions-plan.md) §1.1；
> 本文是它在 sdflow 具体流程节点上的展开。

## 1. 结论速查

| 节点 | 动作 | 首要理由 |
|---|---|---|
| **① ff 完成 → grill 之前** | **`/compact`** | grill 是**审人不是自审**，热上下文让提问更有的放矢；冷启动会把已定决策逐条重问 |
| **② grill 后 → spec-review 之前** | **`/compact`** | Step3 对抗裁决需要记得 grill 已拷问掉什么 |
| **③ 设计 GATE 过 → 实现之前** | **`/compact`** | 省钱空间最大；且实现期禁 `/clear`，这是最后机会 |

**三个节点都是 compact，没有一处该用 `/clear`。** 独立性、连续性、成本三个维度都不支持它（§3）。

**附带的时机规则**：要切模型或切 effort，**在刚 compact 完、上下文最小时切**——
实测同一次模型切换，438K 上下文时代价 $4.39，72K 时 $0.72，差 6 倍。

## 2. 为什么三个节点都不 clear

### 2.1 独立性不靠 clear——两个阶段各有来源

`~/.sdflow/workflow/workflow.md` §三.2（**G1**）：

> **子代理 fresh-context 替代 `/clear`（最关键，G1）**：`/clear` 唯一作用是给评审独立上下文；
> 但 sdflow-spec-review / sdflow-code-review / subagent-dev 的评审**本就 fan-out 到 fresh-context
> 子代理**——独立性是"子代理冷上下文"给的，不是 `/clear` 给的。故**全流程不用 `/clear`**，管线连续跑。
> 代价：评审末尾"对抗裁决"留热主 session（看过生成过程），一丝合成层偏置——由**反静默压制**
> （裁掉的 finding 连理由进报告"已裁掉"区）焊死边界。**注意**：子 agent 调度运行中仍禁 `/clear`。

这条论据覆盖**阶段二/三**。阶段一（grill）的独立性来源写在同文件**决策 4**：

> **grill 是对话岛（人类对抗，不折叠）**；设计门是唯一 HARD-GATE。

⇒ **阶段一的独立对抗方是人，阶段二/三是 fresh 子代理。两边都不需要 `/clear` 来提供独立性。**

### 2.2 grill 是"审人"不是"自审"——这一点决定了节点 ①

追完委派链才能确认（**别停在第一个文件**）：

```
/grill-with-docs  (~/.claude/skills/grill-with-docs/SKILL.md)
    └─ 可执行正文只有一行（第 7 行）：
       "Run a /grilling session, using the /domain-modeling skill."
       其余 78 行全是注入的通则块

/grilling  (~/.claude/skills/grilling/SKILL.md，全文 12 行)
    └─ "Interview me relentlessly about every aspect of this plan...
        Ask the questions one at a time, waiting for feedback on each question
        before continuing... If a *fact* can be found by exploring the codebase,
        look it up rather than asking me. The *decisions*, though, are mine."
```

**全程零子代理，形态是"一次一问、等人回答"的访谈。**

由此推翻一个看似合理的直觉——「grill 拷问的是模型自己刚写的设计，所以该冷启动去锚定」：

| 直觉 | 实际 |
|---|---|
| 对抗方是模型自己 → 会护短 | **对抗方是人**，人不会被模型的上下文锚定 |
| 热上下文 = 偏置 | 热上下文**有用**：它知道 ff 里哪些决策是秒答的、哪些是猜的、哪些被挥手放过 |
| 清掉只损失冗余 | 清掉会把 ff 已定的决策**逐条重问**——一次一问的格式下，每个冗余问题都是一次完整往返 |

而通则② 写着「人的注意力是唯一消耗掉就补不回来的资源」。**冷启动 grill 正是在花这项资源。**

> **残留风险**：ff 期间只在对话里说过、没落进四件套的约束，compact 后可能被摘要稀释。
> 缓解不是"别 compact"，而是 **grill 自带的落档纪律**——ADR→`openspec/adr/`、术语→`openspec/CONTEXT.md`。
> 一条只活在对话里的决策本来就是缺陷。

### 2.3 成本上也没有 clear 的理由

实测（数据来源见 §5）：

| | `/compact` 后 | `/clear` 后 |
|---|---|---|
| 上下文规模 | 72,369（实测） | 30K–92K（实测 12 个干净启动会话） |
| 启动前缀 | **cache-read**（22,556 token 存活） | **cache-write**（`cache_read` 实测恒为 0） |
| 每轮重读成本 | $0.036 | $0.015 – $0.046 |
| 保留的工作上下文 | 摘要（约 5 万 token） | **零** |

两者每轮成本**在同一量级**——因为启动前缀（CLAUDE.md × 3 份 + tools + memory + skills 清单）
两条路都躲不掉，它才是大头。

⇒ **`/clear` 相比 `/compact` 每轮只多省 1–2 分钱，代价却是整个工作上下文归零。**
它唯一的正当理由是"确实要换话题从头开始"，不是省钱。

## 3. G1 的评估：结论对，前提不对

把 G1 拆开逐条判：

| G1 的组成 | 评估 |
|---|---|
| **结论**「全流程不用 `/clear`」 | ✅ **成立**，且有三条独立支撑 |
| 支撑 A：独立性由 fresh 子代理提供（阶段二/三） | ✅ 成立 |
| 支撑 A'：独立性由人类对抗提供（阶段一，决策 4） | ✅ 成立 |
| 支撑 B（G1 未明写）：`/clear` 是人工动作，破坏"连续自动运行" | ✅ 成立，比 A 更硬 |
| 支撑 C（本次实测补充）：成本上 clear 不优于 compact | ✅ 成立（§2.3） |
| **前提**「`/clear` **唯一**作用是给评审独立上下文」 | ❌ **不成立** |

### 3.1 缺口：被禁的工具有第二份工作，没人接

`/clear` 有**两个**作用：

| 作用 | G1 的处理 |
|---|---|
| ① 给独立上下文 | 论证充分 → 由子代理 / 人类对抗替代 |
| ② **重置上下文规模** | **完全没提** |

G1 只论证了①就得出"全流程不用"，于是②这份工作**没有指派给任何人**。

翻遍 `workflow.md`，`/compact` 只以**症状**形态出现过——「事中判定超单 session
（讨论已跨 session/跨天，或**经历 /clear/压缩仍未收敛**）才切入 wayfinder」。

> **工作流知道上下文膨胀是失效模式（拿它当 wayfinder 的触发信号），却没有任何一处主动管理它。**

实际发生的是 **auto-compact 在 token 阈值处自行触发**，触发点在语义上**任意**。它可能压在：

- Step2 fan-out 进行到一半（各镜结果未收齐）
- **Step3 对抗裁决进行到一半**（丢掉裁决要用的那批 findings）
- 实现期某个 task 的 TDD 循环中间

第二项尤其要紧：Step3 裁决是 **G1 自己点名的薄弱处**，靠"反静默压制"（裁掉的 finding
连理由进报告）焊死。**若 auto-compact 在裁决前压掉了 findings 的细节，这道焊缝是焊在摘要上的。**

**实测佐证**：本次会话的 compact 一刀砍掉 366,136 token（83%），触发点纯粹是"到阈值了"，
与当时在做什么无关。

## 4. 建议的规则改动

**不改 G1 的结论，改它的前提，并补一条 compact 的正面立场。**

### 改动一：修正前提措辞

> 「`/clear` 唯一作用是给评审独立上下文」
> → 「`/clear` 有两个作用：**独立性**与**上下文重置**。独立性由 fan-out fresh 子代理（阶段二/三）
> 与人类对抗（阶段一 grill）替代；**上下文重置由在语义边界主动 `/compact` 承接**。」

### 改动二：新增 G1b —— 在语义边界主动 compact，别等阈值

三个点即 §1 的三个节点。理由：这三处都是"前一阶段的细节已落档、后一阶段用不上"的天然断面，
主动压的信息损失最小；阈值触发点是随机的。

**落位要求**：写进 workflow 的**步骤表**（第 3/4/6 步的备注列），**不要**只写进"关键设计决策"那节——
这条规则的成败在"人记不记得做"，藏在决策节里等于没有。

### 改动三：写明 compact ≠ clear

`/compact` **保留摘要，不提供任何去锚定效果**，它只解决成本与长度维。
别把它当独立性手段用——独立性仍然只有两个来源（fresh 子代理 / 人类对抗）。

### 三镜代价

| 镜 | 代价 |
|---|---|
| **系统** | G1 从一条铁律变成"禁 clear + 建议 compact"两条，认知负担 +1；真相源在 `~/.sdflow/workflow/`，**跨项目分发，改动影响所有仓** |
| **用户** | 三个节点各多一个人工动作。但节点 ① 本来就是硬人工断点（grill `disable-model-invocation: true`）、节点 ③ 前是设计 GATE 人类门——**三处有两处本来就在等人**，边际负担接近零 |
| **开发循环** | **主要成本**。主动 compact 靠人记得做，**没有机械化路径**——模型读不到自己的上下文用量（HUD 能读是因为它拿 stdin，skill 内拿不到）。所以它只能是纪律，不能是门禁 |

**主次判定：开发循环镜为主。** 这条规则的真实成败在"人记不记得做"，不在措辞——
所以落位（步骤表 vs 决策节）比遣词更重要。

### 备选

只在本仓 `CLAUDE.md` 加项目级约定，不动全局真相源。
**代价**：与 sdflow 分叉，下次 `sdflow-init update` 时两边措辞漂移。

## 5. 实测数据（本次调研的计量基础）

全部来自 `~/.claude/projects/-Users-cheneyzhao-Documents-05-sarvelo-mqtt-console/*.jsonl`
的 per-request `usage` 记录。名义成本按 Opus 5（$5/$25 每 MTok，cache read 0.1x，
cache write 2x @1h TTL）折算——订阅制下不是真扣款，但**与额度消耗成正比**。

### 5.1 单会话总账（92 次主循环请求）

| 项 | token | 名义成本 |
|---|---:|---:|
| cache write | 574,259 | $5.74 |
| **cache read** | **22,293,916** | **$11.15** |
| output | 146,346 | $3.66 |
| **合计** | | **$20.55** |

- **上下文重读占 54%**，是最大单项。22.3M ÷ 92 次 = 平均每请求携带 **24 万 token** 上下文。
- **缓存本身省了约 $100**：那 22.3M 无缓存要按 $5/MTok 全价 = $111.5。
  cache_read : cache_write = **39 : 1**，命中率健康。

### 5.2 一次 compact 的实测效果

```
compact 前：ctx = 438,505
compact 后：ctx =  72,369   (cache_write 49,813 + cache_read 22,556)
           ↓ 砍 366,136 token = 83%
```

**关键在 `cache_read = 22,556` 不是 0**——启动前缀（system + tools + CLAUDE.md + MEMORY.md +
skills 清单）**存活并命中缓存**。

⇒ **compact 是三层失效里最温和的一种**：只重建 messages 层，tools + system 层原封不动。

| 操作 | Tools 缓存 | System 缓存 | Messages 缓存 |
|---|:---:|:---:|:---:|
| 切 effort | model-specific | model-specific | ✘ |
| 切模型 | ✘ | ✘ | ✘（无 escape hatch） |
| **`/compact`** | **✓ 存活（实测）** | **✓ 存活（实测）** | ✘ 重建 |
| `/clear` | ✘（实测 `cache_read`=0） | ✘ | ✘ |

### 5.3 compact 的回本计算

| | 数值 |
|---|---|
| compact 前每轮重读 | 438,505 × $0.5/MTok = **$0.219/轮** |
| compact 后每轮重读 | 72,369 × $0.5/MTok = **$0.036/轮** |
| **每轮省** | **$0.183** |

一次性代价：

| 项 | 估算 |
|---|---|
| 摘要生成的 output（实测摘要 16,415 字符 ≈ 11K token × $25/MTok） | $0.27 |
| 摘要生成的 input（读全部 438K；命中缓存 $0.22 / 未命中 $2.19） | $0.22 – $2.19 |
| compact 后首轮 cache write（49,813 × $10/MTok） | $0.50 |
| **合计** | **约 $1.0 – $3.0** |

**⇒ 回本 5–16 轮。** 长会话里 compact 几乎必然划算。

> ⚠️ **摘要生成那次调用不在 transcript 里**——查了 compact 前后 20 分钟窗口内全部记录，
> 无对应 usage 条目。它的成本是**估算不是实测**，区间上限即源于"input 是否命中缓存"未知。

### 5.4 节点 ③ 的具体收益

实现期是主 session 轮次最多的阶段（50–150 轮）：

| | 每轮 | × 100 轮 |
|---|---|---|
| 带 438K 设计期上下文进实现 | $0.219 | $21.9 |
| compact 到 72K 再进 | $0.036 | $3.6 |
| **差额** | | **约 $18** |

作为对照，本次会话 92 轮总账才 $20.55。

> **注意**：子代理跑 fresh context，**它们的开销与主 session 上下文大小无关**。
> 所以节点 ② 省得最少（spec-review 的 token 大头在 5–8 个镜身上，主 session 只跑协调 + 裁决），
> 节点 ③ 省得最多（实现期主 session 轮次最密）。

### 5.5 未量化的风险：20-block 回看窗口

每个缓存断点最多向前找 **20 个 content block**。一次 turn 若产生超过 20 个 block
（多轮工具调用的 agentic loop 很常见），下一次请求的断点就找不到上一次的缓存，**静默 miss**。

本次会话 39:1 的读写比说明**没有大面积踩到**。但这是"静默"失效——不 fail、不报错，只是账变贵。
**观察信号**：cache_read 骤降而上下文没变。

## 6. 附带发现（与 clear/compact 无关，但更要紧）

`~/.claude/skills/grill-with-docs/SKILL.md` 注入的通则块是**旧版「三条通则」，缺第 ④ 条**。

文件自己带着警告：

> ⚠️ 本 skill 是第三方 skill，**升级会覆盖本区块** —— 覆盖后重贴一次。

它被覆盖过，然后没人重贴。而本仓 `692b9b3` 已把三条升到四条。

**缺的正是 ④「方案尽量简化，不为低概率小影响纠结完美方案」——而 grill 恰恰是定范围的那一步。**
一次一问、逐条拷问的格式天然容易把每个边角挖到底，④ 正是防这个的。

**处置：不修，这条已不构成风险**（2026-08-20 拍板）。`grill-with-docs` 已被 `/sdflow-spec`
相位 B 的内置拷问取代、**不在本工作流的任何路径上**（`external-dependencies.md` §5）——
一个不被调用的 skill 里通则停在第几版，不影响任何一次运行。

**且 MUST NOT 去修**：它是仓外第三方文件，本仓不负维护责任，贴进去每次升级都会被覆盖
（`sync_principles.py` 的 `PROJECT_TARGETS` 本就不含它，这是设计而非遗漏）。
本条自此为历史观测记录，不是待办。
