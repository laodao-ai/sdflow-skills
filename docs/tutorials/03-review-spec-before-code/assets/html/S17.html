选项 A（推荐）：下限定为 1m。RUN-03 的冷却非法条件改为「不是合法 Go duration，或小于 1 分钟」，报错文案同步说明下限。
选项 B：维持「大于 0」，只把 NFR 表改成如实描述（已按此临时改写 design NFR 行），并把「冷却配得过小会撞限流」记为接受的风险。
查来历
D10 当初拒绝「冷却为 0」的理由是「每条都推必撞限流」，同一理由对 1ns 一样成立。
推荐要验过
可行性：与 config.Load 现有阈值校验同构，一个比较加一条哨兵错误。推荐未亲验。
选项 A（推荐）
系统镜：单设备最多每分钟 1 条，与 20 条每分钟的限流同一量级；同一设备同时在途永远不超过 1 个，NFR 可以写成确定上界。
用户镜：值班的人不会被同一设备刷屏。演示时若想看到「冷却过后再推」，最短也要等 1 分钟。
开发循环镜：TM_NOTIFY_COOLDOWN=90s 等场景照旧可用；需要短冷却的测试本来就在 notify 包内用注入时钟做，不受影响。
主次判定：用户镜与系统镜为主。误配一次的代价是整个群被刷屏、后续推送因限流全部失败，而选项 A 的代价只是演示时多等几十秒 ⇒ 推荐 A。下限具体取 1m 还是更短（如 10s），取决于你演示时想不想用短冷却，这一点只有你知道。
