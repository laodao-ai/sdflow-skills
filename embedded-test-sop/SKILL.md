# 嵌入式手动测试 SOP 编写指南

## 两种工作模式

### 模式 A：生成 SOP（默认）

用户描述要测的功能/变更 → 读取 spec + 源码 → 生成测试文档 + 日志检查规则文件。

### 模式 B：分析日志（验证模式）

用户提供串口日志文件（`.log` / `.txt`）→ 读取对应的 `log-checks.yaml` → 逐条验证 → 输出结果报告。

**识别模式 B 的信号词**：「分析日志」「验证日志」「看看日志里有没有问题」「这次测试过了没有」+ 提供了日志文件路径。

---

## 模式 A：生成 SOP

### 第一步：理解输入范围

用户可以用以下方式提供测试范围（灵活组合）：

| 输入类型 | 示例 | 处理方式 |
|----------|------|----------|
| 变更目录 | `openspec/changes/decouple-conn-monitor-pending-reboot/` | 读 proposal.md + 所有 specs/ + tasks.md |
| Spec 文件路径 | `openspec/specs/safe-mode-protection/spec.md` | 直接读该文件 |
| 功能描述 | "OPS MQTT 断线重连" | 在 openspec/ 下搜索相关 spec 文件 |
| 多个文件/目录 | "测试范围：A目录 和 B目录" | 合并读取，合并场景 |

提取「测试范围」后，确认功能名称用于文件命名（英文 kebab-case，如 `ops-mqtt-reconnect`）。

**如果用户没有提供测试范围，追问一次**：
> 请问要为哪个功能/变更编写测试？可以提供 spec 文件路径、openspec 变更目录，或直接描述功能。

### 第二步：收集上下文

必须读取的信息：

1. **Spec 场景**：从 spec 文件提取所有需求场景（R1、R2…），这些都要覆盖到测试中
2. **源码常量**：读 `custom/inc/user_config.h`，提取所有涉及的超时/阈值/间隔宏
3. **日志 TAG**：从实现文件（.c）里提取 `static const char *TAG = "..."` 的值和关键日志关键词
4. **固件版本**：优先使用用户指定版本；否则读 `custom/inc/user_config.h` 中的版本宏（如 `USER_FW_VERSION`），找不到则写「待填写」

5. **协议校验逻辑**：如果测试涉及 MQTT/BLE/HTTP 等网络指令，必须读取设备侧的指令解析函数（如 `parseMqttServerData`、`parseBleCmdData` 等），提取：
   - 必填字段名称和校验顺序
   - 各字段的有效值范围（如 `time` 必须在 `cmdTimeout` 秒内）
   - 校验失败对应的错误码（精确枚举值）
   - 特殊豁免规则（如某些命令类型不校验时间）
6. **Topic 构造函数**：读取 topic 拼接代码（如 `mqtt_getTopic`），确认实际的 topic 格式和分隔符，不要凭文档或记忆推测

关键信息清单：
- 涉及的超时时间（`USER_*_TIMEOUT_MS`、`USER_*_SEC` 等宏），**同时记录计算公式**（如 `N × 3600s`）
- 涉及的 MQTT topic 格式（**不写实际密码，留空 `<PASSWORD>`**），**标注每个 topic 的方向（上行/下行）**
- 串口日志中的 TAG 名称和关键日志字符串（精确复制源码中的字符串字面量）
- 硬件操作（复位方式、LED 指示含义）
- 指令协议的必填字段、校验规则和错误码映射

### 第三步：设计测试分组

分组数量根据 spec 场景数量自动推断：
- 场景 ≤ 3 个：2-4 组（可合并相关场景）
- 场景 4-8 个：4-6 组
- 场景 > 8 个：最多 8 组（合并相近场景，冒烟测试优先）

**分组顺序**：正常路径（基线） → 边界条件 → 异常注入 → 恢复验证

**分组独立性**：如组间有依赖（如 G3 依赖 G2 进入安全模式），在前置条件中明确写出。

### 第四步：编写每组步骤

每组包含以下部分（全部必须）：

```markdown
## G<编号>：<场景名称>

**测试目标**：一句话说明验证什么场景/需求。

### 前置条件

- 固件版本：vX.X.X（或"待填写"）
- 设备状态：（已上电/已复位/处于安全模式等）
- 工具就绪：串口终端（115200 bps）/ MQTT 工具（连接 <BROKER>:<PORT>，凭证见内部文档）
- 其他依赖：（LoRa 从节点已上电/网络可达等）

### 步骤

| # | 操作 | 命令/动作 | 等待 | 预期观察 |
|---|------|-----------|------|----------|
| 1 | 操作描述 | 具体指令或动作 | 等待时间（精确到秒） | 日志关键词或状态 |

> **测试缩短方案**（仅当等待超过 30 分钟时添加）：将 `<CONST_NAME>` 临时改为 X 秒并重编固件，测试后恢复原值。

### 判定规则

**通过（PASS）**（全部满足）：
- ✅ 条件1（具体日志/状态）
- ✅ 条件2

**失败（FAIL）**（任一出现）：
- ❌ 条件1（如：超过 Xs 未见 "关键日志"）
- ❌ 条件2（如：串口出现 `ASSERT`）

**注意事项**：列出可能干扰判断的已知偶发行为。

### 失败后操作

当本组判定为 FAIL 时：
1. **保存串口日志**：将终端日志另存为 `<YYYYMMDD>-G<N>-<feature>-serial.log`
2. **记录关键信息**：截图最后 30 行日志、当前 uptime、设备 IMEI/SN
3. **保存 coredump**（如有 `ASSERT` 日志）：立即断电，通过调试工具导出 flash dump 后再上电
4. **提交问题**：将日志文件和复现步骤提交到开发，注明固件版本和测试环境

### 恢复操作（如本组改变了设备状态）

说明如何恢复到干净状态，供后续组使用。
```

### 第五步：填写步骤细节规范

**等待时间**（不能模糊）：
- 精确值：`等待 5 秒`（从代码常量推导）
- 有上限：`等待至日志出现 "xxx"（最长 30 秒）`
- 周期观测：`等待 2 分钟，观察每 5 秒是否持续出现 "xxx"`

**等待时间必须标注来源公式**：
- 步骤表中的等待时间，不能只写最终秒数，必须写出常量来源和计算过程
- 示例：`等待 3600 秒（debugTimeoutHours=1 × 3600s/h）`，不能只写 `等待 3600 秒`

**测试缩短方案的"双时间标注"规则**：

当某步骤涉及临时修改代码缩短等待时间时，SOP 中**每一处**引用该时间的地方都必须同时标注两个值：
1. **生产值**（原始常量计算结果，标注公式）
2. **测试值**（临时修改后的值）

格式要求：

前置条件中先声明生产行为：
```markdown
> **生产行为**：`constantName=N` 的超时阈值 = N × MULTIPLIER = X 秒 = **Y 小时/分钟**。
>
> **测试缩短方案**：临时将乘数从 `MULTIPLIER` 改为 `TEST_MULTIPLIER`，使阈值变为 N × TEST_MULTIPLIER = **Z 秒**。
```

步骤表中每个等待时间格式：
```
| ... | 等待 Z 秒（测试值；生产=X 秒/Y 小时） | ... |
```

**禁止**：步骤中只写测试缩短后的时间而不注明生产值——测试人员必须清楚自己验证的是什么生产行为。

**日志关键词**（从源码字符串字面量复制）：
```
[INFO][OpsChannel] MQTT connected successfully
```
不要写"看到连接成功日志"这种模糊描述。

**MQTT/网络指令格式规范**：

当测试步骤涉及向设备下发网络指令（MQTT/BLE/HTTP 等）时，必须遵守以下规则：

1. **Topic 方向标注**：每个 topic 必须标明数据流向
   ```markdown
   **Topic 格式**：
   下行（服务器→设备）：  prefix/product/cmd/{device_id}
   上行数据（设备→服务器）：prefix/product/data/{device_id}
   上行 ACK（设备→服务器）：prefix/product/ack/{device_id}
   ```
   SOP 正文中引用时写「发到 cmd topic」或「监听 data topic」，不要只写 topic 字符串。

2. **动态字段用占位符**：指令 JSON 中凡是每次执行都不同的值，必须用 `<占位符>` 并附操作提示
   - 时间戳：`"time": <当前Unix时间戳>` → 附注：`用 date +%s（Linux/Mac）或在线工具获取`
   - 设备 ID：`"tid": "{device_id}"` → 附注：`从串口启动日志或 ASKNETSTATE 响应获取`
   - 序列号：`"cmd_id": <递增序号>`
   - **禁止**在示例中硬编码过去的时间戳或错误的设备 ID

3. **必填字段校验清单**：在"下行命令 JSON 格式"章节中，必须列出每个字段的：
   - 是否必填
   - 有效值范围或格式
   - 校验失败时设备返回的错误码
   - 特殊规则（如 `time` 字段必须在 cmdTimeout 秒以内）

4. **从源码提取协议结构**：读取指令解析函数（如 `parseMqttServerData`）的校验逻辑，确认：
   - 哪些字段会被校验（type/tid/time 等）
   - 校验的顺序和错误码映射
   - 哪些命令有特殊豁免（如 askTime 不校验 time 超时）
   将这些信息整理到 SOP 的"下行命令格式"章节中。

### 第六步：生成两个输出文件

#### 文件 1：SOP 文档

文件名格式：`YYYY-MM-DD-<feature-name>-test-sop.md`（使用今天日期）

完整文档结构：

```markdown
# 手动测试 SOP：<功能名称>

## 文档信息

| 字段 | 内容 |
|------|------|
| 固件版本 | vX.X.X（或"待填写"） |
| 测试日期 | YYYY-MM-DD |
| 测试人员 | — |
| 测试环境 | 开发板型号 / 量产板 / 测试床 |
| 关联变更 | openspec/changes/<name>/ |
| 日志检查文件 | YYYY-MM-DD-<feature-name>-log-checks.yaml |

## 硬件与工具准备

（具体硬件清单 + 工具清单，MQTT credentials 写"见内部文档"）

## 关键常量速查（涉及 3 个以上常量时必加）

| 常量名 | 值 | 来源 |
|--------|----|------|
| CONST_NAME | 值+单位 | user_config.h:行号 |
| 超时/阈值公式 | `变量 × 乘数` = 结果（单位换算） | 源文件:行号 |

> 所有由运行时变量和编译期乘数共同决定的超时/阈值，必须在此表中列出完整公式，不能只写最终秒数。
> 例：`debugTimeoutHours × 3600` 秒（即 N 小时），0=永不超时

## 测试总览

| 组号 | 场景 | 步骤数 | 预计时间 |
|------|------|--------|----------|
| G1 | ... | N | ~X 分钟 |
| 合计 | — | — | ~X 分钟 |

---

（各组详细步骤）

---

## 附录：日志关键字速查（涉及 3 个以上模块 TAG 时添加）

| 模块 TAG | 关键词 | 含义 |
|----------|--------|------|
| `TagName` | `关键词` | 说明 |
```

#### 文件 2：日志检查规则

文件名格式：`YYYY-MM-DD-<feature-name>-log-checks.yaml`

为每个关键判定条件生成机器可读的检查规则，供模式 B 自动分析使用：

```yaml
# 日志自动检查规则 - <功能名称>
# 使用方式：将此文件与串口日志文件一起提供给 Claude，说"分析日志"
feature: <feature-name>
firmware_version: vX.X.X
generated: YYYY-MM-DD

groups:
  - id: G1
    name: <场景名称>
    checks:
      - id: G1-C1
        description: 网络连接成功
        type: must_contain          # must_contain | must_not_contain | must_contain_before
        pattern: "[INFO][Cat1_net] Network is ready"
        window_seconds: 60          # 从组开始计时，Xs 内必须出现（0 表示全文搜索）
        severity: critical          # critical（失败即终止）| warning（记录但继续）
      - id: G1-C2
        description: 无 ASSERT
        type: must_not_contain
        pattern: "ASSERT"
        window_seconds: 0
        severity: critical
      - id: G1-C3
        description: SIM 识别成功
        type: must_contain
        pattern: "SIM Ready: YES"
        window_seconds: 30
        severity: critical

  - id: G2
    name: <场景名称>
    checks:
      - id: G2-C1
        description: ...
        type: must_contain
        pattern: "..."
        window_seconds: 0
        severity: critical
```

**规则编写原则**：
- `pattern` 使用源码字符串字面量，不做正则处理（简单子串匹配）
- `window_seconds: 0` 表示在整份日志中搜索
- `severity: critical` 的规则失败时，该组直接判 FAIL，不再检查后续规则
- `severity: warning` 的规则失败时，记录为 WARNING，该组仍可 PASS
- 只为「可通过日志判断」的条件编写规则；需要人眼确认的（如平台侧状态、LED）不写规则

## 模式 B：分析日志

当用户提供串口日志文件路径时：

1. **定位规则文件**：在同目录或 `custom/docs/test/` 下找对应的 `*-log-checks.yaml`；若找不到，告知用户并列出可用的规则文件
2. **读取日志**：读取串口日志文件（可能很长，按需分段读取）
3. **逐组执行检查**：
   - 按 `window_seconds` 限定搜索范围（0 = 全文）
   - `must_contain`：在范围内找到 pattern 子串 → PASS
   - `must_not_contain`：在范围内未找到 pattern → PASS
4. **生成结果报告**：

```markdown
# 日志验证报告：<功能名称>

日志文件：path/to/serial.log
规则文件：path/to/log-checks.yaml
验证时间：YYYY-MM-DD

## 汇总

| 组号 | 场景 | 结果 | Critical失败 | Warning |
|------|------|------|-------------|---------|
| G1 | ... | ✅ PASS | 0 | 0 |
| G2 | ... | ❌ FAIL | 1 | 0 |

**整体结论**：PASS / FAIL（有任意 critical 失败则整体 FAIL）

## 逐组详情

### G1：<场景名称> — ✅ PASS
- ✅ G1-C1 网络连接成功：在第 234 行找到 "[INFO][Cat1_net] Network is ready"
- ✅ G1-C2 无 ASSERT：全文未找到 "ASSERT"

### G2：<场景名称> — ❌ FAIL
- ❌ G2-C1 安全模式激活（critical）：60 秒窗口内未找到 "SAFE MODE ACTIVATED"
  → 建议：检查重启次数是否达到阈值（USER_DEFAULT_REBOOT_THRESHOLD = 5）
- ✅ G2-C2 无 ASSERT：全文未找到 "ASSERT"

## 无法自动验证的条件（需人工确认）
- G1：平台侧设备在线状态（需登录平台查看）
- G3：MQTT 工具是否收到心跳数据包
```

## 写作要点

- **具体 > 模糊**：写 `等待 30 秒` 而不是 `等待一会儿`
- **日志原文**：从源码字符串字面量复制，而不是转述
- **credentials 留空**：MQTT 密码、token 统一写「见内部文档」
- **来源可追溯**：超时等关键数字注明 `来自 CONST_NAME = 值`，并写出计算公式
- **分组独立**：每组都写前置条件，不假设前一组一定已通过
- **长等待必给缩短方案**：等待 > 30 分钟的步骤必须注明如何缩短
- **双时间标注**：凡是涉及测试缩短方案的步骤，每处等待时间都必须同时标注「测试值」和「生产值」
- **动态字段禁止硬编码**：指令中的时间戳、设备 ID 等运行期变量必须用 `<占位符>` 并附获取方法
- **协议从源码提取**：指令格式必须读源码的解析/校验函数确认，不能凭记忆或文档推测
