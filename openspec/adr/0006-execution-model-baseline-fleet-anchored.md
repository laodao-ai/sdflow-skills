# 执行模型能力基线锚定机队：prose 协议脚本化，强弱措辞相对机队定义

这套 workflow 的实际执行机队 = **opus / sonnet / gpt-5.5 等多家族混编**，不含开发它时恰好在用的更强模型。此前的设计与 grill 隐含以"开发时所用模型"为能力目标——该假设撤销（explore 2026-07-03）。核心观察：workflow 的质量机制分两类，**结构性机制**（脚本、config 注入、fresh 子代理、证据锚点）模型无关不掉价；**prose 协议**（靠模型在长指令里"记得照做"的机械流程）随执行模型变弱而衰减，且失效形态不是"做错"而是**静默跳步**——恰与反静默守卫正面冲突、且检测不到。

据此钉三条约束：

- **(a) 能力基线 = 机队最弱可靠档**：任何一步的可靠性论证，按"该步实际会被指派的最弱模型"评估，不按设计者当时在用的模型。
- **(b) prose 协议脚本化优先（硬约束）**：凡机械协议（路径解析、平台回落链、步末固定动作），MUST 优先落成确定性脚本 / 结构模版（必填 section），模型只调用 + 只做判断。这是本仓既有哲学「机械活交脚本、模型只做判断」从**设计取向升格为硬约束**。
- **(c) 强/弱措辞机队锚定**：规则文件中"强模型 / 最强模型 / 禁弱模型"一律解释为**相对当前执行机队的档位**（强档 = opus / gpt-5.5 级，跑 verify / 对抗裁决 / final 终审；中档 = sonnet 级，可跑领域镜 / 生成，**不得跑 verify 与对抗裁决**；弱档 = haiku 级，只跑纯机械步）。具体"档位→模型"映射放消费仓 `config.yaml`，规则文件不写死模型名（机队会换血）。

## Considered Options

- **机队锚定 + prose 脚本化（选中）**：能力假设显式化、可随机队演进重校；机械协议交脚本后跨模型行为一致，还从"模型行为测试"变成普通脚本单测（可测性提升）。代价 = 多维护几个小脚本 + config 多一段档位映射。
- **按开发时最强模型设计，运行时"尽量跟上"**：零改动，但协议衰减以静默跳步形态出现，无告警无痕迹，违反"任何一层覆盖不得无声蒸发"元原则。不可接受。
- **把机队限定为单一强模型（全流程只许最强档跑）**：假设最干净，但成本不现实，且放弃了混编机队天然自带的跨家族 outside voice 结构红利（盲区错开）。未选。

## Consequences

- **`minimize-repo-footprint` 的 resolver 改脚本化**（本 ADR 首个应用，标 〔model-baseline-amendment〕）：三步链从"写进 SKILL.md 的 prose 协议"改为全局脚本 `~/.sdflow/hack/resolve-workflow.sh`，SKILL.md 只剩"跑脚本、用输出路径"。
- **ROADMAP 调序**：`opsx-ship-orchestrator`（把 15 步编排从 prose 固化进结构，弱主模型漏步兜底）与 Phase C `cross-model-outside-voice`（混编机队下天然可得且更必要）优先级上调，建议紧随 footprint 之后。
- **adr/0001 的"verify 用强模型、禁弱模型"按 (c) 重释**：强 = 机队最强档（opus / gpt-5.5 级）；sonnet 属中档，**不合格**跑 verify。
- **两笔债进 todolist**（结构化兜底类，不阻塞当前 change）：①评审报告"决策登记区"改必填 section（无决策点也须显式写"无"）+ 主审 checklist 核验项——防弱模型 silent pick；②impl-review 置信过滤阈值 `<80` 跨模型不可比——阈值进 config 按模型调、或改判据为"对抗镜复核不通过才滤"。
- CONTEXT.md 补术语 **机队锚定**；后续所有规则/设计写"强/弱模型"处受其约束。
