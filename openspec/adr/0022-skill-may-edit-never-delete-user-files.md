# 0022 · skill 对用户文件：**可改内容，MUST NOT 删除文件**

> 状态：**Proposed**（2026-07-14，grill `add-sdflow-devenv` 收敛时立）——待该 change ship + 首个真实项目试点后升 Accepted。
> 关联：`docs/sad/07-devenv-skill-design.md` §1.4 · §1.5 · §5 ①'（归位模式）· 附录 **A26** · `adr/0021`（代价可见 > 机械拦截，同源原则）· CONTEXT「副驾」· `openspec/rules/doc-authoring.md`（DOC-1：演进史不该被毁）。
> **适用面**：本 ADR 立的是**生态级纪律**，不止 `sdflow-devenv`——任何会写用户项目文件的 skill 都适用。

## Context

`sdflow-devenv` 的「归位模式」（brownfield）要处理一个真问题：项目里已经散着旧的测试文档，**不搬走就双写**——新文档一出生就有个竞争对手。mqtt-console 的实证：*若写成「读模板 → 填文档」的生成型，模型会重写一份而源文件原地不动 ⇒ **双写变三写***。

早期设计因此给了 skill **删除能力**：三种处置（整体删除 / 部分保留改写 / 降为一行指针），配三道护栏（搬运表人门 + 删源前工作区必须干净 + 删后扫残留引用 + 冷审「删源镜」）。

**一个需要四道护栏才敢做的动作，本身就在提示它不该由 skill 做。**

## Decision

**skill MUST NOT 删除用户的任何文件。skill MAY 改文件里的内容。**

| 处置 | skill 做什么 | 内容 | 判据 |
|---|---|---|---|
| **整体失效** | 文件**开头**加一行 `> ⚠️ 已失效 —— 内容已迁至 <path>` | **原样保留** | 范围 = 整份，**无歧义** |
| **部分失效** | **删掉失效的那部分内容**（+ 留指针） | **删除** | **「失效范围」必须由「它不存在了」来界定** |
| **真删文件** | ❌ **不做**——收尾报告给出 `git rm <file>`，**人自己敲** | 人决定 | 爆炸半径不受控 |

**改已有文件的四条 MUST**（与文件类型无关）：
1. **先给 diff 给人看，确认后才写**；
2. **幂等标记块**；
3. **可精确回滚**（skill 知道自己写了哪些行）；
4. **MUST NOT 猜文件里原来有什么**——要知道就**问人**。

## 为何这样（判据）

**① 爆炸半径谁控得住——这是删与改的分界线。**

- **删文件**：指向它的引用可能在**仓外**——别人的书签、别的仓的文档、藏在代码注释里的路径。mqtt-console 那次，旧路径藏在 `Makefile` 注释和 7 个测试文件注释里，**共 20 处，而那还只是 `grep` 得到的**。**skill 看不见的地方，它就是看不见。**
- **改内容**：文件在原地、引用不断、`git diff` 是真内容、`git checkout -- <file>` 精确回滚。**半径受控。**

**② 「搬运表」这个人门是橡皮图章——而 `07` 自己在隔壁识别过这个失效模式。**

§5 ③-pre 论证「跑前列命令给人过目」是假门：*给人看的是 `make integration` 这一行调用，对「target 里到底跑什么」提供**零信息量**——**真正危险的内容恰恰不在那个门里***。

**搬运表完全同构**：它给人看「文件名 + 处置」，而真正的风险是「**这份文档里有没有一段内容没被搬走**」——**搬运表对此提供零信息量。** 一个人不可能逐条核对 20 个文件的内容再点确认。**他会点确认。**

> **一个贵到没人真的走的门，就是橡皮图章。**

**③ 它与副驾身份冲突**（`adr/0021` 同源）：「**辅助**我搭建环境 + **提醒**我别忘了考虑什么」——**删我的旧文档，既不是搭建，也不是提醒。是代劳，而且是最不可逆的那种。** 而它对核心承诺的贡献**是零**。

**④ 为什么「部分失效」必须真删（不能只加标记）**（操作者 2026-07-14 定）：**「失效范围」不能靠一行标记来界定。** 内容还留着、读者却得自己猜哪几行失效了——**这是最糟的中间态**。范围要么由「文件顶部一行」界定（整份失效），要么由「它不存在了」界定（部分失效）。

## 代价（如实记）

**不删 ⇒ 双写留存。** 旧文档还在 `docs/`，新文档在 `openspec/architecture/`。

**接受它**，理由与 `adr/0021` 同源——**代价可见 > 代劳**：
- 旧文档**第一行就写着**「已失效，去看那边」；旧链接还通、`grep` 还找得到、**任何人打开它当场就知道该去哪**（比「文件消失、链接 404、人一脸懵」好得多）；
- 收尾报告白纸黑字列着「这 5 份已被取代」+ **现成的 `git rm` 命令**。

> **看得见的双写，是一个待办；看不见的误删，是一个事故。**

## 被否方案

- **skill 删，靠「搬运表人门 + 工作区干净 + 删后扫残留 + 删源镜」四道护栏**（原设计）：见「为何这样」②——**搬运表这个门给不了人做判断所需的信息**。
- **skill 删，但人门放在删完之后（看 `git diff` 而非文件名表）**：门确实换到了有信息量的位置，**但它仍然要求人事后核 20 个 diff，而且 skill 已经删了**。
- **skill「清空内容、降为一行指针」**（我一度提的折中）：**仍然在销毁内容**——被操作者当场堵死。**加一行是纯加法；清空是全损失。**
