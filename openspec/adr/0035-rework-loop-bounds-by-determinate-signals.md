# 返工循环的边界由确定信息与硬上限界定，不由模型判断界定

> 状态：**Accepted**（2026-07-31，`curb-rework-loop-cost` 拷问阶段收敛，用户拍板）· 关联 change：`curb-rework-loop-cost`

返工循环（实现期 fix 循环、代码审复审循环）此前有三处边界交给模型当场判断：**跑哪些测试**（"受影响层"）、**要不要再审一轮**（"还有没有问题"）、**算不算同一个发现**（问题指纹比对）。三处的共同失效模式是：判断出错时一律偏向**少做**——少跑一层、少审一轮、计数清零——即 fail-open。

三处都有反例实证。**测试范围**：`align-sdflow-spec-with-openspec-schema` 给 `copy_bundle` / `handle_config` 加了关键字参数，implementer 判定 `test_runtime_gitignore.py`（测 gitignore 合并）不在影响面内，实际被击穿，8 个用例红在 `main` 上直到本 change 修复（`f0c2dee`）；该 change 跑了 37 个 fix 轮、深至 fix8，无一轮抓到它。**熔断计数**：同一 change 的 `CR-02 / CR-09` 跨 `fix5/fix6/fix7` 三轮换三个 YAML 语法角落（注释后的 document start → `%YAML` directive → `schema :` 带空格），每轮指纹不同 ⇒ `review-loop-breaker`「连续 2 轮同指纹」永不触发。**复审轮数**：`sdflow-code-review` 全文只描述一轮，多轮是编排器自发行为，无触发条件也无终止条件，实跑到 10 个 `checkpoint(impl-review)`。

本决策是 `openspec/CONTEXT.md`「**盘面即状态**」（机判锚点须是确定性产出，不押模型自由生成的措辞）在返工循环上的落点。

## Decision

三处边界一律改由**确定信息 + 硬上限**界定：

- **测试范围（`sdflow-implement`）**：中间 fix 轮跑 **unit 全层**（整层跑、不筛选）+ **上轮失败的具体用例**（有记录的确定信息）；集成 / e2e 整体推到收口。**按成本分档，不按影响面分档**——"哪层受影响"不再是判据。收口跑一次全量，报告中所有判「通过」的行锚同一最终 SHA（单一盘面语义不变）。
- **复审轮数（`sdflow-code-review`）**：自动修复后 MUST 复审**一轮**，只审修复 diff、不重审全量；仍有 Critical/Important ⇒ **不再自发第三轮**，全部 defer 进 buglist 并在报告标注。硬上限 = 1。
- **熔断计数（`sdflow-implement`）**：在既有「同文件 + 规范化问题指纹连续 2 轮」之外，增加一条**与指纹无关**的上限——同一文件累计被 Critical/Important 命中 ≥3 轮即熔断，升 strong 档仲裁「**这个门本身该不该存在**」，而非继续仲裁单条 finding 是否成立。

## Considered Options

- **本方案（确定信息 + 硬上限，选中）**：三处判断点全部替换为可机械求值的信号。代价 = 精确性下降（中间轮会跑一些"其实没被影响"的 unit 用例；熔断会对真·不同问题提前触发），换来的是失效方向从 fail-open 翻转为 fail-safe。熔断的处置是**升档复核**而非直接放过，故提前触发的代价有界。
- **保留「受影响层」判断，改为要求 implementer 写明判定依据（砍掉）**：让判断留下书面痕迹以便追溯。砍掉理由：写依据不改变判断本身的可靠性——`align-sdflow-spec` 的 implementer 完全可以写出一段自洽的「schema 改动不涉及 gitignore 合并」，而它是错的。**要求解释一个不可靠判断，只会得到一个有说服力的错误判断。**
- **test impact analysis（按用例级依赖图精选，砍掉）**：用覆盖率数据或依赖图精确算出受影响用例，兼得精确与可靠。砍掉理由：需要覆盖率采集或静态依赖图，本仓三个消费栈（pytest / go test / vitest+playwright）无统一现成工具，成本远超本 change；且它解决的是"精确性"，而本决策要解决的是"可靠性"，二者不同问题。留作未来台阶。
- **code-review 一轮即止、残差全 defer（砍掉）**：更省，且贴合 `sdflow-code-review/SKILL.md:7-8`「一份报告 + 残差交 hand-off 异步再入口」的原意。砍掉理由：① 自动修复**改的正是源码盘面**（`sdflow-code-review/SKILL.md:314-316`），一轮即止会留下「那份修复无人审」的盘面缺口，而 `sdflow-done` 的 verify 审的是实现完整性、不是修复正确性；② `sdflow-implement/SKILL.md:349,353` 已把 code-review 的「自动修复循环 / fix 循环」写进自己的契约，选此项须反向改那两处；③ 与既有实践对抗（实跑已在多轮），护栏比禁令易落地。
- **熔断只调指纹算法、让它更能识别"同一根因"（砍掉）**：把「规范化问题指纹」做得更聪明，使换语法角落的 finding 仍被认作同一发现。砍掉理由：这要求指纹算法理解"什么是同一个根因"——本身就是一个模型判断，等于用一个更复杂的判断去补另一个判断的漏，且它落在无界语法面上（判断两个 YAML 构造是否"同一类问题"），撞 CLAUDE.md 基准 5。

## Consequences

- **集成层回归的暴露时点后移到收口**，修复更贵。**这是本决策明确接受的代价**——但现状是集成/e2e 在中间轮**根本没被可靠地跑过**（8 红测即证据），故修正后严格优于现状，不是新增风险。
- **中间轮会跑一部分"其实无关"的 unit 用例**。unit 是三层中最便宜的一层，整层跑的成本可接受；这是用少量确定成本换掉一个不可靠判断。
- **「受影响层」这个提法在本仓退役**。任何文档 MUST NOT 再用「只跑受影响的测试」来描述中间轮范围——它读起来合理，但落地即 fail-open。
- **`sdflow-implement` 与 `sdflow-code-review` 关于「code-review 有无 fix 循环」的文档分叉必须在本 change 内消除**：前者 `:349,353` 说有，后者 `:181` 说「无 re-review 紧闭环」。本决策取"有，且硬上限 1 轮"，两处措辞一并对齐。
- **硬上限 3 与 1 是启发式，非推导所得**：3 由两个病例校准（两例均在第 3 轮已可判定，且本仓 7 天 16 change 中 fix 轮 ≤2 者占多数，不误伤）；1 由"修复本身需被审一次、但不需被审第二次"的对称性定。按通则④不为它们反复调参，落地后如误伤再调。
- **本决策不触碰单一盘面的语义**：`sdflow-implement/SKILL.md` 原条款要求「报告里所有判通过的行锚同一最终 SHA」，该要求原样保留；被改掉的只是"每轮都重跑"这条**对该目的零贡献**的强化（中间轮结果按条款自身定义就不进最终报告）。
- **回滚代价**：revert 后三处条款一并回退，已按新契约跑过的 change 不受影响（其证据 schema 形状未变）。
