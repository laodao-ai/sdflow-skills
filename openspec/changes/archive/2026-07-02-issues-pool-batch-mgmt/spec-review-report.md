## Findings（去重合并，按严重度，附裁决）

### 🔴 Finding A — 硬切迁移 + 全局 ID 撞号（需拍板 Q1）
**命中**：对抗镜2-F1、领域镜-5、接地镜-F1（联动）。置信高、严重度**最高**。CONFIRMED。
- 路径硬切 `buglists/`→`issues/buglist/`（task 2.1），**无迁移工具、无 dual-read**（proposal 只写"下游 routine 自行迁移"一句）。
- 后果链：下游 `update` 拉新脚本 → 旧数据仍在旧路径 → `next_id()`(buglist.py:204) 只扫新目录 → 新增从 B1 重数 → **与旧文件 B1/B2 撞号**（违脚本核心不变量"跨文件不撞号"）；旧 OPEN 债对新 scan/reindex **隐形** → 正是 Success Metric 要杜绝的"无声堆积"被迁移缺口重新引入。
- 本仓自身豁免（无 issues 数据），但共享 toolkit（TG-20）风险 100% 转下游。
- **裁决**：真爆点，且违 change 自身指标 → **Q1 需拍板**。推荐至少 (b)：迁移仍算下游，但 Phase B **必须**加过渡期 **dual-read**（新旧路径都扫再取 max）+ **ID 撞号检测**，否则"零无声堆积"名不副实。

### 🔴 Finding B — 批次命名/对账机制缺失（需拍板 Q2）
**命中**：对抗镜1-F1。置信高、严重度高。CONFIRMED。（= grill 时我判"留实现期"的批次 key 悬空分支，被证明够格设计层。）
- 批次 key=清理 change 名，但 PLANNED 时该 change **未出生**（umbrella §8.4 自认"批次=还没出生的 change"）。item↔批次仅靠**字符串相等**关联。
- 缺三环：① sweep 分诊进"哪个"批次、名字/聚类算法**未定义**（tasks 4.1 只说"分诊入批次"）；② 人真开 cleanup change 时可能用**不同名** → 关联断链；③ `batch` 命令只有 add/set-status，**无 rename/merge**；reindex 遇"item 有批次 tag 但 batches.md 无此 key"的 orphan **行为未定义**。
- **裁决**：真设计空白 → **Q2 需拍板**。推荐保守简化：sweep 永远新建 1 批次 key=本change、禁跨 change 合并 + 加 `batch rename` + reindex 对 orphan 批次 tag **显式报警不静默生成 ghost**。

### 🔴 Finding C — batches.md 无格式契约 + 「纠正」语义未定义（需拍板 Q3）
**命中**：对抗镜1-F2(a+b)、领域镜-3。置信高、严重度高。CONFIRMED。
- **格式**：batches.md「半手维护」但无 machine grammar（不像 buglist.py 有 block 正则）。design §8.4 示例"状态"是**单行箭头链**（PLANNED→IN_PROGRESS→DONE 挤一行），而 tasks 3.3 把"完成记录"列为**独立字段** → 矛盾。reindex 是"全量覆盖"还是"原地 patch"未定 → **大概率吃掉人写的「计划/优先级」**。
- **纠正语义**：spec"状态与成员不一致则标出纠正"只有正向 Scenario；**反向**（手标 DONE 但成员未全终态）该做什么未定。且 reindex **无权**改 PLANNED→IN_PROGRESS（§8.5 那是人的权限）→ 只能"打警告不改值" → batches.md 同存"状态=DONE"+"⚠️不一致"两个矛盾信号，下游信谁未定；若实现选"直接改回"则越权、可能与人手改形成**震荡环**。
- **裁决**：真设计空白 → **Q3 需拍板**。推荐：定字段级 grammar（生成行 vs 人写行 + 分隔）；reindex 对 batches.md **只精确 patch 状态/成员行、绝不覆写人写计划**；"纠正"= **只追加警告标注、绝不越权改人写状态值**（防震荡）。

### 🟠 Finding D — 0 成员批次 vacuous 假 DONE（自动决策 D1）
**命中**：对抗镜1-F3。置信高、严重度中高。CONFIRMED。
- 判据"全部成员∈终态集"是全称量词，**对空集永真**。`batch add` 可独立于 sweep 提前登记计划性空批次 → 下次 reindex **立即误判 DONE**，绕过 PLANNED→IN_PROGRESS，且是最隐蔽的"无声堆积"（计划没落地却记"已清完"）。
- **裁决**：清晰爆点、修法明确 → **D1 自动决策**：判据加"成员数≥1"前置，0 成员保持 PLANNED/待分诊。

### 🟠 Finding E — reindex 从未接入触发 + INDEX 禁手改零强制（自动决策 D3）
**命中**：对抗镜2-F3。置信高、严重度中高。CONFIRMED。
- task 4.1 的 sweep 序列**不含 reindex** → 即便 sweep 走完，INDEX.md 也不自动刷新，全靠人记得手敲 reindex。"禁手改"无 banner/校验 → 两次 reindex 间被手改无人察觉，review UI（task 5.1）可能读到污染数据。
- **裁决** → **D3 自动决策**：reindex 接入 sweep 步末；INDEX 加 `<!-- GENERATED by issues.py reindex — DO NOT EDIT -->` banner，reindex 覆盖前弱校验告警。

### 🟠 Finding F — sweep 孤儿兜底无触发点 + 源探测退化（自动决策 D4 + Q1 关联）
**命中**：对抗镜2-F2、对抗镜1-F5。置信中高、严重度中。CONFIRMED。
- 孤儿（源=""）交"通用 --open-ungrouped 清理流程"，但该流程**无自动触发、无责任人**（三步都要人主动敲）→ 孤儿实际可能没人跑而堆积（重演被修的 smell）。而多 change 并行是本仓常态、`detect_change` 此时返回"" → 孤儿不是边角是常态子集。
- **裁决** → **D4 自动决策**：opsx-done 运行时**知道本 change 是谁**，sweep 应**显式传 --change** 而非靠 detect_change 猜，从源头减少假孤儿。剩余真孤儿的兜底触发若不落地，proposal 须**诚实记 Non-Goal**（不用"交给另一条流程"制造已解决错觉）→ 并入 Q1 一并裁。

### 🟡 Finding G — 批次列位置 + 新旧列混扫（自动决策 D2）
**命中**：接地镜-F2、对抗镜2-F4。置信高、严重度中。CONFIRMED。
- 现有解析纯**位置索引**（cells[4]=状态、cells[6]=关联Change）。批次列若插在"状态"前会错位所有硬编码读写 → 静默腐化。旧7列 vs 新8列文件混扫无 spec Scenario。
- **裁决** → **D2 自动决策**：批次列**追加表末**；沿用 `len(cells)>N` 防御式解析；补 spec Scenario 覆盖新旧列混存。

### 🟡 Finding H — 失败模式 / 原子写 / 幂等 / 并发 全缺（自动决策 D5–D9）
**命中**：领域镜-1/2/3/4、对抗镜1-F4。置信中高、严重度中。CONFIRMED。
- design/spec/tasks grep"原子/锁/并发/幂等/失败模式/损坏"**零命中**，全 happy path。现有 recorder 写是 `open(w)+writelines` **非原子**（无 temp+os.replace、无锁）；reindex 跨写 INDEX+batches 两文件无事务边界；reindex/triage 重跑安全未定义；umbrella 自认 **TG-26 并发/共享可变状态**是 HR，但 TG-26 要 Phase C 才落地，而 Phase B 恰在造共享可变状态系统；跨池 ID 前缀互斥（B/T）是偶然事实非契约。
- **裁决** → **D5–D9 自动决策**（design 声明失败模式表 / 恢复模型 + 原子写 / 幂等 / 并发串行假设 / ID 前缀规范 + 冲突检测）。**并发不加锁**（proportionate：串行 CLI 工具，显式声明假设即可，真并发留后续）。
