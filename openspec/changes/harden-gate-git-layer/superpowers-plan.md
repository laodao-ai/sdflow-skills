## Global Constraints

实现期 MUST 遵守（逐字来自 `design.md` 的 `## Compliance` 节）：

- 内容比较 **MUST** 显式判 returncode；**MUST NOT** 让两次失败读比较相等（读失败 ≠ 内容为空）。
- `ls-tree` **单侧缺失 MUST 判 stale**，**MUST NOT** 混作读取失败。
- **MUST NOT** 在 `reviewed_sha` 缺失/非法时回退到 `report_last_sha` 或任何反推式锚。
- **MUST NOT** 为凑触发点诊断而保留任何路径枚举通路；但 `emit` **MUST** 输出 `reviewed_sha` 值。
- 勾选豁免 **MUST** 常开、按内容切；**MUST NOT** 按阶段切。
- design 域失鲜 **MUST** 只在实现窗口内求值，且 **MUST** 分别覆盖 `RUN_SOP`/`RUN_PLAN`/`CONTINUE_IMPL` 三个分支；
  **MUST NOT** 只在 step 7 后加一次检查（那会让前两个分支逃出检查）。
- **MUST NOT** 引入语义分诊层或任何形式的重锚逃生口。
- 监视集 **MUST** 保住：实现期改源码、勾 `superpowers-plan.md` 复选框 **MUST NOT** 让设计门失鲜。
- code 域 **MUST NOT** 用整棵树的 sha，**MUST NOT** 用负向 pathspec（二者均已实测证伪）。
- 子进程 env 清理 **MUST** 用 denylist（剔除 `GIT_` 前缀），**MUST NOT** 用 allowlist（Windows 会漏系统变量）。
- `design_approved` 与 `reviewed_sha` **MUST** 在同一次文件写入中落盘。
- `reviewed_sha` **MUST** 挂在顶层 `ship-gate:` 键下作直接子键，三个 producer 模板逐字对齐。
- `GateIndeterminate` **MUST** 携带结构化 payload，五类失败原因各给可行动诊断。
- 每条新增守卫 **MUST** 附变异证明（删掉即变红），结果落 impl-report；**MUST NOT** 以「用例存在且为绿」充当证明。
- 新增用例 **MUST** 经 `is_stale` 公共入口求值（**例外**：`OSError`/`TimeoutExpired` 用例的触发点可能在
  `is_stale` 调用范围之外，如 D3 短路分支——此类显式豁免，改为经 `decide()`/`main()` 求值）。
- code 域的**两个**消费方（`code-review-report`、`verify-report`）**MUST** 各有覆盖。
- 删除既有用例 **MUST** 在 impl-report 逐条说明其对应哪个退役机制，并区分「纯删除」与「需重新设计等价用例」。
- 共享 fixture（`approved_change` / `tail_ok` / `impl_done`）**MUST** 与新锚模型同批重构。
- `ship_gate.py` **MUST** 保持零第三方依赖；退出码 **MUST** 落在 `{0,3,4,5,6}` 内。

**R-ID 索引**（溯源本 change delta spec 的 Requirement）：

| R-ID | Requirement |
|---|---|
| R1 | 判据 MUST 只在其保护的风险真实存在的阶段求值 |
| R2 | 失鲜判定 MUST 直接比较内容，MUST NOT 从 git 管道推断路径变更 |
| R3 | 评审锚 MUST 由 producer 记录，MUST NOT 从提交历史反推 |

### Task 1: 评审锚成为门禁的唯一真相源，缺失即拒绝放行

**Blocked-by:** none
**R-ID:** R3

三个评审产物在落结论时一并记下「被批准的是哪一份盘面」，gate 读这个锚来判断新鲜度，不再从提交历史反推。锚的语法（完整 40 位 OID）与语义（该对象存在且是 commit）分两层校验；任何一层不过——字段缺失、写成缩写 SHA 或 `HEAD`、指向不存在的对象、指向 blob 或 tree——gate 一律给出 `UNKNOWN(6)` 并说明缺的是哪个字段，绝不悄悄回退到旧的反推式锚。

本票同时把测试基座抬到能表达这件事的形状：现有共享 fixture 把报告与它的审查对象放进同一个根提交，结构上不存在「先于报告的盘面」可供落锚，因此必须先能建模「四件套先落盘、报告后落盘」的两段提交，后续所有票的用例才构造得出来。

- [x] 报告 frontmatter 能承载 40 位 OID 形态的锚字段，且该字段与既有结论字段同层
- [x] 锚缺失 / 格式非法 / 对象不存在 / 对象非 commit 四种形态各自得到 `UNKNOWN(6)`，诊断能指出具体是哪一种
- [x] 「结论字段在、锚字段缺」的中间态同样 `UNKNOWN(6)`，且诊断点名缺的是锚
- [x] 三个评审产物的模板都写出了锚字段，措辞与设计中的示例逐字一致
- [x] 反推式旧锚已退役，仓内无任何调用点仍依赖它
- [x] 共享 fixture 支持两段提交模型，且 44 处既有调用点全部跑通
- [x] 每条新增守卫各附一次「删掉即变红」的变异证明，逐条落 impl-report

### Task 2: git 调用失败一律落在退出码契约内，且带可行动诊断

**Blocked-by:** none
**R-ID:** R5

gate 调用 git 的每条路径在失败时都给出契约内的退出码与一条能直接照做的诊断，不再让异常逸出成 Python 默认退出码。git 二进制缺失、权限不足、调用挂起都被收敛为同一类受控结果，且挂起有明确上界而非无限等待。五类失败原因——git 不可用、超时、锚缺失、锚非法或对象不存在、读失败——各自携带结构化信息，因为五者的补救动作完全不同，一句「git 调用失败」对使用者毫无价值。

同时中和一切能从外部改变判定输入的状态：子进程环境按 denylist 清理（剔除 `GIT_` 前缀键、其余原样透传），确保判定结论在被污染的环境下与干净环境一致。

- [x] 三个 git 调用 helper 各自在 `OSError` 下得到受控结果（三组独立验证）
- [x] 三个 helper 各自在调用超时下得到受控结果（三组独立验证），超时上界的取值理由写在注释里
- [x] 顶层入口把这类失败映射为 `UNKNOWN(6)`，五类原因的诊断文案彼此可区分
- [x] 已知会扭曲判定的 git 环境变量被剔除后判定结论与干净环境一致，且非 `GIT_` 前缀的环境变量原样透传
- [x] 退出码始终落在契约集内
- [x] 每条新增守卫各附一次「删掉即变红」的变异证明，逐条落 impl-report

### Task 3: design 域改为直接比较被审内容，退役路径枚举通路

**Blocked-by:** 1
**R-ID:** R2, R4

design 域的新鲜度判定从「顺着 git 管道推断哪些路径动过」改为「把锚与当前盘面的被审内容摆在一起直接比较」。比较以路径到对象标识的映射为单位，因此新增、删除、改名、修改天然全部覆盖，不需要另做双侧并集。映射完全相等即新鲜；唯一的豁免是任务清单的纯复选框翻转——该豁免常开、按内容切、不按阶段切，因为勾选框的写入方是 agent 的自由行为而非流程契约，按阶段切会让非该阶段的正常勾选立刻假失鲜。

读失败与内容为空必须区分：一侧路径不存在是合法的「缺失」信号，应判失鲜，绝不能呈现成「请检查仓完整性」这类误导人的读失败诊断。

旧的帧比较整簇随之退役——整簇逐一清除，不留悬空引用与孤儿代码；但内容豁免判据与归一化核心属于保留复用，不得误删。既有用例中承载「仍然生效」安全承诺的那批，必须改写成等价形态并入新编号体系，不得静默删除。

- [ ] 实现期修改源码、勾选实现计划的复选框，设计门保持新鲜
- [ ] 任务清单的纯复选框翻转判新鲜，且至少两个阶段各验一次；差异超出复选框即判失鲜
- [ ] 把已批准产物换回锚之前的旧内容即判失鲜
- [ ] 规格子树的新增、删除、改名（内容不变）三类各判失鲜，均经公共入口求值
- [ ] 与被审内容无关的报告排版提交不移动锚，仍判失鲜
- [ ] 一侧路径缺失判失鲜，诊断不呈现为读失败；真正的读失败得到受控结果
- [ ] 旧帧比较簇整簇退役后仓内无悬空引用，保留复用的三处仍在且有调用点
- [ ] 退役用例分「纯删除」与「需重新设计等价用例」两类逐条登记，后者已改写并入新编号
- [ ] 每条新增守卫各附一次「删掉即变红」的变异证明，逐条落 impl-report

### Task 4: design 域失鲜只在实现窗口内求值，三个入口分别接入

**Blocked-by:** 3
**R-ID:** R1

设计门的失鲜判定只在「设计已批准、实现尚未交付」这段窗口内求值——过了代码审起点之后再修订四件套是流程明文允许的动作，不该被判失鲜。这需要真实的控制流重排：先算出待定结论、再决定要不要求值，三个进入实现期的入口各自接入，不能只在末尾加一次检查（那样前两个入口会完全逃出检查，方向是 fail-open）。

失鲜时的诊断要能让人一步定位差异，把锚值直接呈现出来并拼出可直接执行的比较命令。

- [ ] 三个进入实现期的入口各自求值失鲜，且各自无旁路（三组独立验证）
- [ ] 窗口之外——代码审期与收尾期修订四件套——不判设计失鲜
- [ ] 失鲜诊断带出锚值，并给出可直接执行的差异比较命令
- [ ] 每条新增守卫各附一次「删掉即变红」的变异证明，逐条落 impl-report

### Task 5: code 域改用顶层条目比较，两个消费方各有覆盖

**Blocked-by:** 1
**R-ID:** R2

code 域的新鲜度同样改为直接比较，比较对象是仓库顶层条目的浅层快照、排除记账目录后求等值。不用整棵树的标识（收尾阶段写验证报告即改变整树标识，正常流程第一步就假阳），也不用负向路径限定（它会继承外部可控的大小写开关）。这样合并提交引入的源码改动、以及把源码搬进记账目录的改名，都不再从判定中逃逸。

这条判定今天有两个消费方，其中一个零覆盖——两个都要各自验到。

- [ ] 代码审之后经合并提交引入的源码改动判失鲜
- [ ] 把源码改名迁进记账目录判失鲜
- [ ] 记账目录内部的正常写入（写验证报告、归档移动目录）仍判新鲜
- [ ] 两个消费方各有覆盖，均经公共入口求值
- [ ] 前两条正例各附一次「删掉即变红」的变异证明（这是本域改判据唯一的正面收益证明）
- [ ] 每条新增守卫各附一次「删掉即变红」的变异证明，逐条落 impl-report

### Task 6: 评审工作流不与新判定自锁，全套件回归并交接

**Blocked-by:** 1, 2, 3, 4, 5
**R-ID:** R3

锚必须在「它要指向的那份内容已经落盘」之后才写，否则锚指向不含该内容的更早提交，判定当场自锁。两个域各有一个实例，分别处置：代码审把自动修复与报告放进同一次提交，需改成修复先单独落盘、锚指该提交、报告再单独落盘；设计审在拍板前若对四件套有实质改动，需先把该改动单独落盘取得标识，再执行拍板回写。两处都要有端到端用例证明不自锁——变异证明的形态是让锚指向改动前的提交，用例须变红。

收尾：把行为收紧显式登记进交接文档（实现期直接改设计纠偏今后会被拒绝，这是有意为之而非缺陷），补上消费仓的只读自查命令让人一次看清有几个在途变更会因缺锚被拒，并说明本次改动须走哪条升级路径才生效。全套件回归在本票完成，合并后于主干再跑一次。

- [ ] 代码审的自动修复与报告分两次落盘，且有自动修复非空的端到端用例证明锚不自失鲜
- [ ] 设计审拍板前的二次修订单独落盘后再回写锚，端到端用例证明拍板后首次判定不被拒
- [ ] 上述两条各附变异证明：让锚指向改动前的提交，用例变红
- [ ] 设计审收敛口写明拍板前若四件套有实质改动须先跑窄复核
- [ ] 人工补锚指引说明需补两个字段，并给出「该填哪个提交」的语义判据
- [ ] 判定入口的头注释与链序文档反映新的判定形态与窗口边界
- [ ] 交接文档登记：存量报告须重审、行为收紧非缺陷、生效所需的升级路径、消费仓只读自查命令
- [ ] 实现期再跑一次全历史核验，确认已知的三个确证反例仍是全部
- [ ] 仓根全套件回归通过，合并后于主干再跑一次
