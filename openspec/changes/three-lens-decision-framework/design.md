## ADR-1：落点形态 —— 增强现有 BASE-12，不新增独立编号项

**背景**：三镜要在书面层（bundle 质量门）有落点。BASE-12 已是「备选方案记录 / ADR」槽，含「候选方案」「理由」「被否决方案」。三镜是往哪放？

**候选方案**（按三镜评估）：

| 方案 | 系统镜（耦合/单一源） | 用户镜（读 spec 的工程师） | 开发循环镜（未来维护） |
|---|---|---|---|
| **A. 挂进 BASE-12 现有槽**（选定） | 无新文件 / 新编号，规则集单一源、耦合最小 | 在既有「候选方案 / 理由」处就近看到三镜要求，认知连续 | 改决策规则只动一处 |
| B. 新增 BASE-30 独立项 | 三镜逻辑与 BASE-12 alternatives 重叠 → 双源 | 要跨项对照「BASE-12 写方案、BASE-30 写三镜」 | "改一处忘另一处"漂移面 +1 |
| C. 新增独立 `three-lens.md` 约束文件 | 引入新 bundle 文件 + INDEX 登记 + resolver 覆盖 | 又一处要查 | 最重维护面 |

**决策**：A —— 三镜评估法挂进 BASE-12「候选方案」（方案对比按三镜展开）、主次判定行挂进「理由」（末尾补一句主次判定）。

**定主次**：本问题核心是**避免双源 / 规则重叠**——**开发循环镜压倒**。理由：三镜框架若自己造成规则漂移就自相矛盾；BASE-12 的「候选方案 / 理由」本就是三镜的天然宿主，原地增强零新增维护面。用户镜（认知连续）与之同向、不冲突，故不构成 tradeoff。

**当前方案代价**：BASE-12 检查点行变长（可读性略降）；三镜与「最小可行 + 理想架构」两句要在同一槽内共存，措辞需拧清。

## ADR-2：强度 × 触发深度 —— 分两层，书面层只 TG-23 触发 MUST

**背景**：三镜是「每个决策都 MUST 写」还是有触发门？全量 MUST 会让琐碎决策也背三镜样板。

**候选方案**（按三镜评估）：

| 方案 | 系统镜（bundle 噪声/开销） | 用户镜（读者信噪比） | 开发循环镜（生成循环负担） |
|---|---|---|---|
| A. 每个决策都 MUST 写三镜（全量硬门） | 琐碎决策也写三镜段 → spec 噪声爆炸 | 读者被样板淹没 | 生成循环每步背样板，拖慢 |
| **B. 分两层**（选定） | 书面负担限定在 ≥2 方案的高杠杆决策 | 只在真正 ≥2 方案处见三镜，信噪比高 | 高杠杆处焊死、琐碎处轻 |
| C. 全 SHOULD（软建议） | 无强制 | 可能整段缺失 | 无门禁 = 形同虚设，退回私有记忆困境 |

**决策**：B —— **行为层**（私有记忆 `decision-three-lens-framework.md`）每个决策都用（自动决策 / 推荐 / 补主次判定）；**书面层**（BASE-12 + workflow.md G2 + code-review Step4）只在 **TG-23（≥2 合理方案 / 非显然设计）触发时 MUST 写**三镜 + 主次，不下沉到琐碎决策。

**定主次**：本问题核心是**框架要生效、但不能变成样板税**——**用户镜（信噪比）与开发循环镜（不拖慢）并重**。二者都指向"限定在高杠杆决策"；触发深度复用 TG-23 已有机制承载最省（不新造触发条件）。系统镜同向。故 B。

**当前方案代价**：判断"是否 ≥2 合理方案 / 非显然设计"由模型在 TG-23 处判——存在漏判把该写三镜的决策当琐碎跳过的风险；靠 spec-review / code-review 的对抗镜兜底。

## ADR-3：进程 —— 走独立 OpenSpec change + spec delta，不裸改源

**背景**：workflow bundle 改动够轻能直接改 assets，还是须走 propose → review → done？

**候选方案**（按三镜评估）：

| 方案 | 系统镜（防漂移） | 用户镜 | 开发循环镜（审计/兜底） |
|---|---|---|---|
| **A. 独立 change + spec delta**（选定） | spec delta 锚定行为契约，未来改 G2/Step4 措辞时 delta 对码核验挡漂移 | 无直接可感差异 | 留 propose→review→archive 审计 + 评审兜底 |
| B. 直接改 assets 源（轻量） | 无锚，改了就改了、下次谁改 G2 忘了三镜也没人拦 | 同上 | 快但无痕、无评审 |

**决策**：A（grill 决策⑤已拍板）。grill 成果直接喂本四件套，不重新发明。

**定主次**：本问题核心是**治理层改动会传导进此后每个决策的登记与裁决口径**，错了代价高、且极易随后续 workflow 编辑悄悄漂移——**系统镜（防漂移锚）压倒**。开发循环镜（审计 / 兜底）同向。用户镜中性。故 A。

**当前方案代价**：比裸改多一轮 spec-review + done 开销；但治理层改动值这一轮。

## ADR-4：「有把握自动选」→ T10 对齐 —— 顺手纳入（设计门 Q1 拍板 A）

**背景**：spec-review 对抗镜 + codex 发现 code-review SKILL:7/30/96 仍写「≥2 方案有把握自动选」，而主 spec:48、ship:23、workflow.md:84、及 code-review 自身台账:144 均已是 T10 三级协议。是否在 T46 顺手对齐（A）还是纯三镜、债延后（B）？

**候选方案**（按三镜评估）：

| 方案 | 系统镜（消除既有矛盾） | 用户镜 | 开发循环镜（职责/回退） |
|---|---|---|---|
| **A. 顺手对齐 T10**（拍板选定） | 消除 code-review:96 与自身台账:144 + ship:23 + 主spec:48 的既有自相矛盾；全域一致 | 中性 | 同一句已因三镜在编辑，顺带对齐；避免未来再 touch |
| B. 纯三镜、T10 延后 | 既有矛盾留存（虽被 todolist 追踪） | 中性 | 单一职责更纯，但同行未来须再编辑一次 |

**决策**：A（设计门人工拍板，2026-07-05）。

**定主次（据新证据翻转）**：初评倾向 B（担心 A 是语义变更、blast radius 大）；但**接地核实推翻该担心**——T10 早已是既定行为（ship:23 编排 + 主spec:48 governance + 台账:144），code-review:96「有把握」是 T10 落地时漏改的**纯陈旧散文**。故 A 非行为变更、而是**一致性修复**，「blast radius」代价坍缩。**系统镜（消除既有自相矛盾）现压倒开发循环镜（单一职责）** → A。（dogfooding 示范：新证据可翻转主次判定。）

**当前方案代价**：落点③ 从 3 行三镜编辑扩为「三镜 + T10 对齐」；实现须照 ship:23 单一 canonical 措辞抄，避免臆造 T10 变体。风险低（有单一源可抄）。

## ADR-5：fold-vs-defer scope-triage 判据 —— 顺手纳入（设计门追加，用它自己判它自己）

**背景**：设计门上用户指出——我判 Q1（fold T10）用的判据「新发现工作是否并入当前 change，看对现有 change 工作的影响多大」本身是复用率极高的治理规则，且 workflow 未成文；且**一次完整 workflow 循环固定成本极高，固守「change 单一职责」教条会把开发周期和成本都推高**。是否把此判据 fold 进 T46？

**候选方案**（按三镜评估）：

| 方案 | 系统镜（capability 归属） | 用户镜 | 开发循环镜（成本） |
|---|---|---|---|
| **A. fold 进 T46**（选定） | 同一 capability（workflow 决策治理）、是三镜在 scope 决策上的专用应用，不违 BASE-18 单一职责 | 中性 | 一条小规则 + 与三镜同宿主；T46 未进实现，增量微审即可；省一整轮 change 固定成本 |
| B. 另开 change | 无谓拆散紧密相关的两条决策纪律 | 中性 | 为一条小规则单开一整轮 propose→…→merge，固定成本高 |

**决策**：A（设计门拍板）。**用此判据递归判它自己**（dogfooding）：同 capability + 高耦合（以三镜为方法）+ 低增量（一条规则、未进实现）→ fold。

**定主次**：核心是 **workflow 循环固定成本 vs 单一职责教条**。用户明确——循环固定成本极高，反射式拆 change 推高周期与成本；本条 related + 低影响，摊销增量审查成本 << 一整轮新 change 成本。**开发循环镜（省固定成本 + 高耦合）压倒系统镜（单一职责纯度）** → A。

**防吸积纪律**：fold 只在「同 capability + 高耦合 + 低增量」三者齐时成立——不是每个路过的想法都塞进开着的 change。本条满足，T10 亦满足；反例（独立大概念）仍 defer。

**当前方案代价**：微量重开刚过的设计门（加 BASE-18 规则 + delta scenario + 对新增内容增量微审）；落点从 5 扩 6。
