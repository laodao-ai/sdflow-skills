## B8: 子代理上下文的轮次终结会回收该上下文在飞的 run_in_background 任务（主 session 让出轮次转空闲已实证不受影响：702s 跑满 exit 0）——∴ 后台任务 MUST NOT 由子代理派出后跨其轮次边界等待
> 子代理上下文的轮次终结会回收该上下文在飞的 run_in_background 任务（主 session 让出轮次转空闲已实证不受影响：702s 跑满 exit 0）——∴ 后台任务 MUST NOT 由子代理派出后跨其轮次边界等待

**关联文档**：`openspec/changes/async-outside-voice/design.md`

> 🔄 **2026-07-18 复审修订（本块正文已按判别实验重写）**：本条初记时定为 P1／「主 session 空闲即回收」，
> 依据是一组**受控对比**（空闲 399s 被 SIGTERM vs 活跃 660s exit 0）。该对比**有混淆变量**：
> 全部观测都发生在 **implementer 子代理上下文**内，而在子代理里「转入空闲」与「子代理轮次终结」
> 是**同一个动作、不可分辨** ⇒ 原证据只支持「**子代理轮次终结** ⇒ 回收」，推不出「主 session 空闲 ⇒ 回收」。
> 编排层随后在**主 session** 直接做了判别实验（见下「主 session 判别实验」），**证伪了后者**。
> ∴ 现象范围收窄到子代理域、优先级 P1 → **P2**（不再冲击 async barrier 的核心机制，
> 但仍是真实且必须遵守的子代理域约束）。

**现象**：同一会话、同一命令（fake runner 固定 sleep 660、经真实 outside-voice.sh → timeout -k 10 900 派出、内层 --timeout 900）在**子代理上下文**内跑两次，变量是该子代理是否结束轮次：

trial 1（派出后让出轮次、转空闲等通知）：dispatch 10:44:23Z，10:51:02Z 即被 SIGTERM，存活仅 399s；输出文件末行 `outside-voice.sh: line 207: 51309 Terminated: 15`，无 `<<<SDFLOW_EXEC_EXIT>>>` 行（整条命令未走到收尾 printf）。同一时刻该会话在飞的另两个后台任务一并消失：until-loop 守望任务（本应无限循环）与 sleep 240 任务（本应 10:54:37Z 出结果），两者输出文件均 0 字节。即当时在飞的 3 个后台任务在 ~10:51:02Z 同时被回收。

trial 2（全程保持活跃，用 4 次 pytest -q 填满等待、从不空闲）：dispatch 10:57:57Z → RETRY_END 11:08:57Z，**跑满 660s、exit 0**、envelope 恰好 1 行、进程链 zsh→outside-voice.sh→timeout→fake codex→sleep 660 全程完整、ppid 66874←66872←66871←66723←66718 全程不变无 reparent。

∴ 600000ms 外层上限已被 trial 2 排除（660s > 600s 却成功），回收源是另一个、且与「该子代理转入空闲/结束轮次」在时间上重合。

**主 session 判别实验（2026-07-18，编排层直接跑，反证「主 session 空闲 ⇒ 回收」）**：在**主 session**（非子代理）
以 `run_in_background` 起一个每 5s 落盘的心跳探针，期间**多次让出轮次转入空闲**（等双轴审子代理的完成通知）：

| 指标 | 结果 |
|---|---|
| 存活时长 | **702s 跑满，exit 0**（`COMPLETED exit0 total=702s`） |
| 跨过 B8 的 399s 死亡点 | **是** |
| 跨过 600000ms 外层上限 | **是**（702s > 600s） |
| ppid | **全程稳定 53240，无 reparent** |
| 心跳连续性 | **141 拍无断点**（仅 2 处 6s 间隔 = 1s 调度抖动） |
| 主 session 期间是否空闲 | **是，多次让出轮次等通知** |

原始证据：`/tmp/mainsess_probe.log`。⇒ **「主 session 让出轮次转空闲」不触发回收，B8 在主 session 不复现。**

**根因**：触发点是「**子代理上下文的轮次终结**」，而非「空闲」。子代理轮次结束时，该上下文在飞的
`run_in_background` 任务被连带回收（本轮 3 个在飞任务同时消失即此）。主 session 没有对应的「轮次终结」
事件（会话持续存在），故让出轮次等通知不触发回收。**未进一步隔离到 harness 具体实现层**（属平台行为，
非本仓代码），登记到此为止。

**修复方案**：
- ✅ **已落地（本 change 内）**：两评审 SKILL 的 `sdflow:async-branch` marker 段 ⑥ 明文焊死
  「collect barrier MUST 在主 session 执行、MUST NOT 委派子代理」，并写明理由（本条 + 702s 反证）。
- 通则（本 change 之外）：任何编排若需后台任务跨轮次存活，**MUST 在主 session 派出并在主 session 等待**；
  子代理内派后台任务只能在**该子代理自己的轮次内**取回结果。

**影响范围**：**不再冲击本 change 的核心机制**（barrier 执行位已焊在主 session，见修复方案）。残余影响面 =
任何在子代理上下文内派 `run_in_background` 并期望跨轮次存活的编排。下段为初记时的原始评估，**其前提
（主 session 空闲即回收）已被上述判别实验证伪**，保留仅供追溯：SKILL ⑥ 明文要求「站点仍 RUNNING ⇒ MUST 让出轮次、等该后台任务的完成/超时通知」——而「让出轮次」正是 trial 1 触发回收的那个动作。后果：voice 比 fan-out 慢时（正是 async 化要救的场景），barrier 会杀掉它正在等的那个后台任务；且杀死后不再产生完成通知（守望任务一并被杀），collect 可能永不返回。按 ⑦「其余一切情形 → 保守 fallback exec-error」尚不至于假绿，但 async 的收益在该路径上归零、甚至劣于同步（白等一场再降级）。注意 design.md:35 与 spec-review-report.md:28/81 所引的既有 spike（660s/跨600000ms/exit0/ppid稳定）与本条不矛盾——那次 spike 的「ppid 全程稳定」说法本身意味着期间有人持续观察（活跃态），从未覆盖空闲态。
