## B8: 子代理上下文的轮次终结会回收该上下文在飞的 run_in_background 任务（主 session 让出轮次转空闲已实证不受影响：702s 跑满 exit 0）——∴ 后台任务 MUST NOT 由子代理派出后跨其轮次边界等待
> 子代理上下文的轮次终结会回收该上下文在飞的 run_in_background 任务（主 session 让出轮次转空闲已实证不受影响：702s 跑满 exit 0）——∴ 后台任务 MUST NOT 由子代理派出后跨其轮次边界等待

**关联文档**：`openspec/changes/async-outside-voice/design.md`

> 🔄 **2026-07-18 复审修订（本块正文已按判别实验重写）**：本条初记时定为 P1／「主 session 空闲即回收」，
> 依据是一组**受控对比**（空闲 399s 被 SIGTERM vs 活跃 660s exit 0）。该对比**有混淆变量**：
> 全部观测都发生在 **implementer 子代理上下文**内，而在子代理里「转入空闲」与「子代理轮次终结」
> 是**同一个动作、不可分辨** ⇒ 原证据只支持「**子代理轮次终结** ⇒ 回收」，推不出「主 session 空闲 ⇒ 回收」。
> 编排层随后在**主 session** 直接做了判别实验（见下「主 session 判别实验」），**证伪了后者**。
> ∴ 现象范围收窄到子代理域、优先级 P1 → **P2**（不再冲击 async barrier 的核心机制，
> 但仍是真实且必须遵守的子代理域约束）。

**现象**：同一会话、同一命令（fake runner 固定 sleep 660、经真实 outside-voice.sh → timeout -k 10 900 派出、内层 --timeout 900）在**子代理上下文**内跑两次，变量是该子代理是否结束轮次：

trial 1（派出后让出轮次、转空闲等通知）：dispatch 10:44:23Z，10:51:02Z 即被 SIGTERM，存活仅 399s；输出文件末行 `outside-voice.sh: line 207: 51309 Terminated: 15`，无 `<<<SDFLOW_EXEC_EXIT>>>` 行（整条命令未走到收尾 printf）。同一时刻该会话在飞的另两个后台任务一并消失：until-loop 守望任务（本应无限循环）与 sleep 240 任务（本应 10:54:37Z 出结果），两者输出文件均 0 字节。即当时在飞的 3 个后台任务在 ~10:51:02Z 同时被回收。

trial 2（全程保持活跃，用 4 次 pytest -q 填满等待、从不空闲）：dispatch 10:57:57Z → RETRY_END 11:08:57Z，**跑满 660s、exit 0**、envelope 恰好 1 行、进程链 zsh→outside-voice.sh→timeout→fake codex→sleep 660 全程完整、ppid 66874←66872←66871←66723←66718 全程不变无 reparent。

∴ 600000ms 外层上限已被 trial 2 排除（660s > 600s 却成功），回收源是另一个、且与「该子代理转入空闲/结束轮次」在时间上重合。

**主 session 判别实验（2026-07-18，编排层直接跑，反证「主 session 空闲 ⇒ 回收」）**：在**主 session**（非子代理）
以 `run_in_background` 起一个每 5s 落盘的心跳探针，期间**多次让出轮次转入空闲**（等双轴审子代理的完成通知）：

| 指标 | 结果 |
|---|---|
| 存活时长 | **702s 跑满，exit 0**（`COMPLETED exit0 total=702s`） |
| 跨过 B8 的 399s 死亡点 | **是** |
| 跨过 600000ms 外层上限 | **是**（702s > 600s） |
| ppid | **全程稳定 53240，无 reparent** |
| 心跳连续性 | **141 拍无断点**（仅 2 处 6s 间隔 = 1s 调度抖动） |
| 主 session 期间是否空闲 | **是，多次让出轮次等通知** |

原始证据：`/tmp/mainsess_probe.log`。⇒ **「主 session 让出轮次转空闲」不触发回收，B8 在主 session 不复现。**

**根因**：触发点是「**子代理上下文的轮次终结**」，而非「空闲」。子代理轮次结束时，该上下文在飞的
`run_in_background` 任务被连带回收（本轮 3 个在飞任务同时消失即此）。主 session 没有对应的「轮次终结」
事件（会话持续存在），故让出轮次等通知不触发回收。**未进一步隔离到 harness 具体实现层**（属平台行为，
非本仓代码），登记到此为止。

**修复方案**：
- ✅ **已落地（本 change 内）**：两评审 SKILL 的 `sdflow:async-branch` marker 段 ⑥ 明文焊死
  「collect barrier MUST 在主 session 执行、MUST NOT 委派子代理」，并写明理由（本条 + 702s 反证）。
- 通则（本 change 之外）：任何编排若需后台任务跨轮次存活，**MUST 在主 session 派出并在主 session 等待**；
  子代理内派后台任务只能在**该子代理自己的轮次内**取回结果。

**影响范围**：**不再冲击本 change 的核心机制**（barrier 执行位已焊在主 session，见修复方案）。残余影响面 =
任何在子代理上下文内派 `run_in_background` 并期望跨轮次存活的编排。下段为初记时的原始评估，**其前提
（主 session 空闲即回收）已被上述判别实验证伪**，保留仅供追溯：SKILL ⑥ 明文要求「站点仍 RUNNING ⇒ MUST 让出轮次、等该后台任务的完成/超时通知」——而「让出轮次」正是 trial 1 触发回收的那个动作。后果：voice 比 fan-out 慢时（正是 async 化要救的场景），barrier 会杀掉它正在等的那个后台任务；且杀死后不再产生完成通知（守望任务一并被杀），collect 可能永不返回。按 ⑦「其余一切情形 → 保守 fallback exec-error」尚不至于假绿，但 async 的收益在该路径上归零、甚至劣于同步（白等一场再降级）。注意 design.md:35 与 spec-review-report.md:28/81 所引的既有 spike（660s/跨600000ms/exit0/ppid稳定）与本条不矛盾——那次 spike 的「ppid 全程稳定」说法本身意味着期间有人持续观察（活跃态），从未覆盖空闲态。
> 2026-08-03 状态：VERIFIED → WONTFIX（平台行为（Claude Code harness 子代理轮次终结回收后台任务），非本仓代码可修；已有编排纪律规避（barrier 焊在主 session））

## B9: 200KB 截断按字节切断多字节 UTF-8 字符 → codex 拒收整个 prompt → 该次 voice efficacy=0
> 200KB 截断按字节切断多字节 UTF-8 字符 → codex 拒收整个 prompt → 该次 voice efficacy=0

**关联文档**：`openspec/changes/async-outside-voice/design.md`

**现象**：跑 code-voice 时 codex 报 `Failed to read prompt from stdin: input is not valid UTF-8 (invalid byte at offset 107475)`，rc=1 → exec-error → 降级同族 fallback，跨模型第二意见丢失。context 文件本身是合法 UTF-8（已验），stderr 同时有 OV_TRUNCATED=true。

**根因**：`render_prompt()` 按字节截断 200KB 时直接切在多字节 UTF-8 字符中间，产出非法 UTF-8 序列。

**修复方案**：
- `utf8_head_trim()` / `utf8_tail_skip()` 两个回扫函数，截断点退到最近的 UTF-8 字符边界
- 回扫不可用时 fail-loud exit 1（不兜底成按字节切）

**影响范围**：outside-voice.sh 的 `render_prompt()` 截断路径；修复后 260KB 真实中文 context 截断产出严格合法 UTF-8
> 2026-08-03 状态：VERIFIED → FIXED（change fix-mechanical-layer-silent-failures 归档（2026-07-19），utf8_head_trim/utf8_tail_skip 回扫函数 + 260KB 中文实测）

## B10: helper 被 SIGTERM 回收时 runner 子进程 reparent 到 PID1 存活，脱离 harness 回收域跑满内层超时
> helper 被 SIGTERM 回收时 runner 子进程 reparent 到 PID1 存活，脱离 harness 回收域跑满内层超时

**关联文档**：`openspec/changes/async-outside-voice/design.md`

**现象**：对抗镜实测：outside-voice.sh 被 SIGTERM 后 EXIT trap 清掉 workdir，但 `timeout -k 10 <T> claude -p …` 子进程存活并 reparent 到 PID 1（实测 `39014 1 timeout -k 10 60 sleep 45`，父 shell 已死）。

**根因**：旧版 trap EXIT 只清 workdir 不杀子进程；runner 进程在父 shell 死后 reparent 到 PID 1，脱离 harness 回收域。

**修复方案**：
- `ov_cleanup()` 先 TERM、宽限 ~1s、再 KILL 兜底
- `_ov_group_kill_decision()` + `_ov_pgid_of()` 组级 KILL 守卫（D2.1），利用 timeout 既有独立进程组穿透子树
- runner 改后台执行 + 记 PID + wait，使 trap 有 PID 可杀

**影响范围**：主路径已修。残余 4 个 shell 层不可消除的窗口已诚实登记：(a) SIGKILL 时 trap 不执行；(b) `&` 与 `$!` 之间信号窗口；(c) wait 返回与 PID 清零之间信号窗口；(d*) 高频混合信号风暴整体击穿 trap 机制
> 2026-08-03 状态：VERIFIED → FIXED（change fix-mechanical-layer-silent-failures 归档（2026-07-19），ov_cleanup 先 TERM 后 KILL + 进程组穿透；残余 4 窗口已诚实登记）

## B12: 版本偏斜下 reindex 拿残缺集合覆盖权威 INDEX 且 exit 0（写盘丢数据，血半径大于 sweep）
> 版本偏斜下 reindex 拿残缺集合覆盖权威 INDEX 且 exit 0（写盘丢数据，血半径大于 sweep）

**关联文档**：`openspec/changes/fix-mechanical-layer-silent-failures/proposal.md`

**现象**：scratch 副本实跑运行 checkout 的旧 issues.py reindex：stderr 连报『块有 T153/T156/T162/T163 但缺总览表行』，stdout『已重建 INDEX.md（open 108 项，已闭合 51 项）』，exit=0。对比重建前后：已闭合计数 57→51，B9/B10/B11 在重建后的 INDEX 中全部消失。根因同 B11（issues.py 按自身文件位置定位 sibling，运行 checkout 的 buglist.py 是前 canonical/overlay 版，grep -c overlay 开发版 7 / 运行版 0），但 reindex 会写盘，故危害高于 sweep 的『只是不干活』。同一取数路径 read_pool→_scan_pool 亦被 batch rename / batch add / set-status / lint 共用。

**根因**：`_reindex_core` 写盘前未校验新 INDEX 项数 ≥ 旧 INDEX 项数；版本偏斜下旧 `issues.py` 的 `_scan_pool` 取数路径只扫到部分池文件，产出残缺集合后直接覆盖写盘，exit 0。

**修复方案**：
- `_reindex_core` 写盘前调用 `_count_index_items`（两段式解析：open 行 + closed 聚合行 N），新 < 旧 → raise `ReindexStageError`，INDEX 不覆盖
- 旧 INDEX 格式损坏 → 返回 0 + 跳过校验 + 记 problem 警告

**影响范围**：reindex 写盘路径；sweep 间接受益（sweep 调 reindex）

> 2026-08-03 状态：PROPOSED → FIXED（change harden-issues-read-write 已归档（2026-08-02），_reindex_core 写盘前 count guard + 6 测试用例（verify-report Task 2））
