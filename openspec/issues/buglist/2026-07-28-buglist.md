## B23: Windows(GBK) 下 Python 脚本 print emoji 崩溃：setup.sh 四道一致性门在打印成功消息时自爆，被判成「有漂移」的假红
> Windows(GBK) 下 Python 脚本 print emoji 崩溃：setup.sh 四道一致性门在打印成功消息时自爆，被判成「有漂移」的假红

**现象**：中文 Windows 上 sys.stdout 编码取自 locale = cp936(GBK)，仓内脚本输出的 ✅⇒🔴⚠ 等字符 GBK 编不出 → UnicodeEncodeError。**实测（mac 上以 PYTHONIOENCODING=gbk 模拟，2026-07-28）**：`PYTHONIOENCODING=gbk bash setup.sh` 产生 4 次 UnicodeEncodeError，sync_principles / gen_workflow_guide / check_async_branch_parity / check_tier_resolution_parity **四道门全部假红**——它们的内容其实一致，但崩在打印成功消息那一行（如 `print(f"[sync_principles] ✅ {len(targets())} 个投放面全部与真相源一致")`），非零退出码被 setup.sh 的 `if ! python3 ...` 判成门失败，于是报「四条通则有漂移，修：--apply」。setup.sh 自身退出码仍是 0、软链安装与 ~/.sdflow/ 铺设均正常（bash 侧不受影响，set -e 也未触发——四道门都在 if 条件里）。init.py 的 init/update 模式同样会崩在 `print(f"✓ sdflow-init {mode} 完成")`（代码确证，retire-hooks 模式不走该分支）。触发条件：Python 3.6+ 在真实 Windows 控制台走 Unicode API(PEP 528) 不崩，**崩的是 stdout 被管道捕获时**——Git Bash(mintty) 与 agent 的 Bash 工具捕获输出正是管道，故对 agent 调用路径 100% 命中。

**根因**：① 输出侧：脚本未固定 stdout/stderr 编码，听任 locale 决定；全仓 .py 含 39 种 GBK 编不出的字符（⇒959次 · 🔴177 · ⚠122 · ⭐87 · ✅53 · ↔19 · ⊆18 · 🔒15 · ✓14 · ❌13 …）。② 这些字符大量出现在**成功路径**的消息里，于是「打印成功」= 「进程失败」，把崩溃翻译成了门禁的假红——危害方向是 fail-closed 的假红而非放行，但会训练用户忽略这四道门，真漂移时也不再被信任。③ 另有两片同源暴露面：subprocess text=True 未指定 encoding（18 处/13 文件，读 git 中文 commit message 会 UnicodeDecodeError）、write_text 未指定 encoding（2 处，产出 GBK 文件，下次 UTF-8 读乱码，比崩更隐蔽）。

**修复方案**：
- A. 每个 entry-point 脚本顶部内联 4 行 stdout/stderr 自愈：`for _s in (sys.stdout, sys.stderr): try: _s.reconfigure(encoding="utf-8", errors="replace") except Exception: pass`（~19 个脚本；跨 skill 不能共享模块——skill 是独立分发单元，与四条通则托管块同构：内联 + 脚本守）
- B. 18 处 subprocess text=True 补 encoding="utf-8", errors="replace"（ship_gate.py / init.py / issues.py / impl_route.py / outside-voice-job.py / retro_report.py / devenv_scaffold.py / trivial_shape.py / ff0-branch-guard.py / migrate_legacy.py / roadmap_writeback_draft.py / sdflow_issues_core 等）
- C. 2 处 write_text 补 encoding="utf-8"（devenv_scaffold.py:59、hack/check_codex_efficacy_evidence.py:418）
- D. 新增 hack/check_encoding_hygiene.py 进 setup.sh，与现有四道门并列——没机械守就会漂，新脚本必然忘记加 A 的那 4 行（面治，非点补）
- E. .github/workflows/windows-recorder-smoke.yml 注入 PYTHONIOENCODING=gbk 跑一遍全门，并把 paths: 从现在 3 条扩到被改脚本

**影响范围**：Windows 全平台：四道机械一致性门 100% 失效且撒谎（假红）、init.py 铺设看起来失败、读中文 commit message 的脚本解码崩。mac/Linux 无影响（reconfigure 幂等）。

**已否掉的备选（附理由）**：① PYTHONUTF8=1 —— 实测被 PYTHONIOENCODING 覆盖（中文用户常设 =gbk）；且主调用路径是 SKILL.md 指示 agent 直接跑 `python3 xxx.py`，**没有调用侧可控点**，环境变量方案只能靠「每条命令记得加前缀」= 指令层约束非机械门。② 把 ✅ 换成 [OK] —— 点补：39 种字符散在 19 个脚本，且下一个新脚本还会打 emoji（除非有 D 的门守着）。实测四组合（PYTHONIOENCODING=gbk 模拟）：裸脚本✗ / PYTHONUTF8=1✗ / PYTHONIOENCODING=utf-8✓ / 脚本内 reconfigure✓——只有 reconfigure 在任何先前设定下都赢（它最后执行、覆盖一切）。

**诚实边界**：以上均为 mac 上 PYTHONIOENCODING=gbk 的等价模拟。现成 Windows CI(windows-latest) 默认 locale 是 en-US/cp1252，**不注入 GBK 就复现不了本 bug**。真 Windows 行为必须由 runner 判（参照 mlh-p6 T154：本地 mac 照不到、push 才抓到）。

**建议**：范围已量化完整，建议开独立 change（拟名 fix-windows-encoding-crash）走流程，勿点补。
