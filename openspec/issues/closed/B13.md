## B13: outside-voice.sh 失败通道绕过出境 secret_scan（三洞并存）
> outside-voice.sh 失败通道绕过出境 secret_scan（三洞并存）

**关联文档**：`openspec/changes/fix-mechanical-layer-silent-failures/design.md`

**现象**：代码审两个独立跨模型 voice + 一个对抗镜均判 critical/high，三洞同族：
(1) 失败诊断分支未扫描直出——rc≠0 分支 head -3 last-message.md、last-message 为空分支 tail -5 cli.log + tail -5 stderr.log 全部绕过 secret_scan（后者仅在 rc=0 成功路径执行）。runner 非零退出/空输出是常见场景（超时边缘、prompt 被拒收），头部注释「回传含密钥即拒发」的承诺在这两条分支上不成立。现有测试甚至锁定了原始 stderr 转发行为（test_outside_voice.py:249 与 :623）。
(2) secret_scan 自身 fail-open——grep 置于无 pipefail 的管道首端且吞错误，grep 不可用 / IO 失败 / 权限竞态均表现为空结果，函数随后返回成功，context 继续出境。应区分 0=命中 / 1=无命中 / >1=扫描失败，扫描失败必须 fail-closed。
(3) 扫描对象与发送对象非同一快照（换文件 TOCTOU）——context 在 secret_scan 后又被 wc/head/tail/cat 重新打开；扫描后替换路径可使未扫描内容进入 prompt，do_exec 的预扫同样不封闭该窗口。建议先复制进权限受控 workdir，只扫描/渲染该私有快照。

**根因**：三洞成因**各不相同**，不是一个 bug 的三种表现——分治，别指望一处修法覆盖三条。

**先厘清 `secret_scan` 的两个方向**（三洞的归属靠它区分）：
- **入境**（`:352` `do_exec` 预扫、`:610` `render_prompt`）：送出去之前扫 context，防「把自己的密钥喂给外部模型」。
- **出境**（`:689`）：runner 回传的内容落到操作者手里之前扫一遍。
  **出境为什么必须存在**：runner 持有**整仓只读权限**（codex `-C <repo_root> -s read-only`；claude `--tools Read,Grep,Glob`），
  脚本头部注释自陈「`--add-dir` 是增量授权提示、**非**访问围栏（Read 无它也读全盘）∴ 出境侧 `secret_scan` 兜底」
  ⇒ 它读得到 `.env`/密钥，并可能**原样引用在自己的 findings 里**回传。出境扫描是拦这个的最后一道。

**洞(1) 根因 = 扫描点挂错了位置：出境扫描只挂在成功路径上。**
`:672`（rc=124 超时）、`:674`（rc≠0）、`:676`（`head -3 last-message.md`）、`:685`（`tail -5 cli.log` + `tail -5 stderr.log`）
四处 dump 全部先于、且绕过 `:689` 的出境扫描。而 **runner 非零退出 / 空输出恰恰是常见场景**（超时边缘、prompt 被拒收），
∴ 承诺「回传含密钥即拒发」在最常走的几条分支上不成立。
🔴 **注意 `:684` 的既有注释论证**（「`stderr.log` 是 runner 自身的 stderr（非 context 正文）…无新增出境面」）：
该论证**对 `stderr.log` 站得住**，但**盖不住 `:676` 的 `last-message.md` 与 `:685` 的 `cli.log`**——
那两个是 **runner 的产出**，正是 `:689` 出境扫描存在的理由。修复时 MUST 区分这两类，别被那条注释误导成「已论证过、无需处理」。

**洞(2) 根因 = 检测器自身 fail-open，与本 change 所治的 `od` bug 同形。**
`lines=$(grep -nE -- "$pattern" "$file" 2>/dev/null | head -3 | cut ...)` —— `grep` 位于**无 `pipefail` 的管道首端**且 stderr 被吞。
`grep` 缺失 / IO 失败 / 权限竞态 **全部表现为「没匹配到」**（`lines` 为空）⇒ 循环走完 `hit=false` ⇒ `return 0` 放行。
**「扫不动」与「扫过了、干净」在外部不可区分**——这正是本 change 主题（exit 0 但事情没做成）在安全面上的实例。

**洞(3) 根因 = 扫描与发送是对同一路径的两次独立 open（TOCTOU）。**
`secret_scan "$ctx"` 之后，`$ctx` 又被 `wc -c`（取大小）、`head -c`/`tail -c`（截断）或 `cat`（非截断）**重新打开**。
两次 open 之间替换该路径的内容/符号链接，进 prompt 的就是**从未被扫过**的字节。`do_exec` 的预扫是**同一路径的又一次 open**，
∴ 它不封闭该窗口、只是多扫了一遍旧快照。

**共同的可推广教训**：安全门的三个失效面是**位置**（挂在哪条路径上）、**自身可靠性**（检测器失败时倒向哪边）、
**对象同一性**（检查的和使用的是不是同一份数据）。本条三洞恰好各占一个，可作为后续安全门评审的检查表。

**修复方案**：
(1) 两条失败 dump 分支前置 secret_scan，未过则替换为「已拒发（secret-hit）」占位而非原文；最稳妥是失败时只输出结构化错误+字节数+哈希。(2) 单独捕获 grep 退出码并对 >1 fail-closed，补 grep 缺失/读取中断/权限变化测试。(3) 复制 context 进受控 workdir 后只扫描并渲染该私有快照，render-prompt 独立路径同策略。

**影响范围**：凭证可经 helper 的失败通道外泄到 stderr（该通道未过出境扫描），且被后台任务输出文件持久化。归属：三洞均为既有缺口、非 fix-mechanical-layer-silent-failures 引入；该 change 的 Non-Goal 明写「不改出境侧扫描」故 defer 不 fold，但须在 hand-off 点名。
