## T256: 用 PreCompact hook 把「只活在对话里」的易失状态落盘，让上下文压缩随时发生都无害（先答清单问题再决定做不做）
> 用 PreCompact hook 把「只活在对话里」的易失状态落盘，让上下文压缩随时发生都无害（先答清单问题再决定做不做）

**动机**：调研结论(Claude Code 2.1.220 实测四面核实)：**不存在任何脚本可达的 compact 入口**——工具面 ToolSearch 零命中、claude --help 无相关 flag、子命令无、settings/env 无 autoCompact 旋钮(唯一一处 compact 是转轮提示语 Use /compact at ~50% context)。∴「在 sdflow-done 前自动 compact」做不到；hook 也只能拦(permissionDecision)或注入文本(additionalContext)，拦=给阶段三加机械强制人类门，撞 P3e 且比被守对象更难绕。⇒ 正确方向是反过来：不控制压缩时机，而是让任意时刻的压缩无害。真实风险点是 ship 熔断快照——SKILL 明写 fail-safe:快照缺失(如 context 压缩丢失上一次记录)保守判无进展 ⇒ 压缩若砸在某步重跑中途会造成一次假停机(安全但需人工重启)。

**思路**：① **先答闸门问题**：逐项列出阶段三里「只活在对话、盘上没有」的状态。已知候选只有两个——(a) ship 熔断快照(单 invocation 内持有)；(b) merge 意图(从用户调用语透传，RUN_VERIFY→sdflow-done)。② **若答案只有 merge 意图 ⇒ 不做这个 hook**，直接在 ship 摘要里提示一句更便宜。③ 若熔断快照也算，再评估 PreCompact hook 落盘 vs 既有 fail-safe 是否值得——注意 T26「熔断重试计数脚本化(gate 零副作用约束下的计数下沉)」已探索并结项为撞红线不做，本条 MUST 先读那份结论，别重走。

**备注**：非 change 来源：由 harden-implement-review-loop 设计门后的一次 compact 时机讨论引出，不属该 change 交付范围。⚠️ hook 装在 ~/.claude/settings.json 是**全局命名空间**，对本机所有项目生效——这是本条最大的隐性代价，评估时 MUST 计入。对照 CLAUDE.md G4/G5：本仓既有取向是 hook 仅作警告安全网、不驱动流程逻辑；状态 dump 属前者还是后者需先判定。

**2026-08-12 调研记录**（wco-p5 相位 B 拷问中完成；人拍板「本 change 不做、先记录」）：

- **闸门问题答案（不变）**：阶段三「只活在对话里」的状态清单核清 = 仅两项——
  (a) ship 熔断快照：持久化已结项否决（撞三红线，`sdflow-ship/SKILL.md:170` 明文 + fail-safe
  快照缺失保守判无进展，最坏一次安全假停机）；(b) merge 意图（`sdflow-ship/SKILL.md:162`
  从调用语透传，透传前纯对话态）。
- **宿主不对称（本条继续 OPEN 的核心理由，人 2026-08-12 指出）**：Claude Code 本机 1M
  context ⇒ 压缩概率低、需求不迫切；**Codex 上限 400K、可用约 258K，auto-compact 在
  ~90% 阈值自动触发（v0.100.0+ 用户阈值被钳到 90%）** ⇒ ship 长运行中途压缩是现实概率，
  不能以当前仓（Claude 为主）的状态判死本条。
- **新事实：Codex CLI 已有 Claude-style hooks 引擎**（本条原文写作时只针对 Claude Code）：
  事件表含 `SessionStart / UserPromptSubmit / PreToolUse / PostToolUse / PermissionRequest /
  PreCompact / PostCompact / SubagentStart / SubagentStop / Stop`；配置经 `hooks.json` 或
  config 层旁的 `[hooks]` TOML 表；root session 压缩后 `SessionStart(source:"compact")`
  会在下一次模型请求前跑（含 turn 中途 auto-compact）。⇒ **PreCompact 落盘在双宿主都有
  机械落点**。本机 codex-cli 0.147.0 实测有 hooks 面（`--dangerously-bypass-hook-trust`）。
  另：Codex 压缩后自动回读最多 5 个近编辑文件（50K token 预算）——「状态在盘上」的设计
  在 Codex 侧有原生恢复通道加持。
  来源：developers.openai.com/codex/hooks、developers.openai.com/codex/config-advanced、
  getunblocked.com/blog/codex-context-window、codex.danielvaughan.com（2026-03/04 hooks 与
  compaction 架构文）。
- **未来 change 的推荐方向（按优先序）**：① **merge 意图落盘化**（ship 起手把 opt-out 意图
  写进盘上标记，done 从盘读）——零 hook、零全局命名空间代价、双宿主同构，直接消灭最后
  一项对话态，优于任何 PreCompact 方案；② 若 ① 后仍要保熔断快照跨压缩存活，再评估
  PreCompact dump——注意它本质是跨 invocation 持久化，大概率仍撞 T26 时代的三红线，
  且 Claude 侧 hook 装 `~/.claude/settings.json` 全局生效的代价不变（Codex 侧 hooks 可随
  config 层放置，全局代价待核）。
