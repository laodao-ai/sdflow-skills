## 需求与目标态

### 痛点

1. **改进闭环决策端欠账**：13 面镜出现轮数 ≥10 触发 retro「待复评」阈值，但复评从未执行；
   砍留所需的两个判据（token 维度量 T104、实修率指标 T108）至今 open——数据采了、决策没做。
2. **四条 P0 优化被批量错关**：T98/T99/T101/T102 以「wco roadmap P0-P5 全交付」为由关闭
   WONTDO（`resolved_by: null`），但 wco 实际里程碑不含这四项，其中三条（T101 摘要头、
   T102 对抗镜措辞、T98 前缀缓存）在 2026-08 业界调研中拿到官方/文献直接背书。
3. **置信过滤的地基被文献动摇**：code-review 的 <80 硬滤建立在镜自报置信上，而 LLM judge
   自报置信被证明系统性高估正确性（arXiv 2508.06225）。
4. **上游套件吸收无锚无跟踪**（用户点名）：gstack / superpowers / matt 套件 / OpenSpec CLI
   四个上游源的吸收全是一次性快照（调研详解冻结在 2026-07），无「上次吸收到哪」的锚
   ⇒ delta 不可得 ⇒ 实证结果是从不重看；T264/T245/T246/T267 是该缺口的散点症状。
5. **在池优化项的优先序建立在过期条件上**：宿主已原生支持 per-agent effort 分档
   （T105/T103 实现成本降一个量级）、上游演进加速（T264 概率项变大），池内优先级未反映。

### 目标态判据

- retro 报告的「待复评」区块清空或全部带人工处置记录（保留/降采样/淘汰，逐镜有据）。
- retro 能输出 per-镜实修率（历史存量回算）与 per-change token 维（新 change 起累积）。
- T98/T99/T101/T102 四条的关闭理由与事实一致（重分诊后无论去留，理由可复核）。
- 存在一个可重复运行的上游 watch 机制：四源各有版本锚，运行一次能产出「锚点以来的
  delta 分诊报告」，采纳项入 issues 池。
- 裁决协议不再把自报置信当唯一硬门（二元裁决 + critique / severity 分级 / validator 复核，
  具体形态由实施 change 的设计定，但「裸 <80 硬滤」不再是终态）。
- 在池优化项（T105/T103/T124/T98 等）到阶段 4 frontier 时，其排期依据反映实测 token
  基线与宿主现状，而非本文写作时的过期估计（占位判据，验收细节随阶段 4 补细）。

### 验收门槛

| 验收项 | 门槛 |
|---|---|
| 镜复评 | 13 面待复评镜逐一有处置决定 + 依据（实修率/独立率/token 成本三数齐） |
| 度量补全 | retro 再生报告含实修率列 + 可判定/未知/覆盖率三数注记；token 快照锚的采集路径确认为机械捕获，或如实标注自报可信等级 |
| 池对账 | 四条错关项重开→重分诊完成，`closed_reason` 与实际交付对得上 |
| 上游 watch | 对四源各跑通一次 delta 收集 + 一份分诊报告落盘 |
| 裁决改造 | 评审 SKILL 的置信硬滤条款被替代方案取代，且 anchor_lint/度量锚兼容 |

### Non-Goals

- **评审编排层重做（Workflow 原语化 / Stop hook 下沉）** — 可证伪假设：若下次必须动评审
  编排（如多镜结构大改）或 Codex 宿主也获得等价编排原语，此排除失效，届时按「条件已
  变化」记录（见决策 4）重估。
- **推倒任何架构柱子**（冷上下文独立评审、子代理隔离、静态分档、人类门上移、机械活交
  脚本）— 可证伪假设：若 retro 数据显示某柱子的收益消失（如冷层连续多轮零独立产出），
  才重议；当前全部有外部背书 + 本仓实证。
- **grill 相位与冷层独立审的任何缩减** — 可证伪假设：文献出现「spec-vs-intent 漂移可
  机械化检测」的可行机制时重议；当前文献结论恰相反。
- **平台基线重校（Fable 5）** — 可证伪假设：Fable 5 时代 retro 样本 ≥10 change 后启动；
  当前样本不足，重校无据。

### 显式假设

- **A1 实修率历史回算存在可判定样本**：假设归档报告中有足量「finding→修复 commit」可
  无歧义 join 的样本。若覆盖率过低，实修率对该镜降级为参考信号，砍留改以独立率 + 人工
  复核为准（阶段 2 前置条件含此闸）。失效后果：复评仍可做，但判据从三数降为两数。
- **A2 token 度量存在机械采集路径**：假设 hook（Stop/PreCompact 类）可读 transcript 的
  usage 字段做 checkpoint 级机械捕获。已知边界：wco P2 已确认 harness 无 per-子代理
  token ⇒ **逐镜 token 大概率只有自报级可信度**（本仓教训：自报 ≠ 机械捕获）。若机械
  路径不成立，token 列 MUST 标注自报可信等级，MUST NOT 冒充机械锚；采集机制在 p1 实施
  change 的设计相位定案。
- **A3 recorder 可安全扩展 reopen**：`issues_v2.py` 现行契约拒绝修改 `closed/` 中的
  issue（终态不可再改）⇒「重开四条错关项」依赖新增 `reopen` 命令（closed→open 原子
  迁移 + 终态字段清理 + 历史追加 + reindex）。假设该扩展不破坏既有契约测试；它是
  1.A.1 的机械前置，MUST NOT 手工搬文件绕过。

## 1. 架构概览

本 roadmap 不新建运行时系统，改动集中在三个既有面 + 一个新面：

```
既有面：
  retro 管线      sdflow-retro/scripts/*  ──┐
  评审编排        sdflow-{spec,code}-review/SKILL.md ──┤ 阶段 1-2（度量→复评→裁决）
  issues 池       openspec/issues/*       ──┘ 阶段 1（池对账）

新面：
  上游 watch      新 skill（暂名 sdflow-upstream-watch，实施 change 定名）
                  锚文件 openspec/upstream/anchors.yaml（格式实施时定）── 阶段 3
```

## 2. 架构决策

### 决策 1：复评前先补判据（度量 → 复评的硬先后序）

**决策**：阶段 1 先落 T104（token 维）+ T108（实修率），阶段 2 才做镜 roster 复评拍板。

**替代方案**：
- **A. 直接凭现有独立率/采纳率拍板砍镜** → 20260717 快照已判「只能拍感受」；独立率
  跨轮 dedup 尺度不保证同口径（retro 报告自注），单指标拍板误杀风险高。
- **B. 再攒数据不动** → 数据阈值已触发一年量级，继续攒是决策端欠账的延续。

**选择理由**：
- 实修率可对历史存量回算（retro join 修复 commit，覆盖率见假设 A1），不必等新数据——
  阶段 1 交付即解锁阶段 2。
- token 维只能从新 change 起累积，越晚开始盲区越长。

**三镜代价**：系统镜——retro 脚本单点改动、报告列删除即回滚，可回退性好；用户镜——
报告多两列，读表成本微增；开发循环镜——判据一次补齐后，所有后续砍留决策免于重复的
「拍感受」争论。**主次判定**：开发循环镜为主——判据缺失正是决策端欠账的根因。

### 决策 2：裁决地基改造与复评同 change（阶段 2 一体交付）

**决策**：T106（裁决二元化 + critique）+ T112（弱档 validator 复核）与 roster 复评放同一个
change；severity 三级输出作为 T106 的候选实现形态之一，由该 change 的设计相位定。

**替代方案**：
- **A. 复评与裁决改造分两个 change** → 两者都改评审 SKILL 的 Step3 裁决段，拆开 = 同一
  文件面两轮完整流程成本（违反「一个 change 一个完整阶段结果」）。
- **B. 维持 <80 硬滤不动** → 地基被 arXiv 2508.06225 动摇（自报置信系统性 overconfident），
  跨模型豁免通道已经是补丁之上的补丁。

**选择理由**：
- 复评（改 roster）与裁决改造（改过滤协议）是同片一致性面，面治优先于点补。
- 护栏内置：冷层（冷主审 / 冷全 diff）不在砍单——本仓两条实证（sdflow-retro 致命 F1 由
  冷主审独家挖出；harden-gate 4 条跨 ticket 缺口唯冷层抓到）。
- **归因与回滚隔离**：同 change 但 roster 改动与裁决协议改动落**独立 commit、可分别
  revert**；dogfood 观察按预定义指标分别判读（漏检看 roster、噪声/采纳率看裁决协议），
  MUST NOT 一轮混判后整体撤销。

**三镜代价**：系统镜——同 change 改同一 SKILL 面避免两轮 merge 冲突，耦合升高以独立
commit 缓解；用户镜——评审报告形态变化一次到位，免两次适应；开发循环镜——省一轮完整
流程固定成本（本仓实测流程固定成本高）。**主次判定**：开发循环镜为主。

### 决策 3：上游吸收走「统一 watch 机制」（新数据类 skill），不并入 maintain、不维持手动

**决策**：新建轻量数据类 skill（暂名 `sdflow-upstream-watch`）：机械层脚本维护四源版本锚
（gstack=skill 目录+数据仓 git、superpowers=官方插件 cache、matt=GitHub mattpocock/skills、
OpenSpec=npm 版本+schema fork）并收集锚点以来 delta；模型层分诊「与本仓同类面对照」的
可吸收项；人拍板后入 issues 池。

**替代方案**：
- **A. 并入 sdflow-maintain** → maintain 的域是 openspec 目录一致性（INDEX 对账、扫描器），
  上游 watch 是外部源监视，混域会让两边的触发语义都变糊。
- **B. 维持手动定期全量重看** → 实证是「从不重看」：三套件调研详解全部冻结在 2026-07，
  无锚 ⇒ 每次重看都是全量成本。
- **C. 只做 OpenSpec 一源（T264）** → 四源失效模式同构（快照式吸收 + 上游持续演进），
  只修一源是点补；且用户点名的是三套件。

**选择理由**：
- 吸收 ROI 已被三次一次性吸收验证（absorb-gstack-autoplan / absorb-gstack-review /
  matt-workflow-integration 全部 SHIPPED 且有实证收益）。
- 「机械活交脚本、判断归模型」完全适配：锚与 delta 收集有确定性信号，「何为精华」没有
  （诚实边界，合法残余，人拍板收口）。
- 一个机制统一吸掉 T264/T245/T246/T267 四条散点 todo。

**三镜代价**：系统镜——新 skill 零侵入既有 skill，锚文件独立、整体可移除；用户镜——
新增一个触发入口，学习成本一条命令；开发循环镜——「全量重看」变增量 delta，分诊结果
复用 recorder 入池路径。**主次判定**：开发循环镜为主——机制的全部价值在压低重看的
边际成本。

### 决策 4：评审编排大改本轮不做，只落「条件已变化」记录

**决策**：Workflow 确定性编排原语与 Stop hook 四级 gate 阶梯的可用性以 todo 形式入池，
绑定触发条件「下次评审编排必须动刀时一并重估」；本 roadmap 不含任何编排重构阶段。

**替代方案**：
- **A. 本轮直接做编排 Workflow 化** → Codex 宿主无该原语 ⇒ 双路径双维护；且这是分诊
  roadmap 明确延后的设计级重构，塞进优化批次违反其「大块延后」原则。

**选择理由**：
- 收益真实（控制流机械化 + schema 消灭输出格式漂移面）但不紧迫；条件记录的成本趋近零，
  丢失该信息的成本（下次动刀时重新发现）不为零。

**三镜代价**：系统镜——不做即不引入 Claude/Codex 双路径维护面；用户镜——评审行为
不变，无感；开发循环镜——记录一条 todo 的成本趋零、避免未来重复发现。**主次判定**：
系统镜为主——双路径维护是该方向当前最大的代价源。

### 决策 5：错关四条走「重开 + 逐条五问重分诊」，不照单全做

**决策**：T98/T99/T101/T102 重开后逐条重分诊（五问：根因/概率/影响/完美成本/简化方案），
结论可以仍是 WONTDO，但理由必须与事实一致、可复核。

**替代方案**：
- **A. 视为已背书直接全部排期实施** → 背书只说明「方向被认可」，不等于每条在本仓的
  概率×影响都过立项线（如 T99 存在「评审对象是 change、CI 绿否是仓级信号」的粒度错位，
  需分诊时正面回答）。
- **B. 维持关闭状态** → 关闭理由与事实不符，是数据完整性缺陷；且 T101 直击设计审 25%
  墙钟的人读主导段，T102 是官方点名解法，静默维持等于放弃已验证的收益。

**选择理由**：分诊是本仓 issues 池的既有纪律；错的是理由不是流程，修理由、走流程。

**三镜代价**：系统镜——重分诊不改代码，池一致性由 reopen 命令机械保证（假设 A3）；
用户镜——人只需对四条各拍一次板；开发循环镜——理由归真让未来所有分诊记录恢复可信，
避免「关闭理由不可信 ⇒ 每次都得重查」的持续税。**主次判定**：开发循环镜为主。

## 3. 风险、权衡与回滚

### 3.1 风险清单

| 风险 | 级别 | 缓解 |
|---|---|---|
| **复评误杀**：弱产出镜可能在特定 change 类型上有独家价值（如 history 镜对回归类） | 中 | 复评产出「降采样」选项（按 change 类型条件化）而非只有砍/留二元；冷层明确不在砍单 |
| **实修率回算口径**：修复 commit 与 finding 的 join 可能有歧义（一 commit 修多 finding；历史报告存在多对多聚合，逐 finding→commit 映射不可恢复的样本真实存在） | 中 | T108 实施时定 join 规则；报告 MUST 输出可判定/未知/覆盖率三数；未达最小无歧义样本量的镜，实修率不用于砍留（降级为参考，见假设 A1） |
| **上游 watch 三源异构**：plugin cache 无 git 历史、版本信号弱 | 低 | 每源适配分支 + 拿得到什么锚用什么锚（version 字符串也算）；拿不到锚的源如实报「无锚，全量对比」 |
| **裁决改造与度量锚兼容**：改 Step3 协议可能破坏 lens-metric emitter 输入 schema | 中 | 阶段 2 change 的 tasks 里显式含 emitter 兼容项 + retro 再生冒烟 |

### 3.2 关键权衡（明确接受的代价）

**「何为精华」不机械化**。上游 watch 的分诊层是模型判断 + 人拍板，无确定性信号可依
（与「命中哪些 TG」同类，adr/0018 型残余）。接受理由：机械层（锚、delta 收集）已把
全量重看成本降为增量，判断层的量随 delta 收敛到可人工复核的规模。

**复评可能砍掉未来才显价值的镜**。接受理由：处置记录 + retro 持续再生 = 砍错可逆
（roster 恢复是一行 SKILL 改动），且「待复评」阈值机制仍在，复活后数据继续累积。

### 3.3 回滚与应急

| 故障场景 | 回滚动作 | 预估恢复时长 |
|---|---|---|
| 裁决改造后评审质量下滑（采纳率骤降/漏高危） | 只 revert 裁决协议 commit（与 roster commit 隔离，见决策 2），roster 处置不连带撤销 | <1h |
| roster 砍镜后连续 change 出现该镜领域的漏网 | SKILL roster 行恢复 + task-log 记录复活理由 | <0.5h |
| watch 脚本对某源误报 delta | 该源锚回退到上次正确值（anchors.yaml 单行改动） | <0.5h |

## 4. 已决议档案（Q&A）

### Q1 ✅ 本轮要不要动评审编排架构？

**原问题**：宿主已有 Workflow 确定性编排原语 + schema 强制输出，评审编排的散文控制流
（663/546 行 SKILL）按基准 1 本该机械化，要不要趁本轮做？

**决策**：不做，条件记录入池（决策 4）。

**理由**：Codex 宿主无该原语（双路径成本）；分诊 roadmap 已把编排大改列延后池；收益
不紧迫而记录成本趋零。

### Q2 ✅ 上游 watch 是独立 skill 还是并入既有 skill？

**原问题**：机制落点三选一（新 skill / 并入 maintain / 手动流程）。

**决策**：独立数据类 skill（决策 3）。

**理由**：域独立（外部源监视 ≠ openspec 目录一致性）；机械/判断切分天然适配数据类
skill 的「脚本 owns 一致性、模型 owns 判断」形态；手动路线已被实证证伪。

### Q3 ✅ 复评与裁决地基改造的 change 边界？

**原问题**：一个 change 还是两个？

**决策**：同一个 change（决策 2）。

**理由**：同片一致性面（评审 SKILL Step3），拆开付两轮流程固定成本。
