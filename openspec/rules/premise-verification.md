# 前提验证规则（写断言之前先落地）

> **由来**：2026-07-19，变更 `harden-import-error-file-access` 的设计审与重审。两轮共查出 **12 条致命项**，根因高度一致——**写下一个依赖外部事实的断言时，没有去验证那个事实**。其中第二轮的 2 条致命项是**返工本身引入**的，与第一轮同级、同类：不是迭代收敛，是同一个漏洞换个地方复现。
>
> **适用对象**：AI 助手在本仓库产出 proposal / design / specs / tasks / 评审报告 / impl-report，以及做任何「据此得出结论」的核查时。
>
> **本规则不解决「想得对不对」，解决「想的前提是不是真的」。** 推理强度不是本规则的目标——恰恰相反：**在未验证的前提上加推理，只会产出更自洽、更不像需要复查的错误结论。**

## 0. 为什么这条规则值得单独存在

2026-07-19 那次，设计文档里为一个致命 bug 写下了这样一句辩护：

> ⚠️ 启动期校验会在受限根落入静态根之下时**拒绝启动**——这是**预期行为，不是故障**。

推理链本身无懈可击（fail-closed 优于 fail-open）。但它架在一个没查的前提上（以为目标目录存在），而实际 `filepath.EvalSymlinks` 对不存在的路径直接报错，且该目录是懒创建的 ⇒ **每次全新部署都起不来**，fail-closed 实为 fail-always。

**推理越强，辩护越自洽，越不像需要复查的地方。** 这是本规则要防的核心失效模式。

## 1. 十二条致命项的根因分布（实测数据，非假想）

| 断言 | 依赖的外部事实 | 是否验证 | 验证成本 |
|---|---|---|---|
| 「无任何清理/TTL」 | 清理代码是否覆盖该目录 | ❌ grep 用字面串、代码用常量名 | 一次 `grep -rn 常量名` |
| 「加 `RETURNING id` 即可拿到 id」 | `mdb.Exec` 能否返回结果集 | ❌ | 读 `db.go` 三行 |
| 「路径钉在 binary_dir 即安全」 | 产物目录是否带版本号 | ❌ 没看部署脚本 | `sed -n` 看 `compile.sh` |
| 「列表面加个 OR 分支即可」 | 谁在消费这段谓词字符串 | ❌ | 一次 grep |
| 「6.5 是集成测试」 | 本仓集成层是否起得了 HTTP server | ❌ | 一次 grep |
| 「6.5b 能证明与 CWD 无关」 | 被测的值是否可能变化 | ❌ | 读 `gfile.SelfDir()` 实现 |
| 「启动校验 fail-closed」 | `EvalSymlinks` 对缺失路径的行为 | ❌ | 跑一行 Go |
| 「清理器可以读 DB」 | 调用点与 DB 初始化的时序 | ❌ | 一次 `sed -n` |
| 「孤儿判定安全」 | 文件与 DB 行的写入顺序 | ❌ | 读两行调用 |
| 「e2e 能验静态路径」 | dev proxy 的转发范围 | ❌ | 读 `.umirc.ts` |

**共同点**：每一条的验证成本都是**几十秒**；每一条的漏检代价都是**一条会上线的致命缺陷**。

## 2. 五条硬性规则

### 规则 1：落笔前先证伪

每写一条「X MUST 成立」或「测试 Y 能证明 Z」，**先问**：

> **最便宜的、能证明它是假的实验是什么？**

然后**跑那个实验**。跑不了就明确标注「未验证」，MUST NOT 以肯定语气写进文档。

❌ 「断言受限根在不同 CWD 下解析到同一路径」——没问「这个值有可能不一样吗」
✅ 先读 `gfile.SelfDir()`：发现它在包 `init()` 里算一次并常驻 ⇒ 该断言恒绿、是假锚 ⇒ 换判据

### 规则 2：引用即打开

文档里每一个 `file:line`、每一个函数签名、每一个配置键，**MUST 是本次真的打开过的**，不是「我记得它写着」。

> 判据：2026-07-19 第一轮接地核验 90 项中 5 项不符——**凭记忆写引用的指纹**。

### 规则 3：改共享物先溯源

动任何**被多处消费**的东西（常量、SQL 谓词、字符串字面量、配置键、函数签名）之前，**先 grep 谁在用它**。

> 实例：把 owner 分支插进列表面谓词，会打断 `test/guards/import_logs_model_gate_guard_test.go` 里一整段连续字面量的 `strings.Contains` 匹配 ⇒ 4 个既有测试全红。而变红时最省事的修法（放宽断言）会**静默阉割掉上个变更专为防回归建的守卫**。

### 规则 4：决策落文档前先验证其依赖事实 🔴

**本条是 2026-07-19 第二轮返工的直接对策，也是此前工作流的空白。**

在对话中拍板的决策，**MUST NOT 直接写进文档**。落笔前 MUST：

1. 列出该决策依赖哪几条**外部事实**；
2. 逐条验证；
3. 再落笔。

> **为什么单列**：原始设计好歹要过 ff → grill → 设计审三道；而「对话里拍板 → 当场落文档 → commit」这条路径**零验证**。2026-07-19 的六项决策全走这条路，结果第二轮引入的致命项与第一轮同级同类。
>
> 实测：那六项决策依赖的事实里，只要查四条（TTL 覆盖范围 / `EvalSymlinks` 语义 / 部署布局 / 调用时序与写入顺序），**第二轮的两条致命项当场消失**。

### 规则 5：「已清除 / 已一致」必须正反双向验证

任何形如「旧写法已全部替换」「N 处已同步」的结论，MUST **同时**做：

- **正向**：新写法在**每个**目标文件里命中 ≥1；
- **反向**：旧写法命中 = 0。

**只做反向、看到 0 就宣布一致 = 假绿**——一个从未命中过新写法的文件会完全隐形。

> 实例：`grep -c 'OR user_id = ${user_id}'` 返 0，据此报告「全仓已无残留」并 commit（message 写「谓词三处同步」）。实际**只同步了两处**，且那个 0 是假的——`$` 被正则当锚点，模式恒不匹配。含 `${...}` 的模式 **MUST 用 `grep -F`**。
>
> 漏掉的那一处是**列表面的权威规范**，携带一个已被否决的不安全方案——后来者照它核对实现，会把安全收窄「纠正」回去。

## 3. 与既有规则的关系

- `openspec/rules/task-completion-verification-convention.md` 管**做完之后怎么证明做完了**；本规则管**做之前前提对不对**。二者互补，不重叠。
- `openspec/rules/destructive-commands.md` 同为「由一次真实事故固化的教训」体例。

## 4. 诚实边界

本规则**挡不住**「我以为我验证了」——它是纪律，不是机械门。可机械化的部分只有规则 5（正反双向计数可写成脚本）与规则 2 的一部分（接地核验可由独立镜执行）。

规则 1、3、4 依赖执行者的自觉。**其有效性的唯一证据是：下一轮评审的致命项是否变少、变小、且类型不同于上一轮。** 若下一轮仍出现同级同类的致命项，说明本规则未被执行，而非本规则无效。
