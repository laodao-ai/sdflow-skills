# 泳道推导框架（`testing-framework.md` 槽③④ 的附属）

> **⚠️ 定位：这不是一个平行的核心组件。** 它专答 [`testing-framework.md`](./testing-framework.md) 六槽里的 **③（怎么跑）** 和 **④（要配什么）**。
> **泳道不是一个独立的设计对象——它是槽③④的答案落成的形状。**
>
> **固化「问什么」，不固化「答什么」**：**维度**（形态四问 · 阶梯原理）固化，保证推导路径可复现；**答案**（用哪个库 / 哪个容器方案）**交模型现场调研 + 人决策**——工具随生态演进，固化即腐烂，而模型的知识面本就比静态表广。

---

## 1. 按**依赖形态**分格，不按语言分

**按语言分格（Go 格 / Node 格 / Python 格）是错的**——泳道结构不由语言决定，由**系统与外界的边界形态**决定。

> 同样是 Go：连 broker 的服务，与纯算法库，泳道结构完全不同。
> 而 Go 服务与 Java 服务连同一个 broker，**泳道结构几乎一样**。

**形态四问**（答案基本可从 SAD §3「外边界」读出）：

1. 有无**外部有状态依赖**？（broker / DB / 队列 / 缓存）
2. 有无 **UI**？
3. 有无**语言桥 / 生成物契约**？（FFI / 绑定 / protobuf / codegen）
4. 有无**真硬件**？

**一个项目 = 多个形态叠加。泳道 = 各阶梯的并集。**

> **自验**：mqtt-console = 外部依赖(3) + UI(2) + 语言桥(1) = **6 条泳道** —— 精确复现其真实泳道列表。
> **这个框架可被已有实例证伪，不是拍脑袋分类法。**

---

## 2. 每格给四样（**判据，不是规格**）

**每个形态格 MUST 给：**

1. **阶梯的原理**——为什么这层不能并进那层
2. **典型 flake 源 + 隔离机理**
3. **代价**——值不值
4. **最小可用集判据**——初期只建哪一条

---

## 3. 五个形态格

### 3.1 外部有状态依赖（broker / DB / 队列）

**阶梯（三级）**：

```
假替身  ──▶  进程内真实现  ──▶  真实例
(单元层)      (集成层)          (集成层)
```

**为什么中间那层必须存在**：

- **假替身证明不了「消息真的穿过了 TCP、真的落成了文件」**——它只证明「我的代码按我以为的协议在说话」。
- **真实例又太重、不可移植**——CI 上要装、要起、要清理；开发者本机可能没有。
- ⇒ **中间必须有个进程内层**：真的协议栈、真的编解码、但**不需要外部进程**（很多 broker/DB 有嵌入式版本或内存模式）。

**典型 flake 源 + 隔离机理**：

> 进程内 broker 常有**锁竞争 flake**（并发订阅/发布的时序）。
> **隔离**：把它**关进一条泳道**，另留一条「真实例」泳道当**免疫仲裁者**——真实例泳道不共享那份内存态，flake 传不过去。
> **确定性断言优先落最低层**（单元层）——**缩小 flake 能污染的断言面**。

**代价**：养一个真实例（CI service container / 本机服务）= 一次性配置 + 每次跑多几十秒。**值不值，看你有没有踩过「进程内实现和真 broker 行为不一致」的坑。**

**最小可用集**：**先建「假替身」层**（零依赖、秒级、确定性最高）。进程内层与真实例层留 `planned`，**等真撞到 wire 层问题再推进**。

**参考实例（非规格）**：mqtt-console —— `hermetic`（假替身）/ `embedded`（进程内 broker）/ `realbroker`（真 mosquitto）。

---

### 3.2 UI

**阶梯（两级）**：

```
确定性 DOM runner  ──▶  真浏览器
   (单元层)              (e2e 层)
```

**为什么**：**真浏览器只守前者给不了的**——**真 paint · 真 frame timing · 真 pointer 事件**。
**它刻意不重复确定性断言**：能在 DOM runner 里确定性断言的（「点了按钮，state 变成 X」），**MUST NOT 再在真浏览器里跑一遍**——那只是把一个快而稳的断言，换成一个慢而脆的。

> ⚠️ **归层提醒**：DOM runner（vitest/jsdom）**不连任何真实依赖 ⇒ 单元层**，哪怕它渲染了 DOM。**渲染 DOM 不是穿过真实边界。**

**典型 flake 源**：真浏览器的**等待**（元素还没渲染出来就去点）。**隔离**：关进 e2e 泳道，别让它污染单元层。

**代价**：真浏览器 = 慢（几十秒起步）+ 需要 CI 上装浏览器。

**最小可用集**：**先建 DOM runner 层**。真浏览器留 `planned`，**等有了「真 paint 才能发现的 bug」再推进**。

**参考实例（非规格）**：mqtt-console —— `vitest`（DOM runner）/ `playwright`（真浏览器）。

---

### 3.3 语言桥 / 生成物契约（FFI · 绑定 · protobuf · codegen）

**阶梯（两半，不是两层）**：

```
结构门禁（导出面 + arity）  +  形状测试（stub 下的返回值）
        (集成层)                     (单元层)
```

**⚠️ 这两半各有归属，MUST 不可混**：

- **结构门禁**读的是**真的生成物文件**（「生成出来的绑定，导出了哪些函数？签名对不对？」）⇒ **它穿过了「生成物契约」这条真实边界** ⇒ **集成层**。
- **形状测试**在 stub 下跑（「假设绑定返回 X，我的代码处理对不对」）⇒ **不穿任何真实边界** ⇒ **单元层**。

**为什么必须两半都要**：
- 只有结构门禁 ⇒ 「签名对了，但调用它会崩」查不出来。
- 只有形状测试 ⇒ 「生成器改了签名，我的代码还在用旧的」查不出来——**而这正是生成物契约最常见的失效**。

**典型失效**：**生成物没重新生成**。⇒ 结构门禁 MUST 跑在**刚生成的**产物上，不是仓里那份陈的。

**代价**：低。结构门禁通常几十行。

**最小可用集**：**先建结构门禁**（它守的是最高频的失效：生成器变了而调用方没变）。

**参考实例（非规格）**：mqtt-console —— `assert-bindings`。

---

### 3.4 真硬件

**阶梯（三级）**：

```
主机侧单元  ──▶  仿真  ──▶  真板烧录 SOP
 (单元层)      (集成层)      (e2e 层，executor: human)
```

**为什么**：
- **主机侧单元**：业务逻辑与硬件解耦的那部分（协议解析、状态机）——**能在开发机上跑，就别上板**。
- **仿真**（QEMU / renode / 厂商模拟器）：**穿过了真的固件二进制与真的外设寄存器模型** ⇒ 集成层。
- **真板**：**时序 · 电气 · 真外设** —— 仿真给不了。

**⚠️ 真硬件泳道天然 `executor: human`，且天然不自动跑**（要烧板）。
⇒ **直接 `scaffolded` + 指向 [`embedded-test-sop`](../../embedded-test-sop/) 的手动 SOP，MUST NOT 复述那份 SOP。**

**代价**：仿真 = 配置成本高但一次性；真板 = 每次都要人。

**最小可用集**：**先建主机侧单元层**（最大的一块逻辑通常都能解耦上来）。

**参考实例（非规格）**：`04-iot-tools`（ESP32 / ML307C）。

---

### 3.5 纯计算 / 脚本工具（**四问全答「无」**）

**阶梯（两级）**：

```
单元  +  golden（黄金输出对比）
(单元层)     (单元层)
```

**集成层与 e2e 层：`不适用`。**

> **⚠️ 这不是偷懒，是物理事实**——**它没有真实外部边界可穿。**
> **但 `不适用` MUST 记后果**：「不做 e2e ⇒ **使用者若把 API 用错，我们看不见**」⇒ 补偿：文档示例进 `Example` 测试。

**参考实例（非规格）**：本仓（`sdflow-skills`，pytest）。

## 4. 未覆盖的形态：**兜底，不编，也不罢工**

**没有真样本的形态**（Java 服务 / 移动 app / 分布式共识 / 流处理…）：

| MUST | MUST NOT |
|---|---|
| **按形态四问临场推导**，产出候选 | ❌ **凭空编造权威候选** |
| **显式标注「本形态无参考实例，系临场推导」** | ❌ **因为「格子里没有」就罢工 / fail-closed** |
| **登记 todo 请求补格**（跑一次真项目后回灌） | |

> **「不因无格而卡住，也不假装有权威候选。」**
>
> **⚠️ 这一条是硬红线**：一个「未列举的形态 → 当场罢工」的设计，**等于一类项目被拒之门外**——直接背叛核心承诺「**不管什么项目**」。
> 这正是 `07` 附录 **A21** 的病（手搓 make 解析器留下 7 个「语法不支持」的罢工分支 = 7 类项目被拒），**别在这里换个地方复发**。

---

## 5. 最小可用集：首跑交付**一条能跑的泳道 + 一张明确的待建清单**

**MUST NOT 首跑就铺六条半空的脚手架。**

每格的「最小可用集判据」都指向同一件事：

> **先建那条「零依赖 · 秒级 · 确定性最高」的**（假替身 / DOM runner / 结构门禁 / 主机侧单元），**其余标 `planned`**。
> 等**真撞到那层才能发现的问题**，再 `continue` 推进一格。

**⇒ 首跑的产物是：一条 `verified` 的泳道 + 一张写清楚「还差什么、为什么、怎么推进」的清单。**
**这就是合格的。**（渐进 DoD —— 项目刚开始不可能把所有事定下来。）
