# 负面知识：**证伪过的验证方法**

> **这份文件的唯一目的：别让下一个人（或下一次的你）再走一遍这些路。**
>
> 下面每一条，都曾经看起来很聪明，都曾经被写进设计，**都被现场实验或机械推演证伪了**。
> **遇到「我们能不能机械地证明这个测试是有效的？」这个念头时，先读完本文件。**

---

## 0. 一句话总纲

> **skill 保证「有方法 · 执行了 · 结果被认可」。**
> **skill MUST NOT 保证「方法有效」。**

**「这个 smoke 跑绿了，但它到底测出了什么？」—— 这个问题没有机械答案。**
它归**冷审的 vacuous 镜** + **人**（`testing-framework.md` 槽⑥ 就是在逼人正面回答它）。

---

## 1. ❌ 测试计数门槛

**方案**：解析 `go test -json` / pytest 的 `collected N`，断言「**至少跑了 1 个测试，且 0 skipped**」。

**看起来它防住了**：「压根没跑测试就盖章绿」。

**为什么废**：

```python
def test_integration():
    assert True          # ← collected: 1, skipped: 0, exit: 0  ✅ 完美通过门槛
```

**`assert True` 完美满足它。**

> **它防的是「压根没跑测试」，而真正的风险是「跑了，但断言恒真」——这是两个失败模式。它对后者零拦截力。**

**教训（已升为 `07` §0.0 闸门 1 的后半句）**：

> **「这个保证的信号从哪来」还不够——必须再问「它能不能区分我要拦的那个失效模式」。**
> **信号真 ≠ 信号有用。** `collected≥1` 是一个货真价实的确定性信号，**它就是拦不住 `assert True`。**

---

## 2. ❌ Negative control（抽掉依赖，看它红不红）

**方案**：`verified ⟺ 依赖就绪时 smoke 绿 ∧ 抽掉依赖时 smoke 红`。

**看起来它防住了**：「这个所谓的集成测试，其实根本没连 broker」。

**三条独立理由证伪，任一条足够**：

**① 它只证「命令耦合了依赖」，不证「断言有效」。**

```python
def test_integration(broker_fixture):   # fixture 连不上 broker 就 error
    assert True                          # ← 断言恒真
```
> 抽掉 broker ⇒ fixture 报错 ⇒ **红**。依赖就绪 ⇒ **绿**。
> **正向绿 + 反向红 ⇒ 判 `verified`。而它什么都没测。头号风险原样通过。**

**② 对 testcontainers / 内嵌 fallback 永久误判。**

> Go / Node 生态的主流写法：测试自己起容器，或自动 fallback 到内嵌实现。
> `docker compose stop` 对它们**毫无影响** ⇒ 抽不掉 ⇒ **反向不红** ⇒ **好测试被误判为 vacuous。**

**③ 在真实项目上结构性失效**（现场接地，mqtt-console）：

```makefile
# Makefile:11-14
integration:
	./hack/ctl.sh start                              # ← 依赖启停在 recipe 内部
	MQTT_PORT=1883 go test -tags=integration ./...   # ← 连接参数是 shell 前缀赋值
	./hack/ctl.sh stop                               #    不是 $(MQTT_PORT)，对外部覆盖免疫
```

三条抽离路径**全堵死**：
- **隔离式**（改环境变量指向一个不存在的 broker）⇒ **没有注入点**（`MQTT_PORT=1883` 是字面文本）
- **停服务**（`docker compose stop`）⇒ **接不上**（`ctl.sh start/stop` 也在 recipe 内部）
- **改 Makefile** ⇒ **被「skill 是追加者非拥有者」禁止**

> **而这种写法常见且合理，不是反面案例。**

**④ 它还有副作用**：抽依赖 = **改操作者的机器状态**。

**⇒ 降级为本文件的一个参考实例。MUST NOT 作为 `verified` 的定义。**

## 3. ❌ 轮询式连接观测（`lsof` 轮询进程组）

**方案**：smoke 跑的时候，另起一个循环 `lsof` 那个进程组，看它有没有真的建立到 broker 的连接。

**现场实验结果（5 次采样，全部失败）**：

| | 瞬时连接 | 抓得住 vacuous | 副作用 | 结论 |
|---|---|---|---|---|
| 轮询式连接观测 | **❌ 5/5 全漏** | 仅长连接 | 零 | **证伪** |

> **瞬时连接漏检率 100%。** MQTT 的 connect → publish → disconnect 可以在几毫秒内走完，**采样周期再密也抓不住**。
> ⇒ 它会把**真穿过依赖的好 smoke**误判为 vacuous。

**教训**：**采样抓不住瞬时事件。这是方法本身错，不是参数没调好。**
（我们试过缩短采样间隔。它只是让 CPU 更烫，漏检率不变。）

## 4. ⚠️ Proxy 计数（占端口转发并计数）—— **有效但适用面窄**

**方案**：skill 起一个 proxy 占住 broker 端口，转发并计数。**在数据必经之路上，零漏检。**

**实验结果**：**✅ 5/5 全中**，零副作用。

**为什么仍然不用**：

> **适用面 ⊆「skill 能控制依赖的启动」。**
> 对「依赖启停内嵌在 recipe 里」（上面 §2③ 那种写法）**同样无效**——你没有机会插进去。
> 而且它**依然只证「跟依赖说过话」，不证「断言有效」**（§2① 的问题原样存在）。

**⇒ 记在这里，供未来某个明确知道自己控制依赖启动的场景参考。不进主路径。**

---

## 5. 🔴 硬边界：**`assert True` 类语义恒真，任何外部插桩都堵不住**

**这是所有上述方案的共同天花板。**

> **「跟依赖说过话」≠「断言有效」。**
>
> 你可以证明这个进程真的连上了 broker、真的发了包、真的收到了回应——
> **然后它 `assert True`。**

**要堵它，只有变异测试**（删掉一段被测逻辑，看 smoke 会不会红）。
**判为太重**：要改用户代码 + 跑两遍全量。

**⇒ 机械层堵不死。诚实划归冷审语义镜。**
**⇒ `07` §0.0：MUST 如实声明，MUST NOT 佯装机械层能堵。**

## 6. 🔴 最刺眼的案例：**所有机械层同时失效**

> **mqtt-console 的残留 session 泄漏探针**（staff-review 抓出的真缺陷）：
>
> ```go
> // 想测：客户端断开后，broker 里的残留 session 会不会泄漏
> client := connect(CleanSession: true)     // ← 就是这里
> connack := client.Connect()
> assert.False(t, connack.SessionPresent)   // ← 断言残留 session 不存在
> ```
>
> **而 MQTT 3.1.1 规定：`CleanSession=1` 的 CONNACK 恒返回 `SessionPresent=0`。**
>
> ⇒ **这个断言恒真。残留 session 的回归，全部漏过。**

**逐条核对，看看有哪个机械层能抓到它：**

| 机械检查 | 结果 |
|---|---|
| 测试计数门槛（`collected ≥ 1`） | ✅ 通过 —— **断言语句在，数量 > 0** |
| Negative control（抽掉 broker） | ✅ 通过 —— **它真的连了 broker，抽掉就红** |
| Proxy 计数 | ✅ 通过 —— **真的有流量** |
| 字面恒真检测（`assert True` 的 AST 扫描） | ✅ 通过 —— **它读了一个变量，字面上不恒真** |
| 覆盖率 | ✅ 通过 —— **代码路径都走到了** |

**⇒ 五个机械层，全部放行。**

**只有一个东西抓到了它：一个人读代码，然后问——**

> **「这个断言，真的有可能红吗？」**

## 7. ✅ 唯一有效的防线：**冷审 vacuous 镜 + 槽⑥**

| 防线 | 怎么工作 |
|---|---|
| **`testing-framework.md` 槽⑥** | **逼人正面回答**「这层证明了什么、看不见什么」——**在写测试之前** |
| **冷审 vacuous 镜**（[`review-lenses.md`](./review-lenses.md)） | fresh 子代理读 smoke 源码：「**删掉被测逻辑，它会红吗？**」——**在写完之后** |

> **这不是弱点，这是诚实的边界划分。**
> **一个明确写着「我堵不住 `assert True`，这归人管」的设计，比一个假装堵住了的设计安全得多。**
