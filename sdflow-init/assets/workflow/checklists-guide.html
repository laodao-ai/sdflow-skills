审查清单资产指南

sdflow 工作流的核心质量资产——设计审与代码审的领域清单体系。本文介绍当前覆盖面、架构设计，以及如何为新领域（如前端代码审）扩展清单。

权威源位置：sdflow-init/assets/workflow/ 下的 spec-checklists/（设计审）和 code-checklists/（代码审）。两套清单共用 trigger-catalog.md 的 TG 触发决定领域深度。

一、架构：通用 base + 领域 delta

两套清单采用相同的分层架构：一份通用 base（任何项目、任何语言都过）+ 按技术栈叠加的领域 delta。每层只写自己新增的规则，通过 extends: 声明父层，绝不整份复制。

  spec-quality-base.md  ──────  code-review-base.md
  (设计审通用 · 30 条)          (代码审通用 · 11 条)
        │  每份 spec 必过              │  每次 code-review 必过
        ▼                              ▼
  domains/                       domains/
    backend.md                     backend.md
      └ backend-go.md                └ backend-go.md
    embedded.md                    embedded.md
      ├ embedded-ml307c.md           ├ embedded-ml307c.md
      └ embedded-esp32.md           └ embedded-esp32.md
    frontend.md                    frontend.md
      └ frontend-react.md            └ frontend-react.md
    devex.md                       llm.md
    [未来领域...]                   [未来领域...]

选用规则：变更起手按 trigger-catalog.md 的 TG 判命中哪些技术栈 → 叠加对应领域链。例如改 Go 后端 = base + backend + backend-go；跨栈变更取并集。不涉及的领域不叠加。

ID 约定：每条规则有稳定 ID（前缀标明所属层），一经分配不复用、不重排——删除规则只留空号，新增取新号。

为什么有些领域只在一侧？

  • LLM（code-review-only）：LLM 集成的风险主要在代码消费层（输出信任边界、prompt 一致性），设计层面用通用 base 已够。
  • DevEx（spec-review-only）：开发者体验的检查点（TTHW、错误信息三件套、命名可猜性）在设计阶段判定，代码侧无对应检查维度。

五、如何新增一个领域

已建成回顾：code-checklists/domains/frontend.md（add-frontend-checklists，2026-08）是这套五步流程的最近一次实跑，以它为例复盘完整流程：

  1. 建文件：在 sdflow-init/assets/workflow/code-checklists/domains/ 下新建 frontend.md，文件头声明继承关系： 
    # 代码审查领域：前端 / UI（通用）

> `extends: base` —— 前端代码审查特有维度，框架无关；
> 通用维度见 `../code-review-base.md`。
  2. 只写 delta：每条取新 ID（前缀 CR-FE-），只写本层新增的审查项。格式跟随同目录既有文件：ID | 规则 | 触发条件 | 检查点 四列表格。不复制 base 或父层的任何条目。
  3. 更新注册表：在 code-checklists/README.md 的「领域注册表」加一行： 
    | `domains/frontend.md` | base | 前端/UI | `CR-FE-` |
  4. 检查触发：确认 trigger-catalog.md 中已有对应 TG（前端是 TG-03）。如果是全新领域，需要在 trigger-catalog 新增一个 TG 条目。
  5. 同步 config 模版：如果新领域需要项目配置段（如领域特定的约束），在 config.template.yaml 的 domains 列表中注册。
  6. 走正常 change 流程：这类改动本身就应该走 /sdflow-spec → review → ship 的完整流程——dogfooding。

实际条目见 code-checklists/domains/frontend.md（CR-FE-01~08）；设计审侧同批同法补齐见 spec-checklists/domains/frontend.md（FE-06~13）。

分层原则的实例：框架特化规则走同一模式——frontend-react.md 声明 extends: frontend（已建成，spec 侧 REACT-01~03 · code 侧 CR-REACT-01~07）。读 React 项目的完整清单 = base + frontend + frontend-react 三层并集，与 backend → backend-go 的分层完全对称。

六、写规则的约定

每条规则包含

  • 稳定 ID：前缀标明层，号码只增不减（删除留空号）
  • 触发条件（领域规则）：什么样的变更需要查这条
  • 检查点：具体查什么、怎么判 pass/fail
  • 防什么失效（隐含或显式）：为什么需要这条规则

两套清单的分工

spec-checklists（设计审）code-checklists（代码审）
审什么设计对不对（方案、接口、边界）实现对不对（代码、逻辑、安全）
谁用sdflow-spec-reviewsdflow-code-review + sdflow-implement Standards 轴
base 规模30 条（含三级分层）11 条（扁平）
落点列有（T/C/S/R 四种）无（全部为 R 评审型）
单侧领域devex（DX，设计审独有）llm（CR-LLM，代码审独有）

好规则的特征

  • 可判定：审查者能给出 pass/fail，不是模糊的「应考虑」
  • 有失效反例：能举出不遵守时会出什么事
  • 不重复父层：父层已覆盖的不在子层重复
  • 框架无关（通用层）：通用层的 frontend.md 写框架无关的维度；框架特化进子层

本文描述的是 sdflow-skills 仓 sdflow-init/assets/workflow/ 下的审查清单资产。这些清单随 workflow bundle 分发，经 setup.sh 安装到 ~/.sdflow/workflow/，对本机所有项目生效。
