# Spec 质量保证方法论

> 本文是 spec 质量体系的**最上层（L3 方法论）**：不回答「好 spec 长什么样」（见
> [`spec-checklists/`](../spec-checklists/README.md) 规则集），也不回答「现在哪个工具在哪步干活」
> （见 [Spec_Quality_Collaboration.md](./Spec_Quality_Collaboration.md)），而是回答
> **「靠什么样的策略与机制，能可靠地把一份 spec 推到那些标准上」**。
>
> 三层关系：

```
   ┌─────────────────────────────────────────────┐
   │  L3  方法论 / 策略   ← 本文                   │
   │      「用什么机制，可靠地命中标准？」          │
   ├─────────────────────────────────────────────┤
   │  L2  标准 / 口径     ← spec-checklists/      │
   │      「命中了没有，拿什么判？」                │
   ├─────────────────────────────────────────────┤
   │  L1  工具 / 执行     ← brainstorming/autoplan │
   │      「具体哪个 skill 在哪一步干这事？」       │
   └─────────────────────────────────────────────┘
```

L2 是尺子，L1 是干活的手，L3 是「为什么这么布手、布几道、谁来量」。
再好的 checklist 也不会自动变成高质量 spec——中间靠 L3 的机制。

## 一、核心元模型：两个正交轴

任何「spec 质量保证」手段都能拆到一张二维网格上。
**第一个轴：在什么时候动手。第二个轴：拿什么当真相来判。**

```
              拿什么当「真相」来判 ──────────────►
              内部自洽            外部接地
              (cheap/可自动)       (codebase/标准/人)
            ┌──────────────────┬──────────────────┐
  生成时    │  模板/Schema 约束 │  D-1 grep 约束    │  ◄─ 预防 Prevent
 (Prevent)  │  结构化生成       │  引用已有 ADR     │     不让坏 spec 被生出来
            ├──────────────────┼──────────────────┤
  生成后    │  占位符/歧义扫描  │  eng-review 读码  │  ◄─ 检查 Detect
 (Detect)   │  内部一致性检查   │  CEO scope 挑战   │     生出来后挡在门口
            ├──────────────────┼──────────────────┤
  反复迭代  │  generate-critique│  实现期缺陷回灌    │  ◄─ 修正 Correct
 (Correct)  │  -refine 自循环   │  retro 更新清单    │     错了之后修，并改进流程
            └──────────────────┴──────────────────┘
```

把现有体系往图上一摆，重心与窟窿立刻可见：

- 现有 brainstorming + autoplan + checklist **几乎全堆在中间那行「生成后检查」**。
- `Collaboration.md` 自己的结论——「Accurate 是唯一没有 review 兜底的标准」——本质上
  **不是少了一道检查，而是它根本不该靠检查解决**：它属于右上角「生成时 × 外部接地」
  格子（D-1 grep）。检查的是「自洽」，补不了「与代码库真相对齐」。

## 二、三条基础原则（方法论骨架）

### 原则 1：质量内建 > 事后检查（Shift-Left）

> Deming / Crosby：「Quality cannot be inspected into a product; it must be built in.」

越靠上（生成时）解决越便宜，越靠下（检查/返工）越贵。现有体系偏「检查重、预防轻」。
**杠杆最大的动作往往不是再加一道 review，而是把某个反复出问题的维度，改成生成时就约束死。**
Accurate 即活教材。

### 原则 2：纵深防御 / 瑞士奶酪模型

```
   每一道检查都是一片有洞的奶酪。单片必漏，关键是「让各片的洞错开」。

   brainstorming ▓▓░▓▓▓▓   ← 结构/歧义的洞
   autoplan-Eng  ▓▓▓▓░▓▓   ← 架构/测试的洞
   checklist     ░▓▓▓▓▓▓   ← 占位符的洞
   D-1 grep      ▓▓▓▓▓▓░
                 ──────────
   叠起来看：Accurate 那一列，所有片的洞都对齐了 → 漏穿
```

含义：别追求「单道检查更全」，要追求「多道**独立**检查、盲区互补」。
同一个 session 自查 ≈ 同一片奶酪叠自己，洞不会错开。
autoplan 用 Codex 当第二声音，价值就在「独立」二字。

### 原则 3：接地验证（Ground-Truth Anchoring）

每一条质量主张都得能对到一个**参照真相**上，否则不可验证、只是好看的句子。
spec 的真相源有四个，逐个问「这一维有没有锚」：

```
  真相源              对齐手段             现状有没有锚？
  ──────────────────────────────────────────────────
  ① 代码库现状        grep / 读码          ⚠️ 只在 D-1，review 期无
  ② 行业标准/规范     checklist 第 5 层    ✅ 已建（IEEE/NFR）
  ③ 既有决策/ADR      引用 INDEX/边界 ADR  ✅ 有强制规范
  ④ 利益相关方意图    人工 sign-off        ⚠️ 标准里写了，流程没强制
```

没锚的维度 = 必漏的维度。①④ 是当前两个弱锚。

## 三、AI 生成 spec 的额外杠杆

经典 SRS/IEEE 方法论默认 spec 是人写的。本仓库的 spec 是 **AI 生成 + 人审**，
这解锁三个传统流程没有的机制——全部落在元模型的「修正」行与「独立判」列：

```
  ① 生成器/批判器分离 (generator ≠ critic)
     写 spec 的 agent 与挑刺的 agent 不能共用同一 context
     → autoplan 已在做（Claude 子 agent + Codex）

  ② 多采样 + 评判 (sample N, judge)
     同一需求生成 2-3 版，让裁判挑/合并
     → Standards 第 12 条「2-3 方案对比」即此思想的人工版

  ③ 对抗式验证 (adversarial / red-team)
     不问「这 spec 对吗」，而是派 agent「请证明这份 spec 会在实现期爆炸」
     → 比顺向 checklist 更易揪出隐藏假设
```

这三条是 AI 流程与纯人工流程拉开差距之处。

## 四、经典切分：Verification vs Validation

用这条把 L2 的 25 条标准按「谁来判」一刀切开：

```
  Verification「spec 建得对不对」  → 内部属性，多数可机械/AI 自动判
     占位符、内部一致、歧义、错误路径覆盖、NFR 是否数字化…
     ⇒ 适合做成生成时约束 + 自动扫描，不该占用人的注意力

  Validation「spec 的是不是对的事」 → 需要判断，必须人/独立视角
     scope 对不对、方案选得对不对、利益相关方认不认、假设成不成立…
     ⇒ 适合 brainstorming 对话 + CEO/Eng review + 人工 gate
```

现有 25 条按「严重度」分层，混在一起。叠一个 V&V 切分，可回答很实际的问题：
**哪些该自动化掉、哪些必须留给人**——避免让人去逐条数占位符（机器的活），
也避免让机器去拍 scope（人的活）。

## 五、现状诊断与可走方向

一句话现状：**标准很全（L2 几乎做满），但机制偏「事后检查 + 内部自洽」，
在「生成时预防」与「外部接地」两个方向偏薄；且整体是开环（无缺陷回灌）。**

| 方向 | 一句话 | 对应原则 |
|------|--------|---------|
| **A. Accurate 从检查改预防** | 强化 D-1，生成时强制 grep，而非指望 review 补 | 原则 1 + 锚① |
| **B. 加一道对抗式独立验证** | 派独立 agent 专门「证明这 spec 会炸」 | 奶酪 + AI 杠杆③ |
| **C. 给 25 条标准叠 V&V 标签** | 切出「自动化区」与「人工区」，各配机制 | 第四节 |
| **D. 闭环：实现期缺陷回灌清单** | 跟踪「哪些 spec 漏洞导致返工」，反哺标准 | 修正行，当前空白 |

其中 **D 是当前唯一结构性缺失的一环**：现有体系是开环（标准→检查→实现），
实现期暴露的问题没有路径反馈回标准。无此回路，checklist 会逐渐僵化、与真实缺陷脱节。

## 六、与 L1/L2 文档的接口

- 本文给出的「两轴元模型 + 三原则 + V&V 切分」是**思考框架**，不替代具体清单。
- 落地时：用 L2 规则集（`spec-checklists/` 的 base + domains）做尺子，用 L1（Collaboration 里的 brainstorming/autoplan 分工）做手，
  用本文判断「某一维该放在 prevent / detect / correct 哪一格、由谁判」。
- 任何对工作流的改动（如 `openspec/workflow/workflow.md`）应先回到本文的元模型上定位，
  确认是在补「最薄的格子」，而非在已经很厚的「生成后检查」上再加冗余。
