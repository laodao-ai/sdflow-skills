# Change 拆分标准

> **规范类文档（load-bearing，本目录内的例外）**：本目录其余文件是纯说明/方法论、删之不影响执行；
> 本文件不是——它是「一个 change / phase 该拆多细」的唯一权威文本，被
> `sdflow-spec`（相位 B scope 内聚检查）、`sdflow-roadmap`（阶段拆分）、
> `sdflow-implement` + `sdflow-code-review`（执行期票外发现的 fold/defer 判定）三处消费点
> 以指针方式引用，**不复制正文**；删除本文件会让三处引用指向空文件。
>
> 判定入口在 `spec-checklists/spec-quality-base.md` 的 `BASE-18`（评审时的 fold-vs-defer AND 门）
> ——本文件与 BASE-18 互为指针：BASE-18 是判定入口，本文件讲完整规则与 why，二者不复制彼此正文。

## 规则

1. **一个 change / phase = 一个完整阶段结果**：拆分单位是「一个内聚、可独立验证的交付物」，
   不是「同一批发现」或「凑够票数」。触碰多个独立功能域的改动不得塞进同一个 change；
   一件事也不得被拆散跨多个 change。
2. **不按来源批次或凑票拆分**：几个改动是否同批被发现、改起来是否顺手、能不能凑够「看起来
   合理」的票数，均不是拆分依据——唯一依据是规则 1 的内聚边界。
3. **相关发现优先 fold**：执行 / 评审过程中撞到与当前 change 相关的 bug / todo，默认**并入
   当前 change 做掉**，而非另开。是否真的该 defer，判定入口 = `BASE-18` 的防吸积 AND 门——
   **同 capability ∧ 高耦合 ∧ 低增量成本**三者皆满足才真 fold 进当前 change；任一不满足
   → defer 另开（真独立、扩容大、需自身设计审查、高 blast-radius 均天然落 defer）。
4. **「缺依赖模块 → 占位 + 记 todo」是 related 语境下的经典 defer 形态**，不是与规则 3 的
   AND 门并列的「唯一合理 defer」绝对句——AND 门未满足的其余情形（真独立 / 扩容大 / 需自身
   设计审查 / 高 blast-radius）同样合法落 defer，缺依赖模块只是其中最常见的一种，不得被写成
   排除其它 defer 理由的绝对句。

## Why

碎片化（同一件事被拆成多个 change）不是省事，是把「反复对现状提疑问 + 给妥协方案（WARN /
grace / flag）」的根因种下：每次只做半件事，后续每个接手的人都要重新拼出全貌、重新论证
「这次要不要顺带修一下」。一次做完整、锚目标态、fail-closed 收尾，这类反复论证根本不会发生。

反过来，逢新发现就机械「另开一个 change」同样有害——workflow 循环的固定成本（起分支 / 评审 /
gate / merge）远高于把一个低风险、高耦合的小发现顺手做掉的增量成本；固守单一职责教条只会把
评审预算耗在流程开销上，而不是耗在真正的判断上。规则 3 的 AND 门存在的意义就是把这两个方向
的失衡都挡住：判据落在「是否同 capability、是否高耦合、增量成本是否低」，而不是「看起来像不像
同一件事」的直觉。
