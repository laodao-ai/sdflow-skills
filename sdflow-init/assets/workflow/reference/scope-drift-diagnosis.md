# 协议 / 契约 文档漂移诊断（scope-drift）

> **说明类文档**（非 load-bearing）。生成期的强制动作是 `BASE-29`（design 必含协议文档套件
> scope-check 表），触发是 `TG-25`。本文只解释「为什么」+ 出问题时怎么排障，删之不影响执行。
>
> 来源：实战复盘 `protocol_doc_audit`（一次协议升级中，代码改了但部分编号协议文档没同步，
> 且漏掉的文件**根本没进 tasks 列表**，导致下次升级仍不会被想起）。

---

## 核心洞察

**tasks 全 ✓ ≠ 事情做完。** 工作流足够严谨时，tasks 全勾仍出问题 = 问题不在实施层（plan/review/code），
而在**更上游的 scope / roadmap 层**——某个该改的文件从一开始就没被列入。

## 关键判定区分：未完成 vs 未列入

| 类型 | 表现 | backlog 找得到？ | 严重性 |
|------|------|-----------------|--------|
| 未完成 | task 标 `[ ]` / `[~]`，**在列表里** | ✓ | 低——下次冲刺会想起 |
| **未列入** | task 列表里**根本没有这个文件** | ✗ | **高——下次升级仍不会被想起** |

防御 = `BASE-29` 的 scope-check 表：起 change 时枚举**全套**协议文档，对**没改的**也强制写「不改的理由」，
空理由 = 不通过。把「未列入」从隐性漏点变成显式判断。

scope-check 表形态（每个 change 现填真实文件清单，不硬编进规则）：

```
| 文件 | 当前版本 | 本 change 是否改 | 不改的理由 |
|------|---------|------------------|-----------|
| 01_envelope.md | v1 → v2 | ✓ | — |
| 02_uplink_frame.md | v1 → v2 | ✓ 仅头 | 内容无字段变更 |
| 06_cmd_temperature.md | v1 | ✗ | **必须填理由，空着=不通过** |
```

## 诊断捷径（出现「协议契约 / spec 落地」问题时）

```
查 tasks.md 完成度
        │
        ├─ tasks 有 ✗ / [~] → 实施环节问题（查 plan / review / code 三层）
        │
        └─ tasks 全部 ✓
                │ 跳过 plan / review / code（工作流忠实的前提下，前三层不会是 root cause）
                ▼
        直查 scope / roadmap 层
                ├─ scope 显式排除 → 设计决策问题（查 defer 清单的理由是否成立）
                └─ scope 未提及   → 列入漏点（高危：下次升级仍不会被想起）
```

## 反 pattern 警告

> **同一 roadmap 中，代码改造范围 ≠ 文档改造范围 = 高危信号。**

防御：在 roadmap → proposal 之间做一次「对称性 review」——代码改了哪些模块、对应文档是否同步，
差集非空必须逐项显式回答（要么补改，要么写明为何不需改）。这正是 `BASE-29` scope-check 表把
「差集」前置到 design 阶段强制暴露的原因。
