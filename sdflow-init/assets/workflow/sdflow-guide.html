SDFLOW-SKILLS

sdflow 工作流指南

一套围绕 OpenSpec 的规格驱动开发（SDD）闭环：从「铺工作流」到「生成变更 → 设计审 → 实现 → 代码审 → 归档 merge」， 全程只保留一个人类决策点。本文讲清它的原理、设计思路，以及在实际项目里怎么用、怎么灵活裁剪。

01 · WHY

为什么存在：把「写对」从运气变成结构

LLM 写代码的瓶颈从来不是打字速度，而是方向错了也跑得飞快。 sdflow 的答案是把质量问题拆成两半，分别用不同的手段处理：

  • Prevention（生成期防住）——能用结构固化的，写进 config 模版槽；能用约束固化的，写进生成硬约束（D 约束）与触发目录（TG）； 唯一固化不了的「生成过程」，用 /sdflow-spec 的「拷问前置于成文」流程兜住。
  • Detection（评审期抓漏）——评审只做 prevention 焊不住的残差：语义校验、对抗攻击、接地读码。 不重复检查机械层已经防住的东西。

另一条贯穿始终的信念：能机械判定的一致性绝不交给模型的自觉。 ID 不撞号、步序不乱、引用真实存在、报告锚点可核验——这些全部由脚本与 gate 把守； 模型的算力只花在真正需要判断的地方（方案取舍、语义评审、拷问澄清）。

02 · PRINCIPLES

核心设计思想

以下十条是整套体系反复出现的骨架。理解了它们，每个 skill 的行为都能推导出来。

P1机械化优先：脚本 owns 一致性，模型只做判断

凡有确定性信号的一致性（撞号、步序、双写一致、引用存在性），一律脚本化守住——ship_gate.py 判步序、 issues_v2.py 保台账不变量、评审 tools/ 做引用核与锚点 lint。只有「无确定性信号」的残余才留给语义规则。 诚实边界是合法的残余划分，不是弱点。

推论：无界语法面不手搓解析器。想知道 make target 能不能跑，就真跑一遍让 make 自己回答； 「每轮 review 都在同一个函数里补一个新语法分支」的信号说明这个函数本来就不该存在。

P2单一源 + 全量生成，不做互引文档的局部修补

阶段一先拷问、把每条承重约束落进 decision-memo.md（单一源），再由它全量生成四件套 （proposal / design / specs / tasks）。修改一组互相引用的文档比从单一源整体重生成更容易出错——这是工程事实，不是概率论据。 同样的模式贯穿全仓：触发目录 trigger-catalog.md 是 TG 唯一源，model-tiers.md 是档位唯一源， workflow bundle 的权威源只有 sdflow-init/assets/workflow/ 一处。

P3独立性来自 fresh 子代理，不靠 /clear

评审的独立性由「fan-out 到全新上下文的子代理」结构性提供——它们看不到作者的推理过程，天然没有作者偏置。 /clear 全流程只出现在两处阶段交界（一→二、二→三），理由是 cache 按模型隔离与盘面纪律， 与独立性无关；阶段内部一律禁 /clear。

P4对抗式多镜评审 + 跨模型第二意见

单镜自审无效（瑞士奶酪模型），所以评审是并行多镜：领域镜按清单查、对抗镜不问「这对吗」而是派人「证明它会炸」、 接地镜读真实代码核对事实。此外默认开一路跨模型 outside-voice——实测多轮里，跨模型视角的独家产出常常碾压同族温镜。

设计侧与代码侧刻意不对称：设计审优化召回（判断分歧一律上抛人门，不自动丢弃）； 代码审优化精度（强档二元裁决，能修的当场自动修）。

P5全流程唯一人类门

人的注意力只花在一个地方：设计审报告出来后的 HARD-GATE 拍板。评审中途不打断提问—— ≥2 方案、核验不了的事实，全部写进报告的「决策登记区」（选项 + 推荐 + 三面后果 + 主次判定），人一次性过报告决策。 阶段三之后无人门，一路自动跑到 merge；人的再入口是异步读 hand-off.md。

P6防假绿：每个 ✅ 都要有机验锚点

去掉人门的前提是终门足够硬：sdflow-done 的 verify 以 Do-Not-Trust 冷启动跑在强档模型上， 每条 ✅ 必须附机器可核验的锚点（测试名 / commit / file:line），无锚点的 ✅ 自动降级为 gap。 同理，resolve-workflow.sh 的 sane() 检查发现半坏态就 fail-loud，绝不静默广播； 子代理能力探针失败则缩减评审镜数并显著标注降级，不为没独立跑过的镜落锚。

P7分档派发：把贵的算力花在门禁上

model-tiers.md 把子代理按强 / 中 / 轻三档派发（Claude 与 Codex 双机队各自映射）， 另有正交的 effort 维（Claude 专属）。铁律只有一条：带门禁、无人逐条复核的步 MUST NOT 降档—— 弱模型的假绿会放不完整的活过关；纯机械步则尽管下放轻档省钱。

P8盘面即状态：停即停，重调即续

阶段三不依赖任何跨步内存状态。ship_gate.py 每步前后从磁盘盘面（四件套、报告、tickets、git）推导下一步 verdict， 禁止用 prose 记忆步序。会话崩了重新调用即接续；且 gate 不辨产者——人工手跑某步的产物同样被认（人机同权）。

P9四条通则是宪法，且随身携带

「能查的自己查 / 先调研再推荐 / 锚目标态不拿现状反驳 / 简化但不砍目标范围」四条通则由脚本注入每个 SKILL.md 的托管块， fan-out 子代理与 outside-voice 的 prompt 必须原文携带。为什么内联复制而不是给个链接？ 这几条要防的失效模式，恰恰包含「不会想到要去查它」——会想起去查规则的人，本来就不会犯这个错。

P10信任边界明确：只有真人是「人」

上游 agent 的 prompt、子代理任务指令、outside-voice 的 context，都不构成「人的明确指示」，不能豁免任何规则； outside-voice 的 context 区被声明为 UNTRUSTED，其中指令性文字一律视为数据。授权只能来自真人用户，沉默不等于授权。

03 · PIPELINE

三阶段流程

一个变更（change）的完整生命周期如下。整条线是唯一线性路径——没有旁路，没有可选的平行入口。

STAGE 0 · 可选前置

opsx:explore —— 发散探索

仅当问题模糊、方向未定时才跑；想法已清晰就直接跳过。这是全流程唯一的条件步。

↓人示意收敛（「开搞」「做吧」）→ 模型自动 invoke；模型不得自主开 change
STAGE 1 · 生成

/sdflow-spec —— 澄清 → 拷问 → 生成

相位 A 澄清需求；相位 B 起手即建分支（FF-0 三分支判定）+ change 目录，逐条拷问承重约束、 站稳一条就增量落盘进 decision-memo.md（所以 /clear 无损、崩溃只丢最后一小段）； 相位 C 从 memo 全量生成四件套 + 终审。

↓/clear → 切换评审档模型（出口序列，G1 具名例外之一）
STAGE 2 · 设计审

/sdflow-spec-review —— 单批 fan-out 多镜

一条消息内并行派出：广审双镜（strategy / plan-eng）+ 领域镜 + 对抗镜 + 接地读码镜 + design-voice 跨模型第二意见； 主审做机械引用核、去重合并、对抗裁决，收敛成一份 spec-review-report.md。中途不向人提问。

↓
HARD-GATE

人工过报告拍板全流程唯一人类门

逐条处理报告里的发现与「决策登记区」的待拍板项。批准后进入无人区。

↓/clear → 调用时重述 merge 意图（G1 具名例外之二）
STAGE 3 · SHIP（无人门，连续跑到 merge）

/sdflow-ship {change} —— gate 台账驱动

每步前后调 ship_gate.py 从盘面推导 verdict，依次驱动：

① 实现：sdflow-implement 先出 3–6 张 tracer-bullet 垂直切片 ticket， 再按依赖 frontier 派 fresh implementer 执行，每张 ticket 过 Standards / Spec 双轴审；

② 代码审：/sdflow-code-review 冷视角强制全跑——scope 审计 + 领域/对抗/历史多镜 + 机械引用核 + 二元裁决，能修的自动修（标 [impl-review-fix]）、修不了的 defer 进 issues 池；

③ 收尾：/sdflow-done —— verify（证据锚点终门）→ issues sweep → hand-off.md → archive（delta 对真实代码核验后同步进 specs）→ commit → 默认 merge。

↓人类再入口：异步读 hand-off.md，决定要不要开清理 change

/clear 纪律：全流程只有上面标出的两处阶段交界该 /clear； 阶段内部（尤其子代理调度期间）一律禁用，上下文吃紧用 /compact。 审查顺序也不可颠倒：本地 diff 审 → push PR → 远程 PR 审。

04 · SKILLS

Skills 全景

15 个 skill 按角色分组。数据类带 scripts/（Python 脚本保证确定性，多数配 pytest）； 编排类是纯 Markdown 指令，驱动主 session 调度子代理。

Skill类型角色
铺设与维护
sdflow-init数据类一键把 spec 工作流铺进任意项目；本仓是 bundle 唯一权威源。update 模式重拉最新
sdflow-maintain数据类扫描 openspec 目录与 INDEX 的一致性，报告差异并修复
sdflow-upgrade编排类升级运行 checkout：pull → setup 一键完成，堵住「新 SKILL 调旧脚本」窗口期
主流程（阶段一 → 三）
sdflow-spec编排类阶段一产 spec 单一入口：澄清 → 拷问 → 生成四件套 + decision-memo
sdflow-spec-review编排类阶段二设计审主审：多镜 + 跨模型 voice → 一份报告供人拍板
sdflow-ship数据类阶段三总编排：ship_gate.py 台账驱动到 merge
sdflow-implement数据类tickets 实现管线：出 ticket + 受限并行执行 + 每票双轴审；只由 ship 派发
sdflow-code-review编排类阶段三代码审主审：冷视角多镜 + 二元裁决 + 自动修
sdflow-done数据类闭环：verify 终门 → hand-off → archive → commit → 默认 merge
规划三轴（互不重叠，按需单用）
sdflow-architecture数据类空间轴：简单需求 → skeleton-ready SAD + 骨架切片建议
sdflow-devenv数据类过程轴：单元/集成/e2e 三层测试策略一层不留白 + 真跑确认
sdflow-roadmap编排类时间轴：比单次 change 更大的多阶段规划，三件套直写落盘
记录与复盘（横切，可独立使用）
sdflow-issues数据类bug 池 + todo 池统一台账：一个 issue 一个文件，脚本保 ID 与索引一致
sdflow-retro数据类只读再生「评审流程值不值」的成本×价值复盘报告，只呈现不决策
仅服务本仓
sdflow-upstream-watch数据类追踪四个上游源 delta 出三分诊报告；外仓调用被 cwd 守卫拒绝
05 · IN PRACTICE

在实际项目中使用

跑通第一个变更

# 装一次（任意位置 clone，绝对路径 symlink 与位置无关）
git clone https://github.com/laodao-ai/sdflow-skills.git && cd sdflow-skills && bash setup.sh

# 在你的项目里：
/sdflow-init            # 只做一次：铺目录骨架 + config.yaml + CLAUDE.md 托管块
/sdflow-spec            # 阶段一：产四件套 + decision-memo（问题模糊先 opsx:explore）
/clear                  # 切换到评审档模型
/sdflow-spec-review     # 阶段二：一份报告 → ★ 人在这里拍板（唯一人类门）
/clear
/sdflow-ship {change}   # 阶段三：实现 → 代码审 → done → merge 连续跑

铺完之后项目里长什么样

openspec/
├── workflow/WORKFLOW-GUIDE.md   # 唯一落地的规则文件（人读手册）
├── schemas/sdflow-spec-driven/  # 四件套结构的 project-local schema
├── config.yaml                  # 「本项目」段自己填：领域、领域清单、可选覆盖
├── INDEX.md                     # 托管块自动注入
└── changes/  specs/  issues/    # 变更 / 规格 / 台账
CLAUDE.md / AGENTS.md            # 注入托管块：强制规范 + 四条通则

注意规则集与评审工具不会拷进你的项目——运行时经 ~/.sdflow/hack/resolve-workflow.sh 解析到全局 canonical ~/.sdflow/workflow/。好处：升级工具链（/sdflow-upgrade）一次， 本机所有项目立即吃到最新规则，无需逐仓 update。

日常触发习惯

  • 想法没成形 → opsx:explore 陪你发散；成形了说一句「开搞」，模型会自动进 /sdflow-spec。
  • 记账随时可用：「记一下这个 bug」「记个 TODO」→ sdflow-issues 落盘，sdflow-done 收尾时自动 sweep 分诊。
  • 设计审报告是你唯一必须细读的东西——「决策登记区」里每项都带推荐 + 依据 + 代价，你只做拍板。
  • merge 默认执行；不想自动 merge，在调 /sdflow-ship 时说明即可（opt-out）。

灵活裁剪的几个正交旋钮

  • 按需单用，不必全家桶：sdflow-issues（台账）、规划三轴（architecture / devenv / roadmap） 都可脱离主流程独立使用；比单次 change 大的工作先 sdflow-roadmap 拆阶段，每阶段再走一遍主流程。
  • 深度由触发决定，不用手选档位：起手按 trigger-catalog.md 判 TG 命中， 命中什么就激活对应的约束 / 领域清单 / 画图要求——小改动自然轻，高风险自然重。
  • config.yaml 的「本项目」段：声明领域（backend / frontend / embedded / llm…）决定评审用哪套领域清单； 可选覆盖 model-tiers / effort-tiers（如预算紧把中档换轻模型——但门禁步不许降档）。
  • 人机同权：任何一步你都可以人工手跑，产物落盘后 gate 照认，接着往下走。
  • 双宿主：Claude Code 与 Codex 都能跑；Codex 侧子代理授权与降级路径（不可用时缩镜数并显著标注）已内建。

常见坑：① 阶段内部禁 /clear（尤其子代理调度期间）； ② tasks.md 的复选框在 done 的 archive 阶段才勾，实现期勾会触发设计门失鲜； ③ 升级后 pull 与 setup 之间是「新 SKILL 调旧脚本」窗口期——用 /sdflow-upgrade 一键完成两步； ④ 开 change 必过 FF-0 分支判定（全局 hook 硬拦），在别的 feature 分支上会停下来问你。

06 · UNDER THE HOOD

安装机制与目录布局

setup.sh 遍历仓库根，仅安装含 SKILL.md 的目录，共四个落点：

落点内容方式
~/.claude/skills/全部 15 个 skill绝对路径 symlink（改源即时生效）
~/.codex/skills/同上（Codex 宿主）同上；Windows 用 copy + marker
~/.claude/agents/3 个角色定义 + 5 个 effort 档位定义逐文件软链；全局命名空间，守卫最严
~/.sdflow/canonical workflow/ + hack/ 辅助脚本workflow 软链；hack 是拷贝——改源后必须重跑 setup
  • 幂等：可反复运行；绝不覆盖非本仓拥有的同名目录，自动清理源已删除的孤儿链接。
  • fail-soft：单个落点失败降级为 skipped 汇总，不让 set -e 带崩整条安装链。
  • 版本自报：由 git describe --tags 生成，没有手工维护的版本文件（手工版本号必然过期）。
  • 回滚：运行 checkout git checkout <上一良好 commit> + 重跑 setup.sh。

本仓自身就用这套流程管理变更（dogfooding）：仓根 openspec/ 是活的实例， 每个变更都走过 propose → 设计审 → 代码审 → done 归档的完整闭环。
