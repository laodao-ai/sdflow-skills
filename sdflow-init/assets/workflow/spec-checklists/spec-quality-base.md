# 通用 Spec 质量规则集（base）

> **定位**：项目无关、domain-agnostic 的通用质量门禁。任何 spec 都先过本 base，
> 再按变更命中的技术栈叠加 `domains/` 下的领域 delta。架构与选用规则见 [README.md](./README.md)。
>
> **落点列**：T=模版槽位 · C=生成约束 · S=自动扫描 · R=对话/评审（含义见 README）。
> 来源：综合 GStack plan-ceo/eng-review、SuperPowers brainstorming/writing-plans、IEEE 830/29148、NFR 标准。

---

## 【阻塞级】不通过则不得进入下一步

| ID | 规则 | 检查点 | 落点 |
|----|------|--------|------|
| BASE-01 | **完整性** | 所有受影响模块已识别？场景覆盖**四类**（正向/反向/边界/异常）？现有代码是否已部分解决（复用 vs 重建）？触碰 8+ 文件或新增 2+ 模块视为范围蔓延信号 | R |
| BASE-02 | **无占位符** | 无 TBD / TODO / 模糊占位；`"add appropriate error handling"` 也算违规 | S |
| BASE-03 | **可测试性 / 验收标准** | 每个主要需求条款说明可观察的验证方法；覆盖 unit / 集成 / （改 LLM prompt 时）eval；不得只写"测试通过" | T+S |
| BASE-04 | **规则 / 约束合规声明** | 声明对项目架构约束与既有规范的遵守或显式豁免；豁免必须写理由，不得沉默例外 | C |
| BASE-05 | **可行性** | 声明的方案在当前栈下真能实现？每个新 codepath 描述一个真实生产失败场景（timeout/nil/竞态/陈旧数据）？先搜框架内置方案再设计 | R |

## 【质量级】不通过会导致实现阶段返工

| ID | 规则 | 检查点 | 落点 |
|----|------|--------|------|
| BASE-06 | **错误处理完备性** | 每个错误路径有名字（异常类型/触发条件/处理者/用户可见行为/是否有测试）；每个数据流覆盖四条路径：happy / nil / 空 / 上游错误；禁 catch-all | R（物证面=失败模式表→T） |
| BASE-07 | **内部一致性** | 各章节无矛盾；架构描述与功能描述匹配；接口定义、数据类型前后一致 | S |
| BASE-08 | **外部一致性** | 与已有规则、其他 spec、已归档决策无冲突；不悄悄推翻既有约定 | R |
| BASE-09 | **清晰度 / 歧义消除** | 工程师拿到能不问问题直接实现；关键术语有定义；无可两种解读的条款 | R |
| BASE-10 | **范围 / YAGNI** | 无 YAGNI 违反、无范围蔓延；但若完整版边际代价接近零则优先完整版 | R |
| BASE-11 | **可观测性** | 新 codepath 有日志/指标/追踪规划；可观测性是交付范围而非上线后清理 | T |
| BASE-12 | **备选方案记录 / ADR（三镜决策）** | 2-3 方案对比（含最小可行 + 理想架构），**每个候选按三镜评估：系统镜（耦合/依赖/复杂度/可回退）· 用户镜（体验/可感知行为/干扰）· 开发循环镜（心智负担/是否靠人/流程开销/复用）**；关键决策按 ADR 结构落盘：**背景 / 候选方案 / 决策 / 理由（含一句主次判定：对当前决策三镜哪个更重要、为何据此选定，不只罗列）/ 当前方案代价**；被否决方案与否决理由记录在决策记录节。**命中 TG-23（≥2 合理方案 / 非显然设计）时，三镜 + 主次判定 MUST 书面写入；琐碎决策（无 ≥2 合理方案）不强制（避样板税）** | T+R |
| BASE-13 | **不在范围内声明** | design/proposal 有「不在本次范围内」节，逐项列 defer 工作 + 一句理由；每条附可证伪假设 | T |
| BASE-14 | **显式假设列表** | 所有"认为为真但未验证"的前提显式列出，每条标注"若不成立方案如何失效"（假设≠约束） | T |
| BASE-15 | **开放性问题** | 实现前未决问题显式列出，每条标注负责人 + 决策截止；未关闭不得进入实现（或标明哪些可并行） | T |
| BASE-16 | **NFR 数字化** | 性能/可用性/安全等非功能需求一律数字化，禁形容词（"快"不是 NFR；写 p95<200ms@1000并发） | T+S |

## 【完备性】时间允许时执行（出 ticket 前尤为有用）

| ID | 规则 | 检查点 | 落点 |
|----|------|--------|------|
| BASE-17 | **需求可追踪性（全链）** | spec 条款 ↔ task ↔ 实现 ↔ 测试用例 双向覆盖：每条需求有对应 task 与测试，每个 task 可追溯到需求来源（无幽灵任务）；跨 task 函数名/类型/常量一致 | T |
| BASE-18 | **分解检查 / fold-vs-defer** | 变更是否聚焦单一 capability？触碰多个**独立**功能域则拆为多个 change。**过程中（评审/grill）新发现的需求/修复是否并入当前 change：workflow 循环固定成本高，勿反射式以「单一职责」教条拆。判据走三镜、开发循环镜（增量审查成本 vs 一整轮 change 固定成本）通常主导，两级判定：①related 信号（紧耦合 / 一致性修复 / blast-radius 小）使其进入 fold 候选；②候选再过防吸积 AND 门 =「同 capability ∧ 高耦合 ∧ 低增量」三者皆满足才真 fold 进当前 change，任一不满足 → defer 另开（真独立 / 扩容大 / 需自身设计审查 / 高 blast-radius 天然落此）** | R |
| BASE-19 | **图表完备性** | 非平凡的数据流/状态机/处理管道有 ASCII 图；图是交付物，变更前后的依赖图都要画。**画哪些/何时/形态见 [`design-diagrams.md`](../design-diagrams.md)** | T |
| BASE-20 | **利益相关方与外部依赖声明** | 列出跨团队/系统的上游依赖与下游影响方；每项标注"对方是否知晓/是否需配合改动"；谁需 sign-off（标注**权力级别**：否决/决策/建议/知情） | T |
| BASE-21 | **合规声明** | 适用与否都需显式声明（数据居留/隐私/行业合规/审计留存/**数据是否发往第三方 + 脱敏策略**）；"本变更不涉及 PII，无合规约束"也是有效声明 | T |
| BASE-22 | **需求无实现细节混入** | proposal / 需求层只说"做什么"，不混入"怎么做"（实现细节留给 design） | R |
| BASE-23 | **需求优先级** | 每条主要需求标注优先级（P0/P1/P2），区分"必须有"与"锦上添花" | T |
| BASE-24 | **数据模型与生命周期** | 核心数据对象有字段级定义（类型/约束）；数据的创建/更新/删除/归档时机明确 | T |
| BASE-25 | **组件清单** | 设计列出各组件（名称/职责/技术栈/部署方式），与架构图一一对应 | T |
| BASE-26 | **外部服务成本估算** | 外部计费服务（LLM / 云存储 / 第三方 API）有月度/年度费用预算范围（仅外部计费服务适用） | R |
| BASE-27 | **时序可执行性** | 站在实现者视角推演：第 1 小时需要知道什么？第 2-3 小时会遇到什么歧义？第 4-5 小时什么会让他意外？所有"第 N 小时的意外"提前在 spec 写清 | R |
| BASE-28 | **安全与数据保护**（横切） | 识别信任边界与威胁面；信任边界处的输入校验；密钥/凭证/敏感数据的存储与传输处理（不落日志）；最小权限原则。领域特化见 domains（后端 Auth/越权、嵌入式安全启动/OTA 签名/密钥存储、前端 XSS/CSRF/CSP） | T+R |
| BASE-29 | **契约文档套件完整性**（防漂移，触发见 TG-25） | 变更触及版本化多文件协议/契约文档套件时，design 必含一张 scope-check 表：枚举**全套**文档 × 当前版本 × 本 change 是否改 × **不改的理由**（理由空着=不通过）。强制对"该改却漏列"的文件给出显式判断——**未列入**（清单里根本没有该文件）比**未完成**（标 `[ ]` 仍在列表）更危险，因为下次升级仍不会被想起。诊断与反 pattern 见 [`../reference/scope-drift-diagnosis.md`](../reference/scope-drift-diagnosis.md) | T |
| BASE-30 | **正文即最终态，演进史进附录**（触发：**改一份已存在的设计/决策文档**，尤其推翻既有方案时） | 正文只写**当前决策**（是什么 / 怎么做 / MUST / MUST NOT）；**否决的方案、否决理由、走过的弯路、元教训一律进附录**，正文只留编号引用〔A-n〕。**判据①（上一版测试）**：一句话若只有「读过上一版的人」才需要，它不属于正文。**判据②（删除测试，自检）**：删掉正文里所有含「原来/旧版/round-N/已作废/与旧版的差异/本节被收缩」的句子后，正文若依然完整 ⇒ 那些句子本就该在附录。**判据③（禁令与理由分离）**：「MUST NOT 做 X〔A-n〕」留正文，「因为 X 会……」进附录——**禁令要能独立成立，读者不需要庭审记录**。<br>**这不是美学项，它守的是高成本失效**：正文的考古层会给**已废弃的方向**一层「我们已审慎推敲过」的虚假正当性 ⇒ **评审者在错误分支内部做优化**。实证：某 change 的设计文档正文塞满修订播报，**四轮评审、18 面镜、150+ findings 无一发现整条推导链的起手式是错的**——所有镜子都在那条错路内部争论细节。 | R |

## 审计说明（本 base 相对原 universal 清单的变化）

- **合并**：原「plan 覆盖」「类型对齐」「可追踪性」三项归并为 BASE-17 需求可追踪性（全链）。
- **新增**（IEEE/NFR 标准中通用且原清单缺失）：BASE-14 假设列表、BASE-15 开放问题、BASE-16 NFR 数字化、BASE-20 利益相关方/外部依赖、BASE-21 合规声明。
- **回填**（自 srs-quality / sdd-quality 的通用孤儿项）：BASE-22 无实现细节混入、BASE-23 需求优先级、BASE-24 数据模型与生命周期、BASE-25 组件清单、BASE-26 成本估算；并扩充 BASE-01（四类场景）、BASE-12（ADR 结构 + 代价）、BASE-20（权力级别）、BASE-21（第三方数据/脱敏）。
- **并入 L2**（退役旧版 `Spec_Quality_Standards.md`，本集为单一源）：BASE-27 时序可执行性；SLA/RTO/RPO 属服务级，入 `domains/backend.md`（BE-11）。至此 base+domains 为原 L2 的超集。
- **剥离到领域**：原 universal 中「性能分析 / 安全边界」入 `domains/backend.md`（BE-03/06）、「分发管道」入 `domains/backend.md`（BE-10）、「UI 边缘场景」入 `domains/frontend.md`、「嵌入式」项入 `domains/embedded.md`。base 只保留 domain-agnostic 维度。
- **BASE-06 双面**：错误处理既是评审项（R），其物证形态「失败模式注册表」是模版槽位（T），两面并存不矛盾。
- **BASE-28 横切**：安全是跨领域维度，base 给通用口径（信任边界/输入校验/密钥/最小权限），各 domain 再特化（后端越权、嵌入式安全启动、前端 XSS）。
