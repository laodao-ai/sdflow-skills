工作流规则资产指南

sdflow 工作流 bundle 的完整规则资产清单——规则文件、机械层工具、配置模版、参考文档。除审查清单（spec-checklists / code-checklists）外的全部核心资产。审查清单体系见 checklists-guide。

全景 规则文件 机械层工具 配置模版 参考文档 领域关联
权威源位置：sdflow-init/assets/workflow/。经 setup.sh 安装到 ~/.sdflow/workflow/（全局 canonical），对本机所有项目即时生效。消费仓不保留规则副本——resolve-workflow.sh 运行时解析到全局 canonical。

二、规则文件（7 个核心规则）

这些是工作流的「宪法」——编排 skill 在运行时读取它们来决定行为。全部领域无关（领域特定内容在 checklists 里）。

workflow.md 规则 148 行

端到端流程总览——唯一线性路径的单一源。串联三阶段（生成 → 设计审 → 实现/代码审/闭环）的每一步，指向对应规则文件，自身不重复细则。

消费方：WORKFLOW-GUIDE.md（机械生成源之一）、所有编排 SKILL（流程步序依据）
关键约束：§一 步骤表（唯一线性路径）、§二 /clear 纪律（G1）、§三 设计门（G2/HARD-GATE）
trigger-catalog.md 规则 135 行 领域枢纽

触发词单一权威源——每个 TG-NN 编号同时驱动五层：D 约束注入、领域清单选用、画图要求、模版必填槽、评审 cross-model。是唯一连接「领域无关规则」与「领域特定清单」的枢纽。

TG 总览：TG-01 后端 · TG-02 嵌入式 · TG-03 前端 · TG-04~TG-10 后端细分 · TG-26 并发 · TG-27 LLM · TG-28 DevEx
HR-TG 子集：高风险触发词，命中后单开跨模型 outside-voice 领域镜（由 hr_tg_intersect.py 机械判定）
generation-process.md 规则 109 行

生成过程规则——Prevention 三杠杆（结构/约束/过程）中唯一无法固化进 config 的部分。规定 /sdflow-spec 的三相位（澄清 → 拷问 → 生成）、decision-memo 单一源机制、四件套全量生成策略。

§四 自动触发规则：人示意收敛（「开搞」「做吧」）→ 模型 SHALL 自动 invoke /sdflow-spec；模型 MUST NOT 自主判断「该开 change 了」
ff-generation-constraints.md 规则 198 行

FF-0 前置动作 + D 约束——FF-0 三分支判定（保护分支→建 / 本 change→跳过 / 其它 feature→halt 问人）是每次生成的起手式。D-1~D-6 是注入四件套的生成硬约束（如 D-2 DB 迁移须带 v_old/v_new 对照表）。

D 约束由 TG 驱动：命中 TG-04 → 自动注入 D-2；命中多个 TG → 取并集
design-diagrams.md 规则 120 行

设计期画图规则——将评审期的「缺图」发现前移到设计期。规定四类图（结构图/行为图/数据流/部署图）的适用条件、形态（ASCII 优先、Mermaid 可选），由 TG 决定该画哪些。

TG 驱动示例：TG-26 并发 → 必须有序列图（竞态时序）；TG-04 DB 迁移 → 数据流图（若涉及管道）
spec-review.md 规则 115 行

评审残差规则——只审 Prevention（config 固化的结构/约束）焊不住的残差：① Validation（语义判断）② 对抗（证明它会炸）③ 接地（读真实代码核对事实）。不重复检查机械层已防住的东西。

关键原则：Detection 只做 Prevention 残差；决策登记区替代中途 AskUserQuestion；对抗镜的职责是「证明它会炸」而非「这对吗」
model-tiers.md 规则 50 行

模型档位映射——strong / mid / light 三档在 Claude 与 Codex 两个机队的缺省模型 + effort 档（Claude 专属正交维度）。编排 SKILL 引用此文件的变量（$SDFLOW_TIER_STRONG 等），不内联模型名。

铁律：带门禁、无人逐条复核的步 MUST NOT 低于 strong 档（弱模型假绿放不完整的活过关）
覆盖：项目可在 config.yaml 加 model-tiers / effort-tiers 段覆盖缺省值

三、机械层工具（6 个确定性脚本）

「能机械判定的一致性绝不交给模型的自觉」（P1）——这些 Python 脚本是该原则的落地。全部只读、fail-closed、有配套 pytest 测试。

脚本用途消费方输出
anchor_lint.py 校验评审报告的 lens-metric 锚行是否符合契约枚举域/合法组合矩阵 sdflow-spec-review · sdflow-code-review exit 0=CLEAN / 1=VIOLATION / 2=ERROR
findings_ref_check.py 对 finding 的 {file, line, quote} 做路径存在、行号范围、引文子串三查（裁决协议第一层） sdflow-code-review Step3 per-finding pass / fail / uncheckable 三态
hr_tg_intersect.py 模型判定的命中 TG 集与 HR-TG 高风险子集求交，决定是否开跨模型 outside-voice sdflow-spec-review · sdflow-code-review hit / none + 规范锚串（带依据，不 emit 裸码）
lens_metric_emit.py 吃行键 roster + 结构化 findings，做折叠/归属/独立/sev-rollup 归约，输出合规锚注释行 sdflow-spec-review · sdflow-code-review lens-metric 锚行（符合 lens-metric-contract.md）
review_disposition_check.py fence-aware 断言 roadmap task-log 的「## Review 处置」小节存在且非空 sdflow-roadmap 收尾 section-missing / section-empty / section-ok-DISPOSITION-UNCHECKED
trivial_shape.py 只读 git diff，判是否为无逻辑面白名单形状（仅注释/文档/仅新增测试/版本常量），是则 Step2 多镜可免 sdflow-code-review Step1 trivial / non-trivial

另有 lens-metric-contract.md（98 行）作为 anchor_lint 和 lens_metric_emit 的枚举单一源——定义锚行的字段集、枚举域、合法组合矩阵。修改枚举域只改此文件，两个工具自动同步。

四、配置模版

config.template.yaml 配置 121 行

sdflow-init 用此模版为新项目生成 openspec/config.yaml。分两段：

通用段（照搬）：规则集指引、生成软约束（rules），全项目统一。

本项目段（自填）：tech stack、命中领域（backend / frontend(+frontend-react) / embedded / llm）、硬边界。领域声明决定评审时叠加哪套领域清单。

可选覆盖段：model-tiers.claude/codex.{strong,mid,light}（换模型）· effort-tiers.claude.{strong,mid,light}（调 effort）· metrics.enabled（开关复盘度量）

五、参考文档（说明类，可删不影响执行）

这些文件解释「为什么这么设计」，不参与运行时判定。删除它们不影响任何 skill 的执行。

文件内容
quality-layering.md 质量分层（shift-left）：解释 Prevention → Inline Detection → Residual 三层关系，论证 sdflow-code-review 为何必须「每次全跑做独立强制主审」（实测能抓循环内被说服放过的真问题）
scope-drift-diagnosis.md 协议漂移诊断：区分「未完成」vs「未列入」两种 scope 遗漏，解释 BASE-29 scope-check 表的设计原理
PRD_vs_Spec.md PRD 与 Spec 边界：PRD 回答「值不值得做」（用户/业务视角），Spec 回答「怎么做」（工程视角），两者职责不重叠
Spec_Quality_Methodology.md 质量方法论（L3）：最上层策略，与 L2 标准（spec-checklists）、L1 工具（tools/）分三层
Spec_Quality_Collaboration.md 协作分析：历史设计脉络，对话驱动生成 vs 批量审查评估的分工（现行工具已替代，仅存考古价值）
workflow-history.md 流程演进史（DOC-1 附录）：旧版 15 步 runbook 裁减/合并历史，不构成当前约束

六、领域关联分析

规则文件全部领域无关——领域特定内容只在两个地方出现：

                         trigger-catalog.md
                        ┌───────────────────┐
                        │  TG-01 后端        │
                        │  TG-02 嵌入式      │
                        │  TG-03 前端        │     ┌──────────────────────┐
                        │  TG-27 LLM         │────▶│  spec-checklists/    │
                        │  TG-28 DevEx       │     │    domains/*.md      │
                        │  ...               │     │  code-checklists/    │
                        └──────┬────────────┘     │    domains/*.md      │
                               │                   └──────────────────────┘
                  同时驱动五层   │                     领域规则承载体
               ┌───────────────┼───────────────┐
               ▼               ▼               ▼
        D 约束注入        领域清单选用      画图要求
     (ff-constraints)    (checklists)   (design-diagrams)
               │               │               │
               ▼               ▼               ▼
        模版必填槽       评审镜配置      cross-model 开关
      (config rules)   (spec-review)   (hr_tg_intersect)

设计要点：trigger-catalog.md 是唯一的「领域→行为」映射枢纽。新增一个领域只需要三步：① 在 trigger-catalog 加一个 TG 条目，② 在 checklists 两侧各建一个 domain 文件，③ 在 config.template.yaml 的 domains 列表注册。规则文件本身不需要任何修改。

规则文件中唯一的领域引用

trigger-catalog.md 的 TG 表是规则文件里唯一出现具体领域名称的地方（因为它就是领域的定义源）。其余 6 个规则文件通过变量引用——spec-review.md 写「命中的领域清单」而非「backend 清单」，model-tiers.md 写「$SDFLOW_TIER_STRONG」而非「opus」。这保证了新增领域时规则文件零改动。
