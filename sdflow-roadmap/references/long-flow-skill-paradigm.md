# 长流程 skill 设计范式

> **Skill 不是 orchestrator，是助产士。**
> 它帮项目开局立契约，之后由契约指挥流程。Skill 的质量不在于它多长，而在于它多早、多完整地把意图写进产出物。

本文是 `sdflow-roadmap` 的方法论源头文档，提炼自 2026-04-19 至 2026-04-20 对该 skill 后期失效问题的一次探索性讨论。其结论适用于任何"长流程 skill"的设计与体检。

---

## 问题陈述

Claude Code 的 skill 本质是"加载到上下文的 markdown 指令"，不是运行时 orchestrator。当一个 skill 的流程跨越多个阶段（如 roadmap-planner 的 5 阶段），它对流程的约束力会随时间**单调衰减**：

- 上下文压缩会逐步吃掉 skill 文本
- `/clear` 会一次性清空 skill 文本
- 后续阶段的 AI 可能"忘记"母 skill 的约束

**典型失效症状**：后期阶段省略 review、讨论无留痕、"差不多了归档吧"心态占上风。

## 核心原则：文档作为传递链条

Skill 不应依赖"持续驻留上下文"来保证各阶段的一致性。真正可靠的机制是**把每个阶段的意图固化到产出物**，由产出物充当传递链条。

```
错误心智模型：skill 全程指挥
   T0 ── T1 ── T2 ── T3 ── T4
    ↑    ↑    ↑    ↑    ↑
    └─ skill 文本（影响力随 T 衰减）─┘

正确心智模型：skill 在前期立契约，后期由契约指挥
   T0 ─ T1 ─[契约]→ T2 → T3 → T4
    ●skill●        ↑    ↑    ↑
                   └─ 契约文档（影响力恒定）─┘
```

契约有两个方向：

- **前向传递**：保存"推理过程"，防讨论消失（典型：`memo.md`、discussion scratchpad）
- **后向传递**：驱动"执行过程"，防走过场（典型：`tasks.md`、结构化 checklist）

## 三级契约可验证性

不是所有契约都一样可靠。按"可被机械或目视检查的程度"分三级：

| 级别 | 形态示例 | 可检查性 | 糊弄成本 |
|------|---------|---------|---------|
| **A. 可打勾** | `- [ ] 跑 review` | 只能看打勾状态 | 极低 |
| **B. 产出 artifact** | `- [ ] 跑 review，记录到 log.md` | 可查 artifact 存在 | 可空壳 |
| **C. 结构化状态** | `- [ ] 每条 issue 标 ✅采纳/❌拒绝/⏭延后 + 理由` | 可查结构完整度 | 很难糊弄 |

**设计准则**：所有 checklist 条目都应升到 C 级；若一条无法升级，说明它本就不该写成 checkbox（要么删掉、要么改成叙述）。

## 三个设计准则

### 准则 1：每个阶段都要有文档出口

不产出文档的阶段 = 最脆弱的阶段。讨论、探索、头脑风暴这些"软阶段"最容易被当成"可以不留痕"，但它们产生的"为什么选 X 而不是 Y"是后期最难复原、最有价值的信息。

| 阶段规模 | 文档策略 |
|---------|---------|
| 短（<10 轮、单 session） | 文档可选 |
| 中（10-30 轮） | 结束时一次 flush |
| 长（>30 轮、跨 `/clear`、跨天） | **强制**骨架 + 增量 append |

**判别不确定时向上一档取**——多留 footage（讨论考古材料）的成本远低于丢推理过程。

### 准则 2：契约条目要求结构化状态

把"做了吗"升级为"做的结果是什么"：

- ❌ `- [ ] 处理 review issues`
- ✅ `- [ ] 每条 issue 标 ✅采纳（改动位置）/❌拒绝（理由）/⏭延后（去哪处理）`

后者让 apply 必须产出结构化 artifact，verify/人工能机械检查完整度。

### 准则 3：默认行为朝安全方向偏

当 AI 不确定时，让默认选更保守的做法：

- 讨论规模不确定 → 向上一档取（多写 memo）
- 契约状态不明确 → 按"未处置"对待（阻止进入下一阶段）
- 跳过某阶段 → 强制留痕"为什么跳过"
- verify 边界模糊 → 声明为"人工复核"，不假装自动化

## 反模式

| 反模式 | 典型表现 | 修法 |
|--------|---------|------|
| **依赖文本驻留** | "skill 会记得"的错觉 | 把规则编码到产出物 |
| **契约只打勾** | `- [x] 跑 review`（无 artifact） | 升级到 B/C 级 |
| **讨论不留痕** | 只存结论 design.md，丢推理 | 引入 memo.md 策略 |
| **合规 ≡ 质量** | 以为 verify 能替代评审 | 明确区分：verify 查"做没做"，plan-review 查"做得好不好" |
| **虚假自动化** | 谎称"verify 会扫这条" | 诚实标注"人工复核"，未来再接 hook |

## 实战案例：roadmap-planner 的应用

本范式直接从 `sdflow-roadmap` 的失效案例抽象而来：

| 原缺口 | 对应准则 | 修法 |
|--------|---------|------|
| 讨论阶段无 memo 留痕 | 准则 1 | 新增"memo.md 策略：讨论规模预估"章节 |
| review 条目只打勾 | 准则 2 | tasks.md 3.x 从 A 级升到 C 级 |
| 跳过 review 无痕迹 | 准则 3 | 强制"跳过即留痕，归档前再确认" |
| verify ≡ 质量的混淆 | 准则 3（诚实） | 3.4 明标"人工复核项，verify 不扫" |

## 对其他长流程 skill 的推论

以下长流程 skill 都应该自审是否具备"契约闭环"：

- `/ship`、`/land-and-deploy`：跨越本地 → PR → 合并 → 部署 → canary，每一步的成功/失败凭证是否固化到文件？
- `/qa`、`/investigate`：多轮修复时，"每个 bug 的处置状态"是否落到文件？
- `/autoplan`：跑完 CEO/eng/design 三者，分歧点是否有结构化决策日志？

## 契约体检清单

拿任何长流程 skill，按这 4 条自审：

- [ ] 每个阶段都有对应的**持久化产出物**吗？
- [ ] 每个 checklist 条目都是 **C 级**（结构化状态）吗？
- [ ] 有没有"讨论型阶段"完全**无文档留痕**？
- [ ] 最后一步归档时，前面所有阶段的状态能**只读文件重建**吗（不依赖 skill 还在上下文里）？

四条全过 → 契约闭环成立，skill 后期可自持。
任一条未过 → 该点是未来失效的种子。

---

## 范式一句话

Skill 的影响力不在于文本驻留的时长，而在于**契约编码的深度**。
